# Plan lifecycle: one trustworthy next action

**Priority.** Add a compact Company plan-lifecycle card above the existing forms. It shows one primary action for the selected plan and a secondary list of other versions. Keep all exact-plan review and build controls in place. This is a UI change; `Company` and `Harnesses` remain the authority for decisions and admission.

**Observed contract.** `Company.plan_dto/1` returns `status` (`proposed`, `approved`, `rejected`) and `superseded` separately (`company.ex:350-360`). `Company.decide_plan/2` checks the displayed revision (`:stale_revision`), rejects a second decision (`:already_decided`), and approves only current, unsuperseded context (`:superseded_revision`, `:stale_plan`; lines 111-125, 323-335). `Company.build_inputs/1` requires exact approval (`:plan_not_approved`) and re-resolves the pinned snapshot; changed claims/sources/catalogue yield `:stale_claim`, `:claim_not_approved`, `:stale_source`, or `:stale_plan` (lines 139-149, 267-325). `Harnesses.build_plan/2` also rejects a wrong displayed hash as `:stale_plan_revision` (`harnesses.ex:71-79`). Current cards show status and `HAS SUCCESSOR`, but the build button keys only on `approved` (`company/plan.ex:246-335`). The portal's singular “awaiting a decision” metric counts claims alone (`portal_live.ex:980`).

**Acceptance.** Empty: card names the missing profile/project/approved-claim prerequisite and links to its existing control; never marks sources complete. Proposed: one action opens exact plan review, with decision pending; no build invitation. Rejected: show rejection and offer a new proposed successor, never an approval retry on that immutable revision. Approved/current: offer build only after a fresh `Company.build_inputs/1` readiness check. Approved ancestor with proposed successor: show both revisions and their independent decisions; the ancestor stays buildable when still eligible, while the successor remains pending (`company_harnesses_test.exs:105-123`). Stale selected context: show the returned reason and one repair action to review current records and propose a new version; disable build/approval, without changing the stored decision label. A wrong hash or already-decided submission gets a visible specific recovery message. Separate pending claim and plan counts; preserve draft values and keyboard focus when opening the target section. Verify these states in LiveView tests and native keyboard/narrow-screen journeys.

**Risk.** A preflight result can race later edits. Recheck in `decide_plan`/`build_plan`; never present preflight as approval or package eligibility. Avoid treating a successor flag or stale context as a persisted decision transition.
