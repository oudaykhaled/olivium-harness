# Validation recovery: one actionable error

**Observed.** `CompanyPanel.finish/4` puts failures in one `#company-error` alert above seven sections. Specific messages exist for stale displayed context/plan, missing exact-plan approval, already decided/superseded plan, no approved claims and unavailable selection (`company_panel.ex:483–519`). Other reasons, including malformed input, duplicate repository identity, missing profile, out-of-scope membership and milestone errors, fall through to “The action was rejected. Check required fields, explicit memberships, current approved claims and milestone dependencies.” The malformed targeted-plan test asserts this generic string and component survival, but no focus or draft preservation (`company_builder_test.exs:272–313`). Catalog fields have labels and plan rows have stable IDs; the alert identifies neither the failed form nor a control.

**One bounded proposal.** For known domain reasons, associate an error with its form, the field or selected record when determinable, and one corrective action. A summary beside the active form links to that target. Keep the top alert as an announcement and link to the summary. Unknown or malformed event shapes retain a generic message without echoing submitted data or hidden IDs. Stale exact-plan errors lead to current-plan review, never implicit approval or automatic selection.

**Acceptance.** On invalid profile, project membership, repository identity, plan execution limit or milestone dependency, the user sees one concrete correction, the affected field/fieldset is identified with `aria-describedby` and `aria-invalid`, and the summary is keyboard reachable. After submission fails, entered text, checkboxes, milestone rows, selected project/plan and exact revision identity remain unchanged; focus moves to the summary, then its link reaches the relevant control. After correction, the error clears and the original action can succeed. Rejected/stale decisions retain the entered draft while presenting the current record for explicit review. Verify one happy and one error path in the real browser with role/label locators, keyboard-only navigation and an axe check; LiveView tests cover domain mapping and retained values.

**Risks.** Mapping a domain reason to the wrong field could mislead; only map reasons with a reliable target and keep remaining errors form-level. Avoid client-side reset during LiveView patching and avoid moving focus on routine `phx-change` events.
