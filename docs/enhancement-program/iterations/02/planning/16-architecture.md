# Planner 16 — Company guide and render cost

**Recommendation.** Add a Company-only progress guide above the existing seven sections. Derive one next action from already loaded profile, repositories, projects, sources, approved claims, plans and artifacts. Distinguish pending claim decisions from pending plan decisions; keep goals and milestones optional. Label an approved plan as an *approved decision*, never as currently buildable or qualified. On a stale admission error, guide the operator to review context and propose a successor.

**Code evidence.** `CompanyPanel.update/2` reloads profile, repositories, projects and plans (`company_panel.ex:33-38,357-381`); `PortalLive.reload/1` already loads sources, claims, approved claims and artifacts (`portal_live.ex:629-670`). `Company.list_plans/0` maps each plan through `plan_dto/1`, whose status and successor checks query decisions and plans (`company.ex:103-107,349-360`): do not add another per-plan lookup during render. `Catalog.setup/1` and `Plan.builder/1` render all sections unconditionally (`company_panel.ex:543-571`); plan form changes already maintain `plan_draft` (`company_panel.ex:143-150`). The global workflow marks source connection complete unconditionally and its decision metric counts claims only (`portal_live.ex:976-992`). Mobile CSS hides that workflow (`app.css:122`).

**Smallest design.** Compute a pure guide view model once per Company component render from the existing assigns; pass a single pending-claims count from `PortalLive`. Reuse current `company_navigate` for cross-tab actions and stable section IDs for local actions. Wrap existing sections in accessible `details`/`summary` disclosure, or equivalent local open-section state; keep forms mounted so unsaved input and keyboard focus survive disclosure changes. Keep catalog and plan components as the form owners. No new contexts, schema, dependencies, polling or per-item readiness probes. Domain admission remains in `Company`/`Harnesses`; the guide is presentation only.

**Acceptance and risk.** Empty, partial, proposed, rejected, approved and stale scenarios expose a truthful next action and separate pending counts; keyboard and narrow-screen journeys preserve drafts and focus. A proposed successor must not erase an earlier approved plan. A stale approved plan cannot be called eligible based on status alone: report an explicit unknown/current-check-needed state until existing admission runs. Check query counts and LiveView patches against the baseline; avoid a full `reload/1` on disclosure clicks.

**Ownership proposal.** One UI author owns `company_panel.ex`, `company/catalog.ex`, `company/plan.ex` and Company CSS; root coordinates `portal_live.ex` metric/assign changes and integration tests. No `Company` or database changes.
