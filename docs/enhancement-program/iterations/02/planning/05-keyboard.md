# Keyboard focus and task navigation

**Observed baseline.** Company renders seven sequential steps in one panel (`lib/harness_forge_web/components/company/catalog.ex:26`, `lib/harness_forge_web/components/company/plan.ex:256`); the saved accessibility snapshot lists source review, plan proposal, decision and build controls after the first form (`tmp/enhancement-program/01/browser/company-dom.txt:82-248`). The screenshot shows workflow chrome above the first form (`tmp/enhancement-program/01/browser/company-before-ux.png`). Company actions send `company_navigate`, and Portal only assigns a new tab (`lib/harness_forge_web/components/company_panel.ex:58-62`, `lib/harness_forge_web/live/portal_live.ex:369-370`). Buttons and summaries have focus outlines, while fields use a border/shadow treatment (`assets/css/app.css:16,25`). This is code and static baseline evidence, not a keyboard audit.

**Bounded next action.** Add one state-derived Company next-action control that opens the relevant existing step or workspace tab, then moves focus to its heading or first required control after the LiveView update. For an in-page step, scroll it into view; for a tab change, focus the destination heading with `tabindex="-1"`. Provide a stable, keyboard-operable way back to Company with the plan draft intact. When sections are progressively disclosed, use semantic buttons or `details`/`summary`, expose state, and never hide the focused control. Keep exact claim review, exact plan review, and build as distinct actions; optional goals must not block required progress. On validation failure, put focus on a concise error summary linked to the affected form/control, preserving entered values. Preserve existing approval and eligibility gates.

**Behavioral evidence required before acceptance.** In a real native Chrome synthetic workspace, use Playwright role/name and label locators for the Company action, destination heading and form controls; assert `document.activeElement`, visible focus, Enter/Space operation, Tab and Shift+Tab order, return navigation and draft retention. Exercise empty, partial, proposed, rejected, approved and stale-plan states plus a rejected form submit at desktop and 390px width. Capture before/after screenshots and a focused accessibility-tree snapshot; run `@axe-core/playwright` on the new summary and error state, report violations and manual keyboard observations separately. The current `test/browser/smoke.cjs:20-90` covers mouse-led flows and mobile rendering, not this behavior.

**Risks.** LiveView patch timing can send focus to a removed node; focus only after the destination exists. A collapsed section can strand focus or silently discard a draft. Automated axe results alone cannot establish accessibility conformance.
