## Blocking

### CR-1 — A reset-generation wrapper does not erase focused browser input

Owner: A/B. Source at review: `lib/harness_forge_web/components/company_panel.ex:864`; stable descendant controls in `company/catalog.ex:61` and `company/plan.ex:107`.

**Disposition: closed for the corrected v2 candidate by the administrative evidence closure above.** Original finding, line anchors and requested conditions below are retained as review history.

At initial review, the reset changed the inner `company-cache-0` wrapper to `company-cache-1`, but every descendant form and input kept its original ID. The installed LiveView 1.2.13 client indexes keyed descendants and reuses them even while adding a different ancestor (`deps/phoenix_live_view/priv/static/phoenix_live_view.esm.js:2196–2220`, `2351–2366`). Its captured focused control then takes the focused-input preservation path (`2722–2728`); `mergeFocusedInput` excludes the new `value` (`863–866`). A sibling tab could therefore keep a private focused input value after successful purge/restore even when server assigns were cleared and rendered HTML contained no canary. The original server-only cache assertions at `test/harness_forge_web/company_builder_test.exs:658–662` could not establish this browser boundary.

Fix: make the privacy generation force authoritative values onto reused client controls, or replace the actual keyed component/input boundary. Trigger that mechanism only on server reset generation changes; preserve ordinary typing, refresh, drafts, fixed navigation destinations and unrelated controls. Root must record a disposable synthetic client/browser regression with a focused canary in the sibling view. No destructive operation against main/demo/native workspaces is needed or authorized by this review.

**Round 2 source resolution:** `assets/js/app.js:28–95` now installs a LiveSocket `dom.onBeforeElUpdated` callback for nine compiled Company form IDs. It acts only when both generations are valid safe nonnegative integers and the incoming generation increases. It matches controls by tag/type/name plus checkbox/radio value; copies authoritative live/default values, checked/defaultChecked and selected/defaultSelected state; clears obsolete controls; and stamps the new generation. It resets both the supplied form and the connected form if LiveView supplied a private lock clone. All nine forms carry the token through Guide (`guide.ex:55`, `265`), Catalog (`catalog.ex:23`, `47`, `174`, `286`, `360`), and Plan (`plan.ex:23`, `93`, `285`, `309`, `385`, `527`, `589`); CompanyPanel passes it to both builders. Normal equal-generation patches return without mutation. Existing fixed focus destinations and colocated/chat hooks remain intact. The installed client invokes this callback through its before-update hooks, including the locked clone path. This addresses the identified source mechanism.

**Original requested closure evidence, owned by root/conductor:**

1. Exercise the served correction through the actual installed LiveView 1.2.13 patch machinery in disposable synthetic Portal instances. A private QA stdin PubSub reset is sufficient; no new product endpoint, purge or deletion is required.
2. Keep the sibling on Company with a focused input/textarea canary, checked selection and changed select/milestone state. After a real server reset generation reaches it, inspect live `.value`, defaults, checked state and option selection, as well as the cleared server draft. Server-rendered HTML alone is insufficient.
3. Include a genuine pending form lock/ack sequence. Verify both visible connected controls and any supplied private clone are corrected, and that the subsequent acknowledgement does not reintroduce the pre-reset canary or roll the generation back. Returning early for older/equal incoming generations is not itself proof that LiveView will not later morph stale source DOM.
4. Confirm ordinary typing and a same-generation parent refresh retain the draft, focused value and checkbox/milestone selections, with no focus jump. Retain the separate ordinary refresh token behavior.

Round 2 accepted the source correction while leaving observed-client evidence open. The focused/pending-submit artifacts above now close this finding for their bound candidate. Final iteration acceptance remains separate.

### CR-3 — Queued pre-reset Company events can recreate cleared drafts or save them

Owner: A event admission with B event transport and C regression coverage. Confirmed by source inspection at root's request; the requested real-browser queue ordering has not been executed by this reviewer.

**Disposition: closed for the corrected v2 candidate by the administrative evidence closure above.** Root executed the real queue/lock/ack proof; this reviewer read its artifacts. The original source finding and line anchors below describe the pre-v2 implementation.

**Line/risk:** `lib/harness_forge_web/components/company_panel.ex:84–96` admits events using authentication and shape only. There is no comparison with `socket.assigns.company_reset_token` before capture or domain dispatch. Forms contain `data-company-reset-token` (`catalog.ex:47`, `plan.ex:93`, `guide.ex:265`), but no generation-bearing named input or `phx-value-*` metadata. Installed LiveView serializes named controls through `FormData(form)` (`phoenix_live_view.esm.js:6021–6036`); its metadata extractor copies only `phx-value-*`, not arbitrary `data-*` (`5991–6000`). The existing reset callback changes DOM values after a server patch and cannot invalidate a form payload that the client already serialized.

**Concrete ordered path:**

1. A valid operator has a Company form at generation 0 with an unsaved private canary; its normal change/submit payload is serialized before the browser receives a reset.
2. `PortalLive.handle_info(:company_cache_reset)` increments generation and reloads (`portal_live.ex:386–388`, `665–666`). CompanyPanel clears state before reassigning/reloading (`company_panel.ex:30–40`). Authentication remains valid.
3. The already serialized old change is then processed. It passes admission and `company_profile_change` calls `capture_draft` (`132–141`, `530–550`), recreating the private draft at generation 1. `company_plan_change` likewise assigns the old plan draft (`249–257`). The next patch is equal-generation, so the reset-only client callback intentionally does not erase it.
4. An old profile save captures the old payload before its record check (`154–163`). `pinned_input` compares only content hash and record ID (`553–557`). For a new profile, both hashes can still be nil, and `Company.expected_hash(nil, nil)` accepts creation (`company.ex:195`). With unchanged saved context, the old matching hash also permits save. The same absence of event freshness applies to other catalogue/plan/cache events.

The domain purge lock is not a fence for old UI generations. `Company.mutate` serializes with purge (`company.ex:393–395`), while `Workspaces.ensure_writable` only calls privacy readiness (`workspaces.ex:22–26`); readiness becomes `:ok` when no incomplete privacy operation remains (`privacy/purge.ex:10–17`). After successful completion it does not distinguish a pre-reset browser event. Existing exact approval/build admission and auth still apply, but neither establishes event freshness.

**Fix:** carry the bounded server reset generation in Company event payloads and compare it with the current generation before any draft/cache change, selection or domain action. Reject stale, missing, malformed and future values without capturing/echoing their content; preserve ordinary same-generation drafts and current events. Keep the DOM callback for already displayed/locked values. A generation-bearing named field handles form serialization; fixed button metadata needs equivalent admission if the component uses a uniform fence. No domain/schema/API or session renewal is required.

**Required regression/evidence:** in a disposable synthetic Portal channel, queue `:company_cache_reset` first, then an already serialized pre-reset real browser change and submit, resume processing, and inspect after the actual acknowledgement. The old canary must remain absent from server draft, live DOM/defaults and saved catalogue, and no old action may restore selection/preflight/cache. Prove a fresh generation event works afterward and same-generation ordinary typing remains preserved. This is the pending lock/ack condition made concrete, not replaced by a direct callback invocation or server-only rendered assertion. No product endpoint or destructive privacy operation is needed for the requested probe.

**Authorized v2 resolution and provenance:** the accepted [admission decision](admission-decision.md) replaces numeric-counter-only admission with a fresh 128-bit opaque generation on each component mount/reset, independent of the numeric DOM-reset token. As independently reviewed by the guardrail owner, all nine forms send one enabled named root generation and all 22 click producer definitions send explicit metadata. Panel authenticates first, then requires an exact current bounded lowercase-hex root generation before normalization, capture, cache/selection changes or domain dispatch. Missing/stale/malformed envelopes change only a fixed notice; ordinary refresh preserves generation; parent overrides are dropped. Tests capture raw old envelopes before reset and replay them unchanged afterward, including old-mount rejection when numeric tokens both equal zero, valid current events, privacy-success/sibling paths and domain/audit non-mutation. The actual queued profile submit above supplies the separately required installed-client lock/ack proof. This resolution was reviewed under root's escalation decision, not an extra independent source round by this reviewer.

## Non-blocking

### CR-2 — Execution fields bypass the bounded string validator (closed)

Owner: A, with C regression coverage. Source at review: `lib/harness_forge_web/components/company_panel.ex:463–465`.

`valid_plan_shape?/1` accepts any binary for `max_turns` and `timeout_seconds`, whereas other scalar fields enforce 16,384 bytes. A targeted change stores and renders the oversized value, and create also sends it to `Integer.parse/1`. Authentication remains enforced, so this is bounded-input hardening rather than a claimed unauthenticated exploit.

Fix: apply the existing scalar byte limit to binary execution values while preserving supported integer values. Add targeted oversized change/create cases that retain the previous draft and create no plan.

**Round 2 resolution:** `company_panel.ex:464` uses `(bounded_text?(value) or is_integer(value))` for these execution values. The then-current `company_builder_test.exs:349–384` regression covers 16,385-byte values independently for both fields on targeted change and create, asserts the prior draft remains intact and no plan is created, then successfully creates an integer-valued proposed plan. The corrected raw targeted transport test passed in focused 06 (16/0) and remains covered by focused v2 (19/0) and UX correction (20/0). Source and executed regression evidence close CR-2.
