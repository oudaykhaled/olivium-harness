# Independent retrospective 04 — trust, privacy and security

**“Was this tool really helpfull and reliable to build a complete harness for a company? and what is missing to make it reliable?”**

**Verdict:** Helpful for reviewed local company harness construction; complete company reliability remains unproven. Iteration 02 improves truthful guidance and privacy lifetime. It demonstrates synthetic construction/build/export, without establishing real company policy completeness, model fitness or operational outcomes. This verdict concerns the frozen final candidate; root’s ongoing main upgrade is unverified here.

Ranked missing capabilities, rather than newly demonstrated exploits:

1. **Qualified company outcome evidence.** Existing [evaluation/release gates](../../../../../lib/harness_forge/releases/validation.ex) distinguish static integrity from qualified tasks, but no real-company pilot exists. Add a company qualification-readiness record bound to exact plan/artifact, suite/grader, runtime/model/environment and cleanup identities. Acceptance: synthetic positive flow produces an attributable receipt; stale inputs, forged results, missing isolation/model, cancellation or incomplete cleanup block qualification. Goal-origin policy and explicit conflict-resolution support must remain visible completeness gaps. Company-reliability claims require an independently graded authorized pilot with declared task-success, cost and failure criteria.
2. **Portable authenticated approval.** Exported v1alpha1 provenance cannot independently prove local company-plan approval ([contract](../../../../company-builder-contract.md)). Add versioned signed approval receipts with explicit signer trust, company/scope/claim/plan/artifact bindings and revocation semantics. Acceptance: a fresh-workspace verifier rejects tampering, unknown/revoked signers and mismatched bindings; historical v1alpha1 bytes remain verifiable without gaining portable approval authority.
3. **Per-client machine-access lifecycle.** [MCP](../../../../mcp.md) deliberately uses a separate shared bearer; browser logout leaves it valid, and rotation requires owner restart. Add client-specific read scopes, expiry, selective revocation and metadata-only audit. Acceptance: expired/revoked client A is refused while client B works; responses/logs expose no credential/source bodies. Preserve the three read-only tools and default-off behavior.

**FUNCTIONALITY 03:** implement item 1’s bounded readiness/receipt path using existing Evaluations/Releases; retain unavailable inference as a blocker. Portable authority and client lifecycle follow separately. **Next UI priority:** a package handoff showing approval, integrity, current eligibility, runtime/evaluation and release status separately, with accurate export-path recovery and stale errors cleared after success. Acceptance must include keyboard recovery and actual 200% zoom; current narrow-screen evidence supplies no zoom proof.
