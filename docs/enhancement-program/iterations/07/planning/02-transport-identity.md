# Transport identity: one validated observation per coding attempt

**Recommendation.** Give each task attempt one validated, typed Docker transport observation, then derive relay mode, proxy configuration, network expectation, and persisted environment profile digest from it. Discover before resource creation and record an unavailable reason if discovery fails. At release admission, independently observe the current route and compare its derived profile with the historical run; preserve read-only Readiness abstention. This repairs a qualification prerequisite, not company/model quality.

**Evidence.** `Coding.profile/0` calls `transport/0` three times (`lib/harness_forge/execution/coding.ex:28-50`). `Coding.run/2` discovers again at line 130; `start_proxy/2` rediscovers at 446 and `verify_container/6` at 661. Discovery maps *every* non-`Docker Desktop\n` result, including timeout and malformed output, to Unix (427-431). `Evaluations.create/2` persists `Coding.profile_digest/0` before dispatch (`lib/harness_forge/evaluations.ex:391-415`); `Evaluations.applicability/2` later rediscovers through the same digest (64-109), which `Releases.Validation.check/3` trusts (45-48). This is source-derived inconsistency, not an observed exploit. `Readiness.current_task_identities/1` correctly abstains for OpenCode (`lib/harness_forge/readiness.ex:105-110`). Existing run/workspace/profile labels govern teardown (`lib/harness_forge/execution/coding.ex:634-642,690-694,802-820`); retain them independent of current transport.

**Decision trade-off.** A route-string-only parameter to `start_proxy` leaves profile creation, container verification, and later applicability free to disagree. A broad runtime redesign increases blast radius. The typed observation costs one explicit failure path and a live recheck at release; keep the supported Desktop/Unix signatures explicit and reject unknown output rather than guessing Unix. Do not rewrite historical run identities.

**Acceptance.** Positive: recognized Desktop and supported Unix observations each yield one attempt profile whose route, proxy digest, relay mode, and verified networks match the dispatched resources. Negative: timeout, nonzero exit, malformed or unknown OS output blocks before relay/container creation and never records a qualified Unix route. Edge: changing route or model configuration after a completed attempt makes release applicability fail; cancellation/reconcile still remove only originally labeled resources, and synchronous Readiness remains command-free/Not assessed.

**Ownership/verification.** Principal Elixir author owns `Coding` and focused tests; root owns shared `Evaluations`/release integration and the sole Mix window. Use an injectable Docker-command seam for positive/negative/drift tests, then one root-coordinated guarded Docker integration on each available supported route. Report unavailable routes explicitly.
