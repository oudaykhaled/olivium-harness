## Blocking

**B1 — Revoke the owned local relay even when original Docker identity is unavailable.** `lib/harness_forge/execution/coding.ex:864` puts `CodingTransport.verify(observation)` before `CodingSession.stop(id)` at line865. A cancelled running attempt with a valid persisted context but unavailable/mismatched daemon exits cleanup before stopping its local relay. `Evaluations.cancel/1` records cancelled/cleanup_failed, but `Relay.handle_call({:chat,...})` and `Models.Runtime.chat/2` do not inspect that cancellation. An already-running original candidate/exec connection can continue requesting inference until execution unwinds or relay lifetime expires. This is a source-derived regression: before07, `cleanup_owned` stopped CodingSession before Docker operations. Normal `Coding.run` eventually calling `Relay.stop` does not revoke authority when the cancellation request returns and the original execution is still active.

Concrete fix: after validating the persisted owned run/context, stop its owned local CodingSession before checking daemon identity; keep the identity guard before every Docker observation/mutation and retain context plus failed cleanup when that guard fails. This preserves original-daemon safety while revoking local capability independently of daemon availability. Alternatively, implement separate always-attempted local revocation and guarded remote cleanup phases; that is more explicit but a larger change. Do not fall back to another daemon or report cleanup complete.

Root verification requested: start a controlled active relay/coding attempt, make the original ID guard fail while execution remains active, cancel, and prove session/listener revocation, refusal of subsequent inference, no Docker resource mutations, cancelled outcome, failed cleanup and retained context. Retry after restoring original daemon identity must preserve cancellation. I performed no runtime reproduction; root was sent this exact request before this report. Root subsequently confirmed the source ordering and accepted B1 as blocking, taking bounded correction ownership plus an actual active-Relay/CodingSession failing-ID regression. ## Root-requested B1 revocation-scope addendum

**Decision: actual persisted workspace/run ownership is sufficient for local session revocation, before private-context decoding.** This refines B1's initial suggested ordering. I read the relevant live Coding/Evaluations/CodingSession/Relay source on root's explicit follow-up; these reads are not a new frozen-candidate acceptance. No peer report, runtime check or product edit was performed.

The local session is addressed by `{CodingSession, Workspaces.current_id(), id}`. Its stop handler uses its already-owned in-memory Relay handle/token to revoke the listener; it does not derive a destination from `execution_context`. Therefore a valid run UUID and an actual database row whose `id` and `workspace_id` match the requested run/current workspace authorize this local revocation even when its result or private context is corrupt/null. A missing or foreign persisted row must not authorize stopping another session. Keep revocation serialized with resource creation under the existing Coding per-run lock; missing local session remains an idempotent success.

**Docker authorization remains stronger and unchanged:** exact private-context ownership/profile validation, original endpoint/daemon verification, and resource labels/absence checks must precede Docker effects. A dispatched row with corrupt/null context still fails cleanup, remains unqualified, retains its authority record and issues zero Docker commands. Successful local revocation alone never means resource cleanup complete. A local stop error must also prevent a complete result. Existing restored/static/no-session branches stay no-daemon-contact.

The minimal correction must cover both call paths. Moving stop earlier inside `Coding.cleanup/1` alone is insufficient: `Evaluations.cleanup_backend/1` rejects corrupt context before calling it. Reuse one owned-local-revocation boundary before that classifier can return an error, and enforce the same ownership/lock rule for direct Coding cleanup. This serves cancellation, retry, recovery and scoped purge without inventing a fallback backend or cleanup sweep. A broader cancellation check inside every model request is a possible extra defense but spans another execution contract and is not needed for this bounded correction; limiting the reorder to valid decoded contexts is smaller but leaves the same failure under context corruption.

Root evidence requested: active session with valid context/failing ID, active session with corrupt context, and active session with missing required context must all revoke the owned local capability while preserving cancelled/failed cleanup and zero unauthorized Docker mutation. Missing/foreign-row cases must not stop a session; restored/static absent-session cases must issue zero Docker commands. The initial reproducer's omitted public workspace_id caused an earlier classifier rejection, so it does not yet establish the intended valid-context/failing-ID RED. Root is correcting that premise before RED/GREEN. All verdicts above remain open pending actual results and a new freeze.
