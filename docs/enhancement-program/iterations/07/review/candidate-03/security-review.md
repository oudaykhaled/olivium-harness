## P1 closure and authority separation

**Root P1: cancellation could retain a usable local relay when original Docker verification failed.** Candidate02 `coding.ex:858–865` required context and daemon verification before `CodingSession.stop`. Thus a durable cancellation/cleanup-failed result could coexist with a live local capability. Root's corrected RED02 demonstrates that live-session state; it does not demonstrate a successful attacker inference. Severity is P1 for the accepted cancellation/security contract. CVSS is not assigned because the supplied reproduction establishes revocation failure, without measuring attacker reachability or downstream confidentiality/resource impact. The threat is bounded to an existing owned active relay and its capability, not an unauthenticated remote endpoint.

Frozen03 `coding.ex:853–870` introduces internal `stop_session/1`: it takes the existing per-workspace/run Coding lock, validates the UUID, queries an actual persisted Run with both current workspace and run ID, then calls CodingSession.stop. It does not trust the public result or require intact Docker context to revoke an already-owned **local** capability. Missing/foreign rows return a fixed context-invalid error without session revocation. Direct cleanup uses the same locked private helper **before** context decode at `:873–879`; it avoids recursively acquiring the public lock from inside the cleanup lock.

`evaluations.ex:707–725` invokes this local stop before backend classification, covering null/corrupt context that would otherwise be rejected before Coding.cleanup. A local-stop error short-circuits backend work; the existing rescue/result handling returns a bounded cleanup error. The subsequent coding cleanup still decodes persisted original context, checks public identity/ownership and original daemon ID, and verifies resource labels/absence. The change grants no Docker permission from mere row existence and adds no default-daemon fallback. Static, managed and restored paths may attempt an idempotent local-session stop, but still issue no Docker command under their existing classifier.

The unchanged `coding_session.ex:8–29` propagates Relay.stop failure, stops normally on success and is workspace/run keyed. `relay.ex:44–57,160–165,179–196,252–256` stops the capability listener/process and checks stopped state. Existing fences serialize local session creation with the same Coding lock; cancellation marks the row cancelled before cleanup, so later effect fences cannot restart it as running. A direct cleanup call is not itself a cancellation-state transition; this review does not claim otherwise.

The expanded focused tests actually create Relay/CodingSession processes, prove initial authorization/liveness, and exercise cancellation for unavailable/replaced origins. They retain cancelled/unqualified state/context while failing Docker cleanup; retry against the original identity completes cleanup without converting cancellation to passed. They also cover six null/corrupt-context cases across cancel/direct cleanup with zero daemon commands, and missing/foreign persisted ownership with the local session deliberately left alive. Freshly fetched records and explicit persisted-value assertions fix the earlier stale-Ecto-struct premise ambiguity.

These are real **local relay/process/HTTP** observations using a synthetic model-health endpoint and synthetic Docker executable. They are not live-daemon compatibility or model-fitness evidence. The negative HTTP probe establishes no subsequent inference through that stopped listener; these added cases begin with an idle relay and do not prove immediate interruption of a previously executing upstream chat.
