# 06 proposal: package-owned export handoff

**Context.** The MCP contract exposes three read-only tools; `harnessforge_inspect_package` reports verified stored bytes, current eligibility, a blocker and `qualification: not_assessed_by_this_tool`, while directing the operator back to the Portal ([docs/mcp.md:58](../../../../mcp.md), [tools.ex:248](../../../../../lib/harness_forge/mcp/tools.ex)). MCP cannot export. Its structured errors separate unavailable packages from malformed calls ([protocol.ex:119](../../../../../lib/harness_forge/mcp/protocol.ex)). That clarity should carry through the Portal handoff.

**Observed gap.** Each package has its own export form ([portal_live.ex:1945](../../../../../lib/harness_forge_web/live/portal_live.ex)), yet success stores only a page-wide `export_path`, leaves an older error flash in place and reports no digest ([portal_live.ex:432](../../../../../lib/harness_forge_web/live/portal_live.ex)). Contract errors such as `export_conflict`, `unsafe_artifact_path` and `artifact_io_error` fall through a connector-specific generic message ([portal_live.ex:1162](../../../../../lib/harness_forge_web/live/portal_live.ex), [artifacts.ex:245](../../../../../lib/harness_forge/artifacts.ex)). This can make an occupied-directory retry look like an import failure. The native05 record also observed a stale direct-build alert beside a real export success ([verification.md](../../05/verification.md)).

**Decision.** Give the submitting package row one result area naming its exact digest and successful destination, or the export-specific recovery action. Keep its target draft on failure and focus its input; clear only superseded export feedback when that package retries. Map the fixed domain error codes to safe remedies: choose a fresh directory for conflict, correct an absolute contained path for unsafe target, check directory access/storage for I/O failure; approval or evidence refusal points to current Company/Evidence review. Do not echo arbitrary server error text. `Harnesses.export/2` continues to recheck eligibility and perform the actual write ([harnesses.ex:122](../../../../../lib/harness_forge/harnesses.ex)); the UI never treats an MCP eligibility observation as permission.

**Acceptance.** Positive: fresh export shows digest/path beside the correct row and an accessible status announcement. Negative: occupied destination retains input, shows fresh-directory remedy and does not overwrite existing bytes; stale eligibility reports review, not success. Edge: another package, lock/remount, purge or restore cannot display the old row's private path or result; unrelated actionable errors remain visible. Keyboard focus and next Tab reach the corrected input/action. Verify native 320/390 CSS widths and actual 200% zoom; this does not establish screen-reader speech or operator comprehension. Ownership: Portal LiveView/UI and focused web tests; no MCP, export-domain, approval, readiness or privacy-contract change.
