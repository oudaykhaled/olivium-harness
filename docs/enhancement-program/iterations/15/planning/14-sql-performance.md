# Bounded question retrieval: SQL and performance proposal

**Problem and evidence.** The public long question in iteration 14 selected three passages and omitted policy; a focused question selected four including policy. In the curated `Company.Retrieval` snapshot, `tokens/1` keeps the first four and last four content terms after eight, so a middle term can be discarded before FTS5 runs. That mechanism is concrete; its contribution relative to ranking and packing has not been isolated. This is one observed miss, not a corpus recall rate.

**Proposed decision for iteration 15.** Use the existing SQLite FTS5 `Company.Retrieval` path to compare three bounded plans on independently authored public development cases before selecting a change: current eight-term truncation; one capped full-question OR expression; and capped overlapping term windows merged into the current lanes. Keep a fourth packing-only diagnostic to locate loss after candidate retrieval. Prefer the smallest plan that retains indispensable policy and later exception/failure evidence without unacceptable irrelevant inclusion or latency. Do not automatically expand the five-search, 100-candidate, 24-passage, 32 KiB evidence and 49 KiB prompt limits. Any proposed cap change needs an explicit measured cost and authority review. The existing per-query 30-second timeout is a failure bound, not a performance target.

**SQL/performance seam.** The existing query materializes authorised active corpus passages, joins `passage_search`, sorts by `bm25`, and limits each lane to 20. For each candidate, record the exact query-plan version, lane expression/term count, FTS result identities, candidate and packed identities, omitted bytes/count, and elapsed search/pack time. On declared public corpus sizes, inspect SQLite `EXPLAIN QUERY PLAN` and measure p50/p95 latency, query count, DB size and process memory under one and several concurrent browser requests; report hardware and warm/cold conditions. Investigate materialized-scope and sort cost before changing indexes or adding an engine. Retrieval remains scoped and generation-checked before search and publication; checked passage bytes and versioned origins remain prerequisites to synthesis.

**Connected acceptance.** Reordered middle-policy, exception/failure, distractor and no-answer questions show where each critical source enters or leaves FTS candidates, packing and reviewed context. Record critical and contrary misses, irrelevant inclusion and abstention; all-abstention fails answerable cases. Through the browser, a reviewer corrects applicability, goal rationale and uncertainty, rejects an unsupported canary, approves the exact successor claim and separately approves the exact plan; actual exported target bytes contain the corrected scoped rule and exclude rejected/superseded guidance. Existing `AnalysisV2`, `OriginV2`, decisions, compiler/export and evaluations supply the seams. A representative model task remains `BLOCKED` if no authorised configured model exists; static integrity alone establishes no task benefit.

**Trade-off.** Full-question OR is one search but may dilute `bm25`; windows preserve local terms but add queries and fusion complexity. Packing-only changes cannot recover a term absent from FTS candidates. Preserve Graphiti 0.31.2/native Jev as the existing optional path, with no new graph/RAG engine. Physical 100k/million-file throughput and real company quality require separate measured evidence.
