# 09 proposal: source-purge impact preview

**User benefit.** Before removing a source, show its downstream removal scope and require confirmation of that scope. The Privacy form accepts a source ID without showing affected claims, plans, packages or runs (`lib/harness_forge_web/live/portal_live.ex:2445`). Purge already computes whole claim families, company plans/artifacts and evaluations (`lib/harness_forge/privacy/purge.ex:128`, `lib/harness_forge/privacy/company.ex:7`). An owner can distinguish a small correction from withdrawing a reviewed package.

**Contract.** Add a read-only, workspace-scoped `Privacy.preview_source_purge/1` using the existing purge dependency planner and returning bounded counts plus a digest of canonical affected IDs, no evidence bodies or credentials. Show those counts, source identity, and digest beside confirmation. On submit, recheck the same plan inside the existing serialized purge transaction; a changed digest returns `:stale_purge_preview` before connection revocation, operation insertion or deletion. The operator refreshes and confirms the new scope. Preserve exact-ID confirmation, durable retry/reconcile, sibling cache resets and current physical-erasure/external-copy language (`lib/harness_forge/privacy.ex:3`, `lib/harness_forge/privacy/purge.ex:62`). A previously prepared retry follows its recorded plan, with its existing recovery semantics, rather than accepting a fresh preview.

**Acceptance.** Positive: a source with a dependent approved claim, company plan, package and run shows their bounded counts; confirming its current digest completes purge and leaves an unrelated project/artifact. Negative: change a dependency after preview; submission returns stale with zero new privacy operation, revocation, or deletion. Edge: two identical previews have the same digest; invalid/foreign source returns no dependency details; an incomplete purge stays fenced and recoverable. `test/harness_forge/privacy_test.exs:107` and `test/harness_forge/company_privacy_test.exs:37` supply existing cascade fixtures; add focused domain and LiveView checks. A stale submission with any write falsifies the contract.

**Choice and limits.** Estimated 1–2 implementation days for planner extraction and atomic admission. An informational preview is cheaper but can mislead after concurrent edits. Goal coverage improves plan admission; MCP-client revocation isolates machine clients (`lib/harness_forge/mcp/auth.ex:51`). This makes deletion consequences reviewable. Preserve MCP's response-send purge fence (`lib/harness_forge_web/plugs/mcp.ex:2`). Operating-log confidentiality remains unverified: development debug disclosure is a source prediction, not an observed leak (`config/dev.exs:22`, `config/runtime.exs:38`).
