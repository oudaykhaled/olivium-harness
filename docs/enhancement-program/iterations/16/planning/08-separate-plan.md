# Lens 08 — separate exact plan decision and next build action

**User and job.** A company owner who approved a sourced recommendation must decide whether a package plan carries that claim and saved goal into a build. Success is identifying both revisions, material choices and the next action before deciding. Mistaking approval for build or attributing predecessor approval to a successor falsifies the hypothesis.

**Observed problem.** Iteration 15 approved corrected claim `a762ce…`, separately approved plan `2c2f02…`, and exported eight files; task assessment remained BLOCKED ([handoff](../../15/handoff-to-16.md); [review capture](../../../../../tmp/enhancement-program/15/browser-evidence/20-separate-exact-plan-review.txt)). Review repeats a long rule while the plan form holds project, repositories, goal, presets, target, limits and milestones. “Compare package versions” appears only after two artifacts exist ([Plan snapshot](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge_web/components/company/plan.ex), lines 424–462). A reviewer lacks a quick successor comparison before decision. This is a review-cost hypothesis, not observed novice failure.

**Options and decision.** A: reuse `Company.Plan`’s list/review and `Company.Guide`’s next action. Show a read-only comparison with the direct predecessor: changed claim revisions, goals, repositories, presets, target, limits and milestones. Keep full text in disclosure, plan hash beside its decision, and the next action visible. B: add a general plan-diff service and screen. It supports arbitrary versions but adds navigation and a new contract without demand evidence. Prefer A as the smallest coherent WEB slice; retain package diff after build.

**Acceptance and Root verification.** Given an approved claim and proposed plan, when review opens, then claim revision, goal and plan hash are identified, and only the plan control approves the plan. Given a successor with a changed claim or target, when compared with its predecessor, then changed fields are named and predecessor approval is not inherited. Given stale, rejected or superseded context, when returning, then Build is disabled, reason and next action appear, and no dispatch occurs. Given a current approved plan, when preflight passes, then Build is next while export, static PASS and task outcome remain distinct. Root can check a public synthetic WEB journey and keyboard/screen-reader semantics. A five-operator study should test whether four identify both approvals and the next action unaided.

**Authority and limits.** `Company.decide_plan/2` checks the hash; `build_inputs/1` rechecks approval and snapshot ([Company snapshot](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge/company.ex), lines 165–249, 445–460). Compare saved records without granting authority from labels. Use semantic headings, labelled changes, visible focus and announced stale status. No schema/provider/graph change. Decision clarity cannot prove corpus completeness, applicability, model quality or task benefit. Own-MCP company-context debt remains.
