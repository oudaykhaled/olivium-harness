# Iteration 16 planning: permissions and currentness at the review handoff

The WEB journey has a trust gap between “I can inspect this evidence” and “this evidence may be sent, approved, or exported now.” The corpus page names the connection, project, goal, available captures, and unknown discovery/model coverage ([corpus UI, lines 247–305](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge_web/components/company/corpus_review.ex)). Its live pages are not corpus snapshots. The four-source demonstration reached a corrected claim, separate plan approval, eight exports, and static PASS, while task evaluation stayed BLOCKED for no selected model ([15 handoff](../../15/handoff-to-16.md); [result](../../../../../tmp/enhancement-program/15/iteration-result.json)). A user can mistake inspection readiness or an old approval for present permission to dispatch.

Authority is already server-owned: `OriginV2.manifest/2` rechecks corpus generations, saved goal, retrieval, stage pin, and source revisions ([origin, lines 224–275 and 329–381](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge/evidence/origin_v2.ex)); consent is tied to a reviewed immutable manifest and current source pins ([stage authority, lines 77–196 and 508–541](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge/models/stage_authority.ex)). Dispatch rechecks current operation, consent, credential and attempt binding; cancellation durably advances an epoch before worker delivery ([stage authority, lines 620–671 and 813–827](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge/models/stage_authority.ex); [stage control, lines 71–126 and 264–304](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge/models/stage_control.ex)). The UI must report these results, never infer access from a cached card.

Two bounded reuse options: **A**, add a compact authority summary at the existing review/dispatch seam, populated from current server decisions and linking to exact source, consent, cost and cancellation details. It gives the reviewer one next action with modest UI work, but the summary must refresh after any scope or source change. **B**, expand the existing corpus scope/details and model settings panels. It reuses more markup, but disperses the decision across screens and makes stale state easier to overlook. Recommend A as the smallest coherent slice; retain existing detailed panels as drill-down.

Acceptance is falsifiable: before synthesis, show selected corpus/goal and exact manifest identity, current versus unavailable captures, provider/model/endpoint, source-scoped consent, budget ceiling or unavailable estimate, and a distinct **no dispatch yet** state. A changed/revoked source, goal, stage pin, or consent yields a blocking stale state and an actionable refresh path; no stale approve/dispatch control stays enabled. During an attempt, show reserved/dispatched/cancelled/ambiguous status and recorded usage without claiming cancellation can retract an already sent request. Claim approval and separate plan approval remain visibly independent; static PASS never implies task success. Root can verify with a public synthetic WEB journey that changes one source after preparation, revokes consent, cancels a reserved attempt, and checks screen state plus server rejection and zero new dispatch; then verify the unchanged approved export path.

Use semantic status text, focus on the invalidated decision, keyboard-operable detail disclosure and labels that name the affected action. This is a UI proposal, not a new consent or authentication contract. External source freshness, semantic sufficiency, real-model cost and representative task benefit remain unproved.
