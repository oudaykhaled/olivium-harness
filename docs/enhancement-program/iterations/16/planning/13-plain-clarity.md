# Plain language and compact hierarchy — independent UI16 proposal

The current Company page offers a corpus-first journey, but its adjacent saved-workflow guide can make manual source assignment look required. The entry says “Choose a corpus and goal,” while the guide counts “assigned current captured sources” and displays a full prerequisite list ([Company panel, lines 1321–1342](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge_web/components/company_panel.ex); [guide, lines 281–370](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge_web/components/company/guide.ex)). That is a plausible reading problem, not a measured novice failure. Iteration15 did reach four captured sources with zero manual assignments, exact corrected claim approval, separate plan approval and eight exports; static PASS remained distinct from task BLOCKED ([handoff](../../15/handoff-to-16.md); [accepted evidence](../../../../../tmp/enhancement-program/15/accepted-evidence01.json)). The usability retro records a real spaced-name rejection with generic advice before a slug succeeded. The plan form has a slug-shaped placeholder but no explicit name rule ([plan, lines 93–166](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge_web/components/company/plan.ex)).

Option A: reuse `Company.Guide`’s computed next action and existing disclosures to put one short, specific step below the corpus action. Label the old assigned-source count as belonging to the manual path, move its checklist behind an explicit “Manual setup” disclosure, and keep status and next action visible without opening it. This is small and preserves the present server-owned eligibility checks; it risks hiding details some expert users rely on. Option B: add a compact journey summary across evidence, claim, plan and task states. It better supports orientation after a user leaves Company, but would join several states and increase stale-summary risk. Neither option should translate lexical counts into confidence or company coverage.

I recommend A, with a narrow plan-name recovery improvement: state the accepted format beside the input and identify that field on a rejected submission while retaining the other selections. Keep one accessible “View exact details” disclosure for full claim text, source context, identifiers and revision hashes in plan review; place the short reason and separate claim/plan decision states first. The exact revision must remain inspectable at the moment of approval. Use native headings, labelled buttons, `aria-expanded`/`aria-controls`, visible focus and a live error linked to the name input.

Acceptance is falsifiable: with a valid corpus and saved goal but zero manual assignments, the primary action opens corpus review and the guide never says assignment is a prerequisite; with an invalid spaced name, the field-specific message preserves project, claim and goal choices; keyboard-only users can expose the full pins and reach both distinct exact approvals. After a scope or revision change, stale actions are withheld and the current reason is shown. Root should verify these paths through the WEB interface, including a 390×844 view and a real invalid-submit recovery, then inspect exported bytes and the honest static-PASS/task-BLOCKED labels. This slice improves comprehension; it does not qualify corpus completeness, policy applicability, real-model quality, representative-task benefit or own-MCP context parity.
