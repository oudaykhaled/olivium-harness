# Exact claim revision and decision visibility — independent WEB planning lens 07

**Observed problem.** Iteration 15 proved a connected path: SCRIPTED synthesis needed human correction, canary rejection, exact successor approval, separate plan approval, and eight actual exports. Static integrity passed while task evaluation remained `BLOCKED/model_not_selected` ([handoff](../../15/handoff-to-16.md), lines 23–27; [product retro](../../15/retro/product.md), lines 3–7). The WEB claim screen saves edits as a separate proposed revision, blocks Evidence navigation for unsaved edits, and shows original citations. Yet its saved list displays status plus “has successor,” while the full claim hash and pinned inputs sit inside collapsed attribution ([curated analysis component](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge_web/components/company/analysis.ex), lines 324–416, 529–545). This could obscure which revision the next decision concerns; no wrong approval was observed.

**Bounded options.** Option A reuses the Company saved list, edit form, report and Evidence navigation: place a compact “decision target” summary beside the action with status, exact revision identifier, predecessor/successor relationship, saved resolution and access to pinned provenance. Its cost is more text in a dense review. Option B uses the Evidence decision screen for revision comparison; it gives stronger decision context but requires a cross-screen comparison. I recommend A with full pins in disclosure, so the edited successor is identifiable before navigation.

**Smallest slice.** On opening a claim, distinguish “original proposed,” “edited successor awaiting decision,” “approved,” “rejected,” and “superseded” using existing data. State that edits create an unapproved successor and only its exact current revision can be decided. Keep original report, uncertainty, excerpts, goal and source pins accessible without implying semantic coverage. The server requires the expected hash, rejects superseded revisions, and gates approval on required human resolution ([curated decisions](../../../../../tmp/enhancement-program/16/source-safe/lib/harness_forge/decisions.ex), lines 7–55); the UI should reflect those outcomes.

**Falsifiable acceptance and Root verification.** With public synthetic data, Root should save a correction, reopen predecessor and successor, and verify the predecessor is superseded while the successor is unapproved with its own hash and retained origin. A stale or superseded decision must show server rejection and a current-revision recovery path; a rejected canary must stay out of export. Keyboard and screen-reader review should announce selected revision, status and next action without color or truncated hashes. Compare the approved hash to fresh exported provenance, then report static PASS and task BLOCKED separately. Real-model quality, company completeness, novice success and task benefit remain unproved.
