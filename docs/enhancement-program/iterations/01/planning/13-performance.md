# Iteration 01 proposal: bounded company reads for MCP

**Priority: high if company catalogue reads are exposed through MCP; otherwise medium.** A coding client should find a reusable capability and inspect a plan without receiving the whole catalogue or making the local portal stall. This is a proposed first-party MCP benefit, not existing behavior: the router currently has only login/session and the portal ([router.ex:18–32](../../../../../lib/harness_forge_web/router.ex#L18-L32)).

## Evidence and scope

`Company.search_capabilities/1` loads every repository DTO, joins and lowercases every capability string, then returns every match ([company.ex:46–62](../../../../../lib/harness_forge/company.ex#L46-L62)). The underlying list query materializes every payload ([company.ex:173–174](../../../../../lib/harness_forge/company.ex#L173-L174)). The repository and project counts are capped at 100 each, but each repository may contain three arrays of up to 100 strings of 4096 characters ([company.ex:198–202](../../../../../lib/harness_forge/company.ex#L198-L202), [validation.ex:155–162](../../../../../lib/harness_forge/company/validation.ex#L155-L162)). `list_plans/0` has no result limit and each plan includes a snapshot ([company.ex:103–107](../../../../../lib/harness_forge/company.ex#L103-L107), [records.ex:37–49](../../../../../lib/harness_forge/company/records.ex#L37-L49)). The portal itself reloads all four company collections ([company_panel.ex:357–375](../../../../../lib/harness_forge_web/components/company_panel.ex#L357-L375)); it is a separate performance concern.

## Bounded change

For an initial **read-only** MCP surface, implement dedicated workspace-scoped list/search queries rather than wrapping the existing whole-list APIs. Use stable `(id)` keyset pagination for repositories and projects and `(inserted_at, id)` for plans, with default 10 and maximum 20 items. Fetch 21 rows to determine `next_cursor`; validate cursor format and bind it to workspace, tool, query and sort order. Search only capability values, preserve the existing all-token lexical semantics and deterministic ordering, and return at most one page. Apply the page limit in SQL before decoding full payloads. Return explicit summary fields (`id`, identity/name, concise capability matches, `content_hash` or plan revision/status); fetch one selected record through a separate bounded detail tool if that tool is included in the chosen MCP scope. Never serialize full plan snapshots or repository examples in list results. Keep the frozen `Company` API and portal behavior intact ([company-builder-contract.md:19–59](../../../../../docs/company-builder-contract.md#L19-L59)).

At the HTTP boundary, reject bodies over 64 KiB before decode, enforce a 256-character search query and at most 20 tokens, impose a 64 KiB encoded response ceiling and a 2-second read deadline. Return a stable, content-free resource-limit error when a result exceeds the ceiling; do not truncate valid JSON or echo input. The shared `Contracts.decode_json/1` already detects duplicate keys and nesting but allows 2 MB, so the smaller MCP byte cap must be enforced separately ([contracts.ex:14–41](../../../../../lib/harness_forge/contracts.ex#L14-L41)). No background indexing or FTS migration is justified by the present 100-repository cap; measure SQL scan time first. If it exceeds the budget, add a workspace-scoped capability index maintained transactionally with catalogue mutations and purge, with no unscoped cache.

## Acceptance and negative cases

- With synthetic records at the 100-repository/100-project caps and 1,000 immutable plans, every list/search page returns at most 20 summaries, stays under 64 KiB, and traverses all pages once in stable order without cross-workspace rows. A selected detail is fetched only by ID.
- On a local release build with warm SQLite and eight concurrent readers, record p50/p95 latency and peak per-request BEAM process memory; target p95 below 250 ms and below 8 MiB additional process memory for the bounded summaries. If these targets fail, report the measured limit rather than claim scale readiness.
- Reject oversized body, overlong query, invalid/foreign cursor, duplicate JSON keys, unknown fields, and response overflow with bounded errors. Empty search returns no rows; no partial or duplicated page appears after a catalogue update (restart paging when the cursor revision is stale).
- Verify read calls make no writes, model calls, approval changes or source-body disclosure. Synthetic HTTP tests demonstrate local protocol behavior only; live client compatibility requires a separate client run.
