# Iteration 01 proposal: MCP transport inside the workspace owner

**Priority: high.** An MCP client should inspect a running company's reviewed catalogue and plan through the same local application the operator uses. Choose **Streamable HTTP at `/mcp` in the existing Phoenix process** for the first delivery, pinned to the 2025-11-25 protocol revision. Defer a stdio adapter. The [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) defines both transports; HTTP handles multiple clients from one server process, while stdio normally launches a child process.

## Why this fits the checkout

`Workspaces` acquires an exclusive SQLite ownership transaction at boot and rejects a second process with `:workspace_in_use` ([workspaces.ex](../../../../../lib/harness_forge/workspaces.ex#L40-L65)). The current launcher starts a new BEAM instance for offline commands, and `serve` starts the portal ([bin/harnessforge](../../../../../bin/harnessforge#L6-L22)); the quickstart explicitly says to stop the portal before CLI commands ([quickstart.md](../../../../../docs/quickstart.md#L79-L95)). A standalone stdio server using the application API would therefore fail while the portal is open. A stdio-to-HTTP bridge could be added later without opening a second workspace, but it brings a second transport and token handoff to test.

The existing application starts `Workspaces`, `Repo`, the startup recovery barrier, and the endpoint in order ([application.ex](../../../../../lib/harness_forge/application.ex#L9-L20)). The endpoint already binds `127.0.0.1` ([runtime.exs](../../../../../config/runtime.exs#L30-L34)); the router currently serves only login/session and the authenticated LiveView ([router.ex](../../../../../lib/harness_forge_web/router.ex#L18-L32)). The MCP route needs machine authentication instead of the browser cookie redirect path. Reuse the workspace access token for a constant-time bearer check or introduce a dedicated generated MCP token with an explicit rotation path; keep token bytes out of URLs, logs, responses, package archives, and test evidence. The current origin guard rejects POSTs lacking both Origin and Referer ([local_origin.ex](../../../../../lib/harness_forge_web/plugs/local_origin.ex#L7-L29)); permit that case only for authenticated `/mcp` clients while retaining exact Host checks and rejection of invalid supplied Origins. The [MCP specification requires Origin validation for HTTP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

## Bounded first implementation

Add one authenticated `/mcp` endpoint and a small, transport-independent dispatcher. Implement `initialize`, `notifications/initialized`, `ping`, `tools/list`, and `tools/call` for **read-only** company profile, repositories, projects, plans, and capability search, mapped to existing `Company` functions ([company-builder-contract.md](../../../../../docs/company-builder-contract.md#L19-L44)). Use string-keyed bounded arguments, opaque workspace-scoped IDs, safe errors, response limits and request timeouts. Return the current reviewed status and citations as data; never turn plan text or imported evidence into instructions. Do not expose `decide`, `build`, `export`, model calls, sync, purge, release, or arbitrary CLI execution in this iteration. Keep `GET /mcp` as a documented 405 when SSE is unsupported and use JSON POST responses; follow HTTP 202 for accepted notifications, protocol-version and content-type checks, and the initialization sequence in the [transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) and [lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) specifications. If the target client needs sessions or SSE, implement and verify them explicitly before claiming compatibility.

## Acceptance and negative checks

1. With the portal owning a disposable synthetic workspace, a real MCP client completes initialization, lists the advertised tools and reads that workspace's company data over loopback. The portal remains usable throughout; a second offline CLI process still fails ownership cleanly.
2. A packaged native release exposes the same endpoint after `serve`, using a fresh synthetic workspace; verify the archive's launcher and actual client exchange, since the current package smoke exercises CLI only ([packaging/README.md](../../../../../packaging/README.md#L45-L53)).
3. Assert 401/403 for missing or wrong bearer token and foreign Host/Origin; prove the listener is loopback-only. Reject oversized/malformed JSON, unsupported method/version, unknown tool, foreign workspace ID and mutations. Check responses/logs contain no credential or unrelated company content.
4. Stop/restart the owner: stale client state cannot authorize a new workspace; no second owner is created. Verify deterministic errors and that failed or blocked operations create no decisions, artifacts, evaluations or releases.

Compatibility claim stays narrow: local HTTP MCP for the pinned revision and verified client(s), no stdio, legacy SSE, remote hosting, OAuth discovery, server-initiated streaming or cross-workspace tenancy. Native archives remain OS/architecture specific ([packaging/README.md](../../../../../packaging/README.md#L3-L7)).
