# Planner 16 — the company owner’s first MCP answer

**First enhancement: a read-only `harnessforge_company_status` MCP tool in the running local app.** The concrete user question is: “I have selected and reviewed this company plan; what can I do next, and what still prevents a complete harness?” The verified synthetic journey already creates, approves, builds, compares and exports two scoped packages. Static integrity passed, while managed Codex tasks were blocked and release approval was correctly refused ([verification, steps 3–6](../../../../company-builder-verification.md)). This is useful package construction, but not proof of a qualified company harness. The first MCP feature should make that distinction available to the assistant helping the owner, without letting the assistant make decisions.

## Bounded slice

Add one opt-in local MCP endpoint in the existing Phoenix process, with one tool accepting either `{}` or `{ "plan_id": UUID }`. An empty call returns a capped, deterministic list of plan IDs, names, exact revision hashes and statuses; a selected plan returns its current **next action** and a small ordered gate report: plan approved/current, package binding and export eligibility, task-evaluation availability, qualified evaluation, and release approval. Each gate has `state` (`ready`, `action_needed`, `blocked`, `unavailable`), a stable reason code and an existing portal destination. Return only opaque IDs, hashes, statuses and short fixed labels. Do not serialize plan payloads, snapshots, source/claim text, actor names or credentials. `Company.list_plans/0` and `get_plan/1` already expose plan status, while `build_inputs/1` rechecks exact approval and current scope ([company.ex:98–108](../../../../../lib/harness_forge/company.ex), [company.ex:138–170](../../../../../lib/harness_forge/company.ex)). Bound artifact eligibility must use the existing `Harnesses.eligible/1` check, not a new interpretation of approvals ([harnesses.ex:132–165](../../../../../lib/harness_forge/harnesses.ex)). Evaluation availability comes from `Evaluations.capabilities/0`; a static result must never satisfy the qualified task requirement in release validation ([evaluations.ex:15–34](../../../../../lib/harness_forge/evaluations.ex), [releases/validation.ex:8–49](../../../../../lib/harness_forge/releases/validation.ex)).

Use a single pinned MCP protocol revision, normal initialization and `tools/list`/`tools/call`, and verify with one real local client. The endpoint must have explicit operator opt-in, machine authentication, bounded requests and loopback/Origin enforcement. The current router has no MCP route ([router.ex:18–32](../../../../../lib/harness_forge_web/router.ex)); start it in the existing app because a second process competes for exclusive workspace ownership ([workspaces.ex:40–52](../../../../../lib/harness_forge/workspaces.ex)). The tool is observation only: no approval, build, export, connector sync, model call, release or code execution.

## Countable acceptance

1. A real MCP client connects to a disposable synthetic company workspace while the portal remains usable, discovers exactly this tool, lists plans, and reports the selected approved package’s exact revision and digest with export eligibility. A proposed plan reports `action_needed: plan_approval`; a stale or revoked plan reports its blocker without claiming it can build.
2. The same call reports static integrity as insufficient and managed task execution as `unavailable` when the runtime is unavailable; release remains blocked. No fabricated green “complete” state. A currently valid predecessor remains eligible after a successor is created.
3. Missing/wrong credentials, foreign Host/Origin, malformed or oversized JSON, unknown arguments and foreign IDs fail safely. Responses and logs contain no source bodies or secrets. Calls cause no database, file or remote mutations. Run focused domain/protocol tests, the canonical `mix test`, and a real-client local smoke; retain exact logs and limits.

## Next priorities across the program

After this first answer: (1) make pre-plan evidence and project-scope gaps actionable in the portal; (2) qualify an isolated local model route with protected task grading and explicit blocked outcomes; (3) validate selected live connector scopes only when authorized credentials exist; (4) add goal-origin rule basis and conflict decisions; (5) design portable plan provenance with a versioned compatibility contract. Later UI iterations should shorten the setup path and explain each gate in context. Track real company task success and operator time as pilot evidence, not synthetic fixture claims. The 50-iteration ledger should prioritize observed blockers; it should not count plans or documentation alone as improvements ([program contract](../../../PROGRAM.md)).
