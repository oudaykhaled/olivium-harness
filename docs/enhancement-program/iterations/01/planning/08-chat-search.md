# Planner 08 — make captured evidence discoverable in chat

**Priority: P1.** A user who asks “What sources have I captured?” should get a useful, bounded source inventory before choosing search terms. Today broad words are removed; an empty token set causes `Evidence.list_sources()` to feed up to 12 excerpts into chat, in title order, without an explicit inventory or total count ([retrieval.ex:8–20, 45–53, 107–136](../../../../../lib/harness_forge/chat/retrieval.ex)). `Chat.ask/2` treats non-live questions as captured-evidence lookup, and a miss only says to connect or sync ([chat.ex:25–57, 140–153](../../../../../lib/harness_forge/chat.ex)). The panel shows per-connection counts, but no question-to-source discovery path ([chat_panel.ex:133–160](../../../../../lib/harness_forge_web/components/chat_panel.ex)). This matters when a company starts with unfamiliar GitHub, Jira, Slack, Confluence, GitHub Projects, or local captures.

## Minimal change

Add one explicit **captured-source discovery** intent for a small set of clear questions (“what captured sources are available?”, “show captured sources”). In assistant and evidence modes, return a structured, local-only reply: total eligible source count; count by existing provider; first bounded set of source title, provider, capture time, and safe source URL; and an honest omitted count. Use `Evidence.list_sources/0` plus the existing `Snapshot.eligible?/1` and active-connection filter, with stable ordering. Render links only through the panel's existing HTTPS validation. Point users to the existing Evidence tab for the full list, or the explicit sync control when empty. Avoid source bodies and model calls for this metadata intent.

Keep ordinary content questions on current FTS/retrieval. Do not broaden cloud consent: model mode still uses the exact consented IDs ([chat.ex:121–133](../../../../../lib/harness_forge/chat.ex); [retrieval.ex:31–43](../../../../../lib/harness_forge/chat/retrieval.ex)). Preserve current reply invalidation when a source, connection, workspace, or revision changes ([chat.ex:66–116](../../../../../lib/harness_forge/chat.ex); [snapshot.ex:43–108](../../../../../lib/harness_forge/chat/snapshot.ex)). This is a reusable read-only discovery operation for a future HarnessForge MCP server; no MCP transport exists in the current `lib/` tree, so exposing one now would add authentication and protocol scope beyond this user benefit. Existing live account listings remain separate and explicitly labeled; the finite live intents already cover those ([intent.ex:4–58](../../../../../lib/harness_forge/chat/intent.ex)).

## Acceptance and negative checks

1. With synthetic captures from all six providers, “show captured sources” returns correct provider counts and bounded, stable source rows through `Chat.ask/2` and the authenticated LiveView. If results exceed the cap, it shows the omitted count and a route to the full Evidence list. No model request or connector API request occurs.
2. Revoked, purged, foreign-workspace, inactive-connection, and stale-revision sources never appear. A previously displayed reply is cleared on withdrawal. Empty workspaces show zero with a useful next action, not an invented result.
3. A normal “What are the testing rules?” question still returns exact byte citations; live “list my GitHub repositories” still uses verified account access. Cloud model consent and source scope remain unchanged.
4. Provider titles and URLs are escaped/sanitized, input remains bounded, and prompt-like source text cannot trigger sync, model inference, claim approval, or tool execution. Tests should use synthetic sources and assert actual request boundaries, not claim live connector or MCP compatibility.
