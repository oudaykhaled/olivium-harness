# UX investigation: setup discovery and company workflow

**Recommendation for functionality iteration 01:** make a first-party, read-only MCP discovery endpoint useful to an operator who is building a company harness. Expose a bounded `workspace_status` tool that reports the existing workspace counts and explicit readiness states, plus a `company_next_steps` tool that returns the next actionable step and the portal destination. Use the same application services as the portal; return no source bodies, secrets, credential references, or inferred approvals. A thin Company panel companion should link to MCP setup instructions and display the same next-step wording. This is useful even when no model or managed runtime is available.

## Why this is the gap

The portal has nine main tabs and opens on Evidence, while Company appears second in navigation ([portal_live.ex:5–18](../../../../../lib/harness_forge_web/live/portal_live.ex#L5-L18), [portal_live.ex:902–917](../../../../../lib/harness_forge_web/live/portal_live.ex#L902-L917)). Its global workflow says “Connect sources → Review evidence → Set goals → Build & evaluate”; it omits the required company profile, service catalogue, project, exact plan proposal, and plan decision ([portal_live.ex:987–1003](../../../../../lib/harness_forge_web/live/portal_live.ex#L987-L1003)). The Company component contains those steps and already links out to Connections, Goals, and Evidence ([catalog.ex:26–95](../../../../../lib/harness_forge_web/components/company/catalog.ex#L26-L95), [plan.ex:45–71](../../../../../lib/harness_forge_web/components/company/plan.ex#L45-L71)). The builder describes separate build, export, evaluation, and release steps ([company_panel.ex:244–250](../../../../../lib/harness_forge_web/components/company_panel.ex#L244-L250)). Current documentation covers native Codex/Claude package output, but the portal navigation has no HarnessForge MCP entry ([portal_live.ex:902–929](../../../../../lib/harness_forge_web/live/portal_live.ex#L902-L929)).

## Minimal user journey

1. A new local operator opens Company and sees one plain next action: capture a source, add profile/catalogue/project context, review claims, propose and approve a plan, or build, whichever is first unmet. The action navigates to the existing panel or tab.
2. The operator opens a compact “Use HarnessForge from an MCP client” disclosure. It shows the supported local transport/start command, required operator authentication, an example client configuration with placeholders, and a quick discovery check. No raw token is displayed or copied.
3. A client lists the server’s tools and calls `workspace_status` or `company_next_steps`. Each response names its workspace, states what is available, and gives the same next action visible in Company. Missing local server, authentication, or storage produces a distinct unavailable/error state. The client cannot create, approve, build, export, or execute through these discovery tools.

## Acceptance for the selected functional slice

- One documented local MCP entry point starts without a cloud account or paid call; standard tool discovery finds both tools. Invalid/unauthenticated requests fail closed, and responses are bounded, string-keyed data.
- Empty synthetic workspace returns a setup action. After saving company context and captured evidence, the next action advances based on persisted state. Proposed claims never appear approved; a proposed plan never appears build-ready. Stale or revoked inputs return an action to review the exact current revision.
- The Company companion mirrors the server’s next action and provides a working destination using existing navigation. It distinguishes connected account access from captured evidence: the Company introduction already says access does not import or fill company facts ([company_panel.ex:525–550](../../../../../lib/harness_forge_web/components/company_panel.ex#L525-L550)).
- Local automated tests cover discovery, authorization, bounded response shape, and state transitions. A real local client probe records the actual handshake and tool call; synthetic fixtures do not establish external-client compatibility.

**Next UI iteration:** make Company the visual home of a concise progress checklist and replace the inaccurate global four-step strip with state-aware milestones. Keep the existing detailed forms below it, and show each unavailable dependency beside its action. The current mobile stylesheet hides the workflow strip entirely, so this checklist should remain visible at narrow widths ([app.css:122](../../../../../assets/css/app.css#L122)).
