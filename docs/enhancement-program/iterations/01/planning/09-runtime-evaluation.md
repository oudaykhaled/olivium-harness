# Runtime evaluation: explain whether a package can be tested

**Priority: high.** A company builder can build a package, but cannot tell whether selecting “Isolated model-backed tasks” will run until an evaluation record has already been created. The evaluation screen offers all three checks for every artifact and shows only the final reason and cleanup state, although task availability depends on the selected local model, Ollama, Docker and three pinned images ([portal_live.ex:1548–1617](../../../../../lib/harness_forge_web/live/portal_live.ex#L1548-L1617), [coding.ex:107–124](../../../../../lib/harness_forge/execution/coding.ex#L107-L124)). Codex and Claude Code have preview renderers only; their task and smoke runs are blocked by design ([registry.ex:15–28](../../../../../lib/harness_forge/adapters/registry.ex#L15-L28), [evaluations.ex:244–255](../../../../../lib/harness_forge/evaluations.ex#L244-L255)).

**First slice.** Add a read-only `Evaluations.preflight(artifact_digest, kind)` returning a string-keyed report with `status` (`ready`, `blocked`, `unavailable`), ordered prerequisite checks, a stable reason code, and one next action for each failure. Reuse current artifact lookup, eligibility and compiler verification from `run/2` ([evaluations.ex:112–129](../../../../../lib/harness_forge/evaluations.ex#L112-L129)). For OpenCode task checks, reuse `Coding.availability/0` and compare the artifact runtime version with `Docker.version/0` before presenting `ready`; for smoke, use the existing Docker probe. For unsupported backends, report `runtime_backend_unavailable` immediately. Show the report beside the selected artifact and check, refresh it after selection or local model configuration changes, and retain the current evaluation action. This prevents predictable blocked attempts and gives operators a precise setup path. “Ready” means prerequisites are present at the instant checked, never that a run will pass or qualify.

Keep the existing run and release gates authoritative. A task qualifies only after observed execution with a metered local route, protected grading, verified cleanup and unchanged model configuration ([coding.ex:127–193](../../../../../lib/harness_forge/execution/coding.ex#L127-L193), [coding.ex:196–229](../../../../../lib/harness_forge/execution/coding.ex#L196-L229)). Static and offline smoke results cannot qualify release ([evaluations.ex:1–7](../../../../../lib/harness_forge/evaluations.ex#L1-L7), [releases/validation.ex:8–49](../../../../../lib/harness_forge/releases/validation.ex#L8-L49)). No new runtime command, source mount, model call, persisted approval or fallback is needed for this slice.

**Acceptance and negative cases.** With a synthetic eligible OpenCode package and no model selection, the screen names `model_not_selected` and the model setup action before queuing. A wrong runtime version reports the version mismatch; missing Docker or pinned image reports unavailability. Codex and Claude Code report unavailable managed execution while static integrity stays selectable. With prerequisites present, preflight says `ready`, yet a later failed run remains failed and cannot approve a release. Revoked evidence, invalid package integrity or a changed model configuration must be rechecked by `run/2`; a stale preflight cannot grant authority. Test reason mapping and the screen state change without paid calls; a fixture-backed task test does not count as live model qualification.

**Next gap.** The only task suite is two fixed synthetic Go exercises ([task_suite.ex:5–6](../../../../../lib/harness_forge/evaluation/task_suite.ex#L5-L6)). A passing run proves a narrow runtime path, not that a company’s repository, policies or milestones work. Company-specific, evaluator-owned suites with trusted fixtures and protected expectations are a later design and isolation project; broadening managed execution to Codex or Claude Code is separate. Preserve the visible gap in the release story rather than inferring company fitness from this preflight.
