# Independent retrospective 04 — Trust, security and privacy

HarnessForge was helpful and reliable for preparing a company harness locally: it preserves reviewed revisions, produces reproducible packages, and now lets an MCP client inspect readiness without granting build or approval authority. A complete operational company harness remains unproven. This verdict follows independent reading of code and accepted evidence; I read no peer retrospective and ran no tests or product processes.

The [accepted manifest](../../../../../tmp/enhancement-program/01/accepted-evidence.json) matches all 19 recorded source/evidence hashes. The [regression report](../review/regression-validation.md) records 388 passes, zero failures and 15 unchanged Docker skips; coverage is unmeasured and two baseline Dialyzer findings remain. The [native client report](../review/client-validation.md) establishes 44 passing checks with official SDK 1.29.0, protocol 2025-11-25, synthetic data and a native candidate. Thirty database tables and ten artifact files remained unchanged. This supports the tested transport and metadata journey; it supplies no real-model or broad-client qualification.

The security boundary is convincing within that scope. [Auth](../../../../../lib/harness_forge/mcp/auth.ex) checks the actual loopback peer, Host/Origin and one bounded independent credential. [Transport](../../../../../lib/harness_forge_web/plugs/mcp.ex) reauthenticates inside the purge fence and holds it through encoding and response send. [Tools](../../../../../lib/harness_forge/mcp/tools.ex) expose fixed projections and distinguish integrity, eligibility and unassessed qualification. [Company admission](../../../../../lib/harness_forge/company.ex) rechecks exact approvals and current inputs. [Restore quarantine](../../../../../lib/harness_forge/privacy/snapshot.ex) withdraws decisions, connections and model authority. The [security review](../review/security-review.md) has no open actionable finding; the exceptional-response no-store defect was corrected with regression evidence. Privacy documentation accurately limits purge to owned content, leaves received/exported copies outside its reach, and identifies unencrypted backups.

My ranked missing capabilities and verification are:

1. **A qualified company workflow.** SDK success cannot establish whether useful guidance survives a real assistant, selected live connector scopes and isolated execution. Acceptance: one bounded company scenario records exact source revisions, approved rules, package digest, actual client/model/runtime versions, protected objective results, cancellation/cleanup and release admission. Unavailable integration stages must remain visibly blocked. Existing Docker skips and the [compiler’s preview/managed distinction](../../../../../lib/harness_forge/compiler.ex) remain explicit until corresponding execution evidence exists.

2. **Portable approval provenance.** Package bindings prove local workspace relationships; tools explicitly return portable approval verification as unavailable. `Company.decide_plan/2` records a supplied actor label, not independently authenticated reviewer identity. Acceptance: a versioned approval receipt binds the package digest, exact plan/rule/source identities and reviewer identity to verifiable trust material. An independent verifier rejects altered or untrusted receipts and distinguishes historical approval from current eligibility; offline revocation status remains unknown. Restoring a backup must still require fresh authority. Goal-to-rule traceability also needs attention: [generation](../../../../../lib/harness_forge/harnesses.ex) currently emits `goal_id: nil`, while explicit conflict resolution remains absent.

3. **Client-specific machine access lifecycle.** The bearer persists independently of browser logout and authorizes all three tools in the active workspace. There is no per-client scope, expiry or selective revocation in Auth. Normal operator rotation requires stop/reconfigure/restart; changing another shell cannot update the running process. Acceptance: two named clients can receive separately bounded credentials, one can be revoked without interrupting the other, expiry and denied scopes are tested, and diagnostics expose status without credentials. Received copies remain outside revocation’s reach.

For UI02, prioritize a guided readiness view connecting sources, exact claim/plan decisions and package status, with actionable blockers and distinct integrity/eligibility/qualification labels. Show MCP enablement and its independent access lifetime without displaying the bearer. Verify comprehension through the real synthetic browser journey. The next functionality recommendation is portable approval receipts, with explicit rule-to-goal provenance, while maintaining the current local authority checks.
