# 08 UI/UX — continue from a saved goal to its rule form

**Problem and evidence.** Saved goal cards show owner, title and acceptance, then stop ([PortalLive:1980–1985](../../../../lib/harness_forge_web/live/portal_live.ex#L1980)). The separate Evidence form requires an explicitly blank “Saved goal” choice and explains that save/selection is not approval ([PortalLive:1542–1601](../../../../lib/harness_forge_web/live/portal_live.ex#L1542)). The current test navigates through the sidebar after saving ([goal_claims_test:28–51](../../../../test/harness_forge_web/goal_claims_test.exs#L28)). Fixed server-directed focus already exists ([PortalLive:514–519](../../../../lib/harness_forge_web/live/portal_live.ex#L514), [app.js:110–129](../../../../assets/js/app.js#L110)); the target heading currently has no focus target.

**One benefit.** Add a “Propose a rule from this goal” button on each saved-goal card. Activation opens Evidence and focuses the goal-rule heading after the LiveView patch; the next Tab reaches the blank “Saved goal” select. Do not preselect the clicked goal: the operator must inspect its current exact version and choose deliberately. Saving, navigation, proposing and approving remain distinct.

**Acceptance.** Positive: keyboard activation from a saved card lands on the visible heading; next Tab reaches the labelled blank select; selecting a current goal and writing a rule uses the existing proposal flow. Negative: activation creates no claim, decision, plan or artifact and sends no hidden selection; an unavailable goal leaves the form unavailable. Edge: after reset, revocation or changed goal content, no stale card/draft/focus event restores private text or silently selects an old version. Check 320/390 CSS widths at actual 200% zoom, visible focus, logical order and an axe WCAG AA scan; inspect screenshots and DOM. A five-person first-time comprehension target (4/5) is **unperformed** and cannot be claimed from those checks.

**Expected ownership and verification.** PortalLive card/event/heading and focused LiveView regression: one product author. `assets/js/app.js` focus allowlist/visible-target guard and browser Playwright keyboard/zoom/a11y checks: a distinct UI author or root, as assigned. Root alone schedules Mix, native browser and release verification, including reset and approval regressions. Preserve existing generation/full-digest, immutable-history, privacy, domain/export and unknown-publication boundaries.

**Competing alternative.** Invalid package names currently reach generic provider-import advice ([PortalLive:1258–1281](../../../../lib/harness_forge_web/live/portal_live.ex#L1258), [Contracts:327](../../../../lib/harness_forge/contracts.ex#L327)). Fixed name-specific recovery is smaller and corrects demonstrated misdirection. I favor the saved-goal keyboard continuation because it opens a blocked next step; human comprehension remains unmeasured, so Astra may reasonably choose the smaller repair. Prior outcome, coherence and portable-authority dissent remains unresolved.
