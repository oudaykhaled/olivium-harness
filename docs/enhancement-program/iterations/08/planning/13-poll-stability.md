# 08 proposal — preserve focus when a running evaluation finishes

**Evidence and problem.** `PortalLive` refreshes evaluations every 2,000 ms on the Evaluations tab ([portal_live.ex:22–26](../../../../../lib/harness_forge_web/live/portal_live.ex), [portal_live.ex:532–551](../../../../../lib/harness_forge_web/live/portal_live.ex)). Each run's Cancel button exists only for `pending`/`running`, so a terminal patch removes a potentially focused control ([portal_live.ex:2196–2211](../../../../../lib/harness_forge_web/live/portal_live.ex)). Iteration07 observed stable Queue focus through 12 polls, but did **not** observe focused-Cancel removal ([final UI review:63–67](../../07/review/final/uiux-review.md)). Focus failure is a risk, not an observed regression. Baseline: 12 stable Queue-focus callbacks; no terminal-Cancel measurement.

**One benefit.** Keep keyboard position and announce the exact run outcome when focused Cancel disappears. Reuse the existing run article and Phoenix LiveView JS hooks; no dependency or new authority. An article hook records focus before its DOM patch and, only if that run's Cancel was focused and removed, focuses its updated, labelled container. No transfer after the user moves elsewhere, changes tabs, loses authentication or resets the workspace. The full run ID remains visible.

**Acceptance.** Positive: focus Cancel on a pending run; after terminal refresh, focus lands on that run's summary and next Tab advances normally. Negative: focus Compare or another run during update; focus remains there. Edge: two runs complete together; only the previously focused run can claim focus. Cancellation, lock/reset and navigation never revive removed state or shift focus across tabs. Inspect at 320/390 CSS px and actual 200% zoom; target zero horizontal clipping and one visible focus indicator. Browser evidence records active element before/after an actual terminal transition.

**Ownership and verification.** A UI author owns `assets/js/app.js`, `portal_live.ex` markup and focused UI tests; root schedules browser/Mix checks. No performance gain is claimed without timing. The stronger competing alternative is invalid-package-name guidance: it repairs demonstrated misleading recovery with smaller scope; this proposal closes an unobserved keyboard risk. Goals-to-Evidence continuation has broader reach but needs unperformed novice comprehension evidence. Company/model fitness and full accessibility remain unproven.
