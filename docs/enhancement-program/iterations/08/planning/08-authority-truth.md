# 08 proposal — deliberate Goals → Evidence continuation

**Problem and evidence.** Saved goal cards end at owner, title and acceptance text ([PortalLive:1980](../../../../lib/harness_forge_web/live/portal_live.ex#L1980)); the separate goal-rule form requires a saved-goal choice and says saving/selecting is not approval ([PortalLive:1542](../../../../lib/harness_forge_web/live/portal_live.ex#L1542)). Existing tab navigation and focus events provide a local seam ([PortalLive:514](../../../../lib/harness_forge_web/live/portal_live.ex#L514)). Operators lack an explicit next step from their saved goal, while an automatic goal choice would falsely imply that this saved intent has already been reviewed.

**One bounded UI benefit.** Add a per-card “Propose a rule from this goal” continuation to the Evidence form. The action only navigates and focuses the form heading. The Saved goal selector remains blank; the operator deliberately chooses a current goal snapshot and writes a rule. Fixed copy states that proposal and exact-revision approval are later, separate actions. No server-side draft, claim, decision or artifact is created by navigation.

**Acceptance.** Positive: keyboard activation from a current card opens Evidence, focuses the rule-form heading, and the next Tab reaches blank Saved goal; explicit selection and valid submission still propose the exact goal-based revision through the existing flow. Negative: continuation alone leaves claim, approval and artifact counts unchanged; no stale or hidden selection survives. Edge: after workspace reset, goal removal/change or unavailable goal data, the old card/action cannot revive a draft or submit an old snapshot; focus lands on a visible recovery message. Controls and copy fit 320/390 CSS widths at actual 200% zoom. Verify screen-reader announcement and an unperformed first-time-operator comprehension target separately; do not infer either from pixels.

**Expected ownership and verification.** UI author: `lib/harness_forge_web/live/portal_live.ex` plus its focused LiveView tests; root owns native browser, canonical Mix window, source-bound evidence and final acceptance. Reuse the existing generation reset ([PortalLive:935](../../../../lib/harness_forge_web/live/portal_live.ex#L935)) and current snapshot token ([PortalLive:1583](../../../../lib/harness_forge_web/live/portal_live.ex#L1583)); preserve immutable digest/run identity, privacy and export boundaries.

**Strongest alternative.** Invalid package names currently fall through generic provider-import advice ([PortalLive:1258](../../../../lib/harness_forge_web/live/portal_live.ex#L1258)); its fixed, name-specific recovery is a smaller, demonstrated repair. I favor the saved-goal next step for workflow reach, conditional on the deliberate-choice checks above. Neither option establishes company/model fitness, portable approval authority, novice comprehension or publication completion.
