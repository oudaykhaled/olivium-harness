# Adversarial admission: inspect release eligibility before approval

**Candidate and value.** Add a read-only `Releases.admission/3` for an operator selecting an artifact digest, evaluation ID and scope. Return a string-keyed report with exact requested identities, `"status": "eligible" | "blocked"`, one stable refusal code, and a safe next action. The report confers no approval; `Releases.approve/1` still repeats its transactional checks. This closes a readiness gap: today `Releases.approve/1` loads the stored artifact/run and calls `Releases.Validation.check/3` inside its mutation flow (`lib/harness_forge/releases.ex`), while the guide preflights only `Company.build_inputs/1` (`iterations/02/handoff-to-03.md`). An owner can know why a package is inadmissible before supplying an actor and attempting approval.

**Boundary.** Resolve through `Harnesses.get/1` and workspace-scoped `Evaluations.get/1`, then reuse `Releases.Validation.check/3`, which checks workspace, artifact digest, qualified task outcome, complete cleanup, scope, runtime, suite, required controls, current `Harnesses.eligible/1`, and `Evaluations.applicability/2`. `Harnesses.get/1` reads verified immutable bytes; `Compiler.verify/1` is deterministic integrity, not approver authentication (`lib/harness_forge/artifacts.ex`, `lib/harness_forge/compiler.ex`, `lib/harness_forge/releases/validation.ex`). Keep admission read-only and recompute on each request; never persist a positive result as authority. Map errors to actionable codes without exposing source bodies or credentials.

**Adversarial acceptance.** A forged evaluation ID or caller-supplied `"runtime_qualified": true` cannot replace the stored run. An evaluation from another workspace is refused; a mismatched artifact digest or scope is refused. Changed plan/claim authority, runtime/model/suite/environment identities or incomplete cleanup block a previously favorable result. Tampered artifact files fail `Harnesses.get/1`; an altered run digest/check record cannot be accepted merely because a prior report said eligible. Recheck these cases through `approve/1`, including the interval after an eligible admission response. A synthetic `synthetic-go-v1` pass remains unqualified, as iteration 02's five retrospectives and handoff warn; no real-model fitness claim follows.

**Scope choice.** Product/architecture favor goal-origin rules and declared conflicts; UX/trust/quality favor qualification readiness (`iterations/02/retro/01-product.md` through `05-quality.md`). Goal authority gives larger expressiveness but requires versioned schema, migration and purge/restore work. Portable signed approval addresses a different receiving-workspace trust boundary. This admission slice reuses existing gates, so it is smaller and immediately useful; its risk is a stale-looking positive UI. Display the digest, evaluation ID and current-check time, and label the result provisional until transactional approval succeeds.
