# Proposal 13 — Exact company artifact inspection from the CLI

**Functionality candidate.** Add a read-only `company inspect PLAN_ID REVISION_HASH DIGEST` command that returns one machine-readable readiness record for an automation operator. The command should identify the requested plan revision and artifact digest, then report separate states for plan authority, stored-byte integrity, current export eligibility, task-evaluation applicability, and release eligibility. Each blocked state needs a stable reason and a safe next command. It must never approve, evaluate, promote, or export by itself.

**Why this gap exists.** `CLI.run/1` currently offers `company decide`, `company build`, `export`, `evaluate`, `runs`, `approve-release`, and `releases` as separate commands (`lib/harness_forge/cli.ex:52-60,184-208`). `company build` returns digest, manifest, capabilities, and diagnostics, but no subsequent command relates that digest back to one exact plan decision. `Harnesses.build_plan/2` pins the expected revision and `Harnesses.eligible/1` rechecks evidence and plan binding (`lib/harness_forge/harnesses.ex:10-28,134-153`). `Artifacts.read/2` verifies stored bytes (`lib/harness_forge/artifacts.ex:30-36,137-165`). `Evaluations.applicability/2` and `Releases.Validation.check/3` enforce richer identities and cleanup (`lib/harness_forge/evaluations.ex:68-77`; `lib/harness_forge/releases/validation.ex:9-58`). The CLI needs a shared domain projection of those gates, not duplicated policy in argument parsing.

**Acceptance.** For a built, approved exact revision, inspection returns matching plan ID/hash/digest and each gate independently, without workspace mutations. Wrong plan/hash/digest combinations, revoked claims, changed context, corrupt stored bytes, stale evaluation identity, failed/cancelled task runs, incomplete cleanup, and unavailable managed runtime/model produce distinct blocked results. A passing static or smoke check remains explicitly unqualified. An eligible predecessor remains inspectable after a proposed successor. JSON output is deterministic and excludes credentials, source bodies, and unsupported claims. Tests exercise the domain projection and CLI contract; successful `mix test` and warning-gated compile are required.

**Scope and risk.** Reuse current local authority; do not add portable approval receipts or imply company fitness. The main risk is an attractive “ready” label concealing missing real-model outcome evidence. Name the final field `qualification_status`, default it to `unproven`, and show the exact missing evaluation/release gate. This complements the retrospective split: product/architecture favor goal-origin conflict authority, while UX/trust/quality favor exact-artifact readiness. Astra should choose the domain capability first if only one bounded feature fits iteration 03.
