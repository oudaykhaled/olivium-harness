# Planner 03 — server-owned corpus scope at the analysis seam

**Recommend a working “analyse this project corpus for this saved goal” flow.** The operator chooses one saved project and one goal, then sees a server-derived scope summary, paginated source metadata, capture/index progress, explicit exclusions and a bounded preview of supporting *and contrary* passages before requesting a recommendation. The server freezes a scope/version and retrieval origin; the browser sends its opaque identity, never a list of source IDs. The first public synthetic demonstration should include more than four eligible source revisions, a contradiction and one excluded or stale capture. A reviewable first slice can use measured SQLite/FTS5 passage retrieval; keep the Graphiti 0.31.2 pinned adapter contract alongside it for the following connected functionality slice, using upstream Jev/runtime/extraction/hybrid components rather than building another engine.

The current boundary is concrete. `Company.Analysis` accepts exactly 2–4 source references, sums whole bodies to 32,768 bytes and embeds them in one prompt (`company/analysis.ex:169–274`). `Company.Validation` stores project/profile membership in 100-ID arrays (`company/validation.ex:12–30,157–163`); `Company.resolve/1` uses those arrays for plan scope (`company.ex:257–320`). The UI pins checked revisions in component memory, renders every assigned source and labels its distinct-citation count as merely structural (`company/analysis.ex:19–67,178–310,430–525`). `CompanyPanel` accepts a client `source_ids` array of at most five, dispatches after draft capture and reloads catalogue records (`company_panel.ex:389–431,697–701,908–946`). Existing web tests establish unchecked selection, stale-pin refusal, late-callback handling and corrected actual export, but only in the small synthetic flow (`company_analysis_test.exs:46–190,335–436`). This is a useful safety baseline, not corpus-scale evidence.

**Three-writer ownership.** Root owns shared migration, PortalLive/CompanyPanel handoff, board and integration. Domain writer owns relational project-corpus membership, versioned selection/retrieval origin, paginated metadata and bounded FTS5 passage API in `lib/harness_forge/company/`; refuse empty or foreign scopes before retrieval and each provider dispatch. UI writer owns `components/company/analysis.ex`, progressive disclosure, focus/keyboard and presentation tests. Keep exact source/revision/hash/UTF-8 spans, parent text, effective/capture dates and status visible beside conflicts; retrieval rank grants no policy authority. Persist all prompt influences, including uncited passages, through claim/plan/export eligibility. Continue consent and per-attempt budget checks, tombstone revoked derivatives before any Graphiti removal, and deny serving after failed rebuild. Preserve exact claim edit/reject/approval and separate plan approval.

Acceptance: selecting project plus goal yields a bounded first page and truthful total/unknown coverage; a more-than-four-source fixture finds supportive and contrary evidence, human correction excludes rejected guidance and reaches actual exported bytes and a representative assessment. Negative: foreign/empty scope, stale revision, revoked source and unconsented stage never dispatch or produce an eligible claim. Recovery: interrupted capture resumes without duplicate membership; changed scope or failed derivative rebuild blocks old results and invites a fresh, explicit selection. Test pagination/latency at increasing public synthetic sizes and compare FTS5 with Graphiti on the same expected evidence; do not call the offline 51 tests production proof. Estimate **medium-large, 2–3 weeks** across three writers plus independent QA. An alternative is a client-side paged picker over existing arrays: cheaper this round, but it retains the manual bottleneck and cannot establish server-owned scope, so I dissent from selecting it.
