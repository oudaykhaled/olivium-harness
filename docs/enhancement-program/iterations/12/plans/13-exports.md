# Proposal 13 — Review a corpus slice through its export consequence

**User and job.** A company operator with an authorised corpus and saved future goal needs to find relevant and contrary evidence, correct a proposed rule, and trace guidance into a target package and representative task. Success is more owner-reviewed critical sources found with less selection time, while exported bytes and task observations remain traceable. The hypothesis fails if reviewers still hand-pick four files or miss a critical contradiction.

**Observed seam.** The current Analysis UI renders a checkbox per assigned source and requires 2–4 selections (`components/company/analysis.ex:19–66,241–285`); the domain packs whole bodies under a 32,768-byte total and one 49,152-byte prompt (`company/analysis.ex:169–213,257–274`). Its review already shows conflict, uncertainty and byte-span excerpts and requires a saved resolution (`components/company/analysis.ex:343–418,430–545`). The downstream contract is valuable: an exact approved plan builds an immutable package, export rechecks eligibility (`harnesses.ex:8–25,211–269`), and the UI links a built package to a one-goal assessment (`components/company/plan.ex:310–422`; `components/company/assessment.ex:202–300`). Existing LiveView tests prove an edited rule reached actual `AGENTS.md` and excluded the original text, with a scripted provider (`company_analysis_test.exs:83–212`); assessment tests prove a structurally accepted owner report while calling it unverified (`company_assessment_flow_test.exs:34–73`). These are mechanics, not model or task-quality proof.

**Decision (bounded UI slice).** Add one project-scoped, saved-goal evidence worklist: server-issued corpus identity, captured/current/blocked/unscanned counts, paginated metadata and bounded passage tray. Group supporting, conflicting and unknown passages beside one recommendation; expose status, effective/capture dates, parent context, exact UTF-8 span and revision/hash. Reviewers inspect, edit/reject/approve, then continue to exact plan, built package, actual export and one-goal assessment. Show export consequence from verified target bytes. Unavailable retrieval/model stages keep the saved worklist and draft. Use a larger public synthetic corpus and FTS5 baseline; following functionality wires resumable capture and Graphiti 0.31.2 through its bounded Python adapter to this path. Server-owned nonempty scope, stage consent/budget, transitive origins and tombstone-denied derivatives gate admission.

**Acceptance.** Given an authorised corpus and saved goal, when a bounded retrieval completes, then the operator sees paginated scope/coverage plus supporting and contrary original passages, corrects a claim, approves exact claim and plan, and verifies corrected guidance in actual exported target bytes and an assessment bound to that package. Given an out-of-scope, revoked or changed revision, when retrieval or export is attempted, then no passage is served or dispatch made and the stale package cannot export. Given an interrupted scan or failed summary rebuild, when the operator returns, then progress resumes from a checkpoint, unknown coverage remains visible, tombstoned material stays blocked, and the prior draft is recoverable without silently approving it.

**Ownership and trade-off.** UI owner: Analysis/Plan/Assessment components and LiveView tests. Domain owner: corpus/retrieval-origin read contracts, checkpoints and export binding tests. Root: shared PortalLive, migrations, model controls and privacy. Estimate 8–12 engineer-days plus backend qualification. A four-file picker costs 1–2 days but retains the bottleneck; standalone search improves discovery yet leaves correction/export causality unproven. Preserve exact approvals, WEB-11-01/02, CODE-11-02, false-owner qualification and no host-generated-code execution.
