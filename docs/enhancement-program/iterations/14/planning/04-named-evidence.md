# 04 — Name evidence before asking for trust

**Source observation.** The question result lists only lane, provisional relation and inclusion state beside repeated “Inspect exact passage” buttons (`lib/harness_forge_web/components/company/corpus_review.ex:601-621`). The title appears only after opening one passage (`:628-634`). `Retrieval.read_run/4` currently pages 26 rows containing passage IDs and retrieval diagnostics, not source metadata (`lib/harness_forge/company/retrieval.ex:579-593`); `RetrievalItem` persists selection and relation, not document identity (`retrieval_records.ex:28-37`). The existing `Passages.envelope/1` already verifies current scope and exact UTF-8 window and supplies bounded title, safe URL, document status, event/effective/capture dates, snippet and parent context (`evidence/passages.ex:343-373,389-425,437-443`). LiveView clears stale results when a run changes and clears a failed passage (`corpus_review_live.ex:399-424,501-514,543-564`). These are source facts, not evidence that users understand the labels.

**Root runtime evidence.** The iteration-13 handoff records a public scripted browser journey through human resolution, exact claim approval, separate plan approval and eight exported files. Static integrity passed; task evaluation remained `BLOCKED: model_not_selected`. Its failed replacement query cleared prior evidence. This planner ran no browser or tests.

**Inference and proposed slice.** Repeated anonymous buttons force operators to open candidates one by one to establish origin and chronology; this likely slows conflict review. Give each existing 25-row question page a compact evidence card: source title (explicit “Untitled source” fallback), actual event/effective date with distinct captured date, document/decision status or “status unknown,” a short exact excerpt, provisional relation and inclusion state. Keep a clear “Open full context” action for the verified parent window and source link. Put full hashes, IDs, byte ranges and lane diagnostics in an expandable provenance detail, while retaining access to them. Never infer policy authority from recency or score. Supporting, contrary and unknown labels remain provisional. Missing metadata stays visibly unknown; do not synthesize dates or status from titles.

**Ownership seam and risk.** Backend owner should expose a bounded, authorization-checked page projection from existing `Passages` verification, retaining the current run digest/cursor and avoiding 25 unbounded revision-body hydrations; LiveView should pass only that projection; component owner renders semantic headings, labelled actions and keyboard-operable details. A changed/revoked passage must disappear or make the run stale before rendering, never survive as a cached card. This is a presentation seam, not retrieval reranking.

**Acceptance.** In a public fixture with policy, later exception, draft and contrary incident, a fresh operator identifies each card’s origin/date/status and opens exact context before review; no per-document assignment is needed. Check missing metadata, long titles, Unicode excerpt boundaries, revoked/changed source, failed replacement and pagination. Confirm hashes remain reachable, claim and plan approvals stay separate, and export/static PASS remains distinct from blocked task evaluation. Defer relevance, semantic support and real-model task benefit to iteration 15.
