# Iteration 14 proposal 11 — keyboard and screen-reader review

**Smallest useful UI slice:** make the connected corpus question → evidence → review handoff operable and understandable by keyboard and screen reader. Retain the existing scope labels, native `<details>/<summary>`, and visible focus outline (`components/company/corpus_review.ex:60–61,201–202,309–310`; `assets/css/app.css:265–269`). Focus work on the pipeline after scope selection.

**Direct source observations.** The pipeline's question and mode have labels (`corpus_review.ex:582–599`). Capture state is plain text, while only “busy” has `role="status"` and pipeline errors have `role="alert"` (`:562–576`). Each evidence row exposes lane/relation and an identically named “Inspect exact passage” button; source title appears only after expansion (`:607–633`). The expanded passage is inserted after the result list without an evident focus target or return-focus action (`:629–634`). Retrieval and synthesis completion update `large` state without calling the LiveView `focus/2` helper (`live/corpus_review_live.ex:570–607`); the existing inspector does call it for opening/closing passages and errors (`:210,:727–739,:763–772`). A failed replacement clears stale run and synthesis handles (`:367–378`); the frozen flow test checks data clearing, not keyboard focus (`corpus_review_flow_test.exs:392–433`). Component tests check inspector alert/status targets (`corpus_review_component_test.exs:233–245`). CSS provides visible focus styles (`app.css:187,269`).

**Predicted accessibility risks, untested here.** After a query, failure, or passage expansion, keyboard focus may remain on a removed or distant control; a screen-reader user may miss the new result/error. Repeated passage-button names make a button list ambiguous. Capture progress can change without a reliable announcement. These are source-based predictions, not observed browser failures.

**Recommendation.** Give each pipeline passage button an accessible name containing its source title and provisional relation, with the title visible in its result row. Add a named, programmatically focusable result/error target and use the existing focus event on retrieval completion/failure and passage open/close. Announce concise capture status through one live region; avoid repeatedly announcing every rendered row. Keep semantic uncertainty, contrary labels, and separate claim/plan approval language explicit. Do not change retrieval ranking, authority, caps or model dispatch.

**Acceptance.** In the packaged public-fixture journey, use keyboard-only navigation from scope through question, evidence, passage, exact recommendation review and the separate approvals; verify visible focus, stable return focus, source-distinguishable accessible names, and no focus on stale evidence after a failed replacement. With a screen reader, verify one useful announcement for capture/retrieval success, insufficient evidence and setup failure, and correct interpretation of static PASS versus blocked task evaluation. Add focused component assertions plus a real browser/AX check; report actual observations separately. Root owns shared JS/focus wiring, component and LiveView owners coordinate markup/events. Defer semantic relevance, real-model task benefit and scale qualification to functionality 15.

**Dissent:** broad page reordering alone may improve discovery but leaves these keyboard and announcement gaps intact; the narrow interaction slice should accompany any chosen journey layout.
