# 14.10 — Outcome and export comprehension

**User/job/hypothesis.** A company operator needs to hand off actual reviewed files and know whether a representative task has succeeded. Success is an uncoached operator identifying the exported target files, the exact package, and the independent static, task and owner-assessment states, then choosing the right next action. Falsifier: an operator calls a blocked task a pass, mistakes a build for export, or cannot locate the files.

**Direct frozen-source observations.** The plan’s build section says export, evaluation and release are separate, yet the built result offers three separate navigation buttons and no joined outcome (`lib/harness_forge_web/components/company/plan.ex:317-323,398-481`). `PackageExport.present/3` confirms an exact digest and destination and returns “Export complete,” but this presentation contract carries no file inventory or task state (`lib/harness_forge_web/package_export.ex:19-26`). The owner-assessment receipt displays recorded judgment, task and critical status; its accepted heading requires current applicability (`lib/harness_forge_web/components/company/assessment.ex:775-810,1039-1048`). Package readiness already separates integrity, selected evaluation, cleanup and release admission, offers a server-provided next action, and explains that static integrity did not run a task (`lib/harness_forge_web/components/package_readiness.ex:107-171,206-265`). `EvaluationReason.label/1` distinguishes `model_not_selected` from `integrity_only` (`lib/harness_forge_web/evaluation_reason.ex:23-32`). Assessment state binds exact plan revision and artifact digest (`lib/harness_forge_web/company_assessment_state.ex:5-8`). These are reusable presentation/identity seams.

**Root-reported execution, not my observation.** The iteration 13 handoff records eight actual fresh exported files and independent persisted-byte verification, static PASS, task BLOCKED (`model_not_selected`), `runtime_qualified=false`, and usage `not_dispatched`. No real-model company-task benefit follows. **Inference:** even accurate labels across separate tabs create a handoff gap: the operator must reconcile the export path, selected package, static result and task blocker unaided. The existing readiness inspector mitigates this, so duplicate admission logic would add risk.

**Smallest UI scope.** Add an exact-package outcome handoff in the existing Company build/Package path: show verified export destination and actual file names only after confirmed export; show static integrity and selected task evaluation as separate rows, including “not run/blocked” and reason; expose the existing readiness next action and an assessment link where bound. Keep owner-reported assessment separate from model-backed evaluation. Reuse `PackageReadiness` and `PackageExport` view contracts; server authority remains unchanged. Avoid publishing local private paths in docs or telemetry. Alternative: copy-only labels in the build section (cheap, weak connection to file evidence); full workflow dashboard (stronger overview, larger scope and more stale-state risk). Recommend the bounded handoff.

**Acceptance.** Given a confirmed export, when the operator opens its outcome, then the exact digest, destination and actual target-file names appear with a route to readiness. Given static PASS and task BLOCKED `model_not_selected`, when viewing the same package, then the task is explicitly “not dispatched,” never “passed,” with the existing model-connection next action. Given a conflicting/uncertain export, when the operator retries, then no file-success claim appears and the destination is checked before choosing a fresh directory. Given changed evidence or historical assessment, when the view refreshes, then current eligibility and historical owner judgment stay distinct. Verify with a packaged public-fixture browser journey and focused rendering checks; semantic fitness remains iteration 15 work.
