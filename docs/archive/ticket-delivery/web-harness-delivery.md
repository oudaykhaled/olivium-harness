# WEB harness file delivery

`HarnessForgeWeb.HarnessDelivery.preview/1` and `download/1` read the exact digest returned by a successful build. They never build, approve, export to disk, launch a coding agent or run generated instructions. The controller and LiveView must authenticate the current operator session and resolve the workspace from server state before using the service. The download controller checks the session again before sending bytes.

Every service call acquires the existing privacy fence, checks `Purge.ready()`, reads the artifact through `Harnesses.get/1`, and rechecks `Harnesses.eligible/1` in a read transaction. Artifact reads verify compiler output, digest, paths, stored metadata and exact payload bytes. Missing, changed, revoked, foreign-workspace, pending-purge and invalid artifacts return the same `{:error, :harness_unavailable}` without payload or internal error details.

The preview is a string-keyed map containing `digest`, `name`, `version`, `target`, `files` and `verification`. Files are sorted by relative path and contain `path`, `content`, original `bytes`, complete-file `sha256` and `truncated`. Text is limited to 32,768 UTF-8 bytes per file and 262,144 bytes across the preview. The UI must render this text with ordinary escaping. A truncated preview is never substituted for downloadable content.

Downloads return `filename`, binary `bytes` and `digest`. An in-memory ZIP contains only verified file-map entries and their complete original contents, including dot directories; it excludes the store's `artifact.json`, workspace records and credentials. Before archive allocation, delivery requires 1–128 safe relative entries totaling at most 16,000,000 bytes. There is no user-supplied filesystem path, disk export, shell command or target execution. ZIP container timestamps are not an artifact identity; exact filenames and contents are the contract.

Root adds the authenticated `GET /harnesses/:digest/download` route using a session/security pipeline that permits ZIP requests. The controller returns an `application/zip` attachment with a digest-derived filename, `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. An unavailable authenticated download returns HTTP 404 and fixed plain text. Unauthenticated requests are rejected by the existing operator-session pipeline before delivery.

Verification describes generated files, current byte integrity and eligible exact decisions only. `representative_task` and `release_qualification` remain `unobserved`; file delivery does not establish company usefulness, model quality, task benefit or runtime enforcement.

The preview now also includes `verification.recorded_checks`: `status` is `available` or `unavailable`, with up to ten historical `rows` containing only `id`, `inserted_at`, `kind`, `outcome` and `reason`. `Evaluations.recent_summaries/1` queries the exact server workspace and verified artifact digest, ordered by timestamp and ID descending. SQL projects allowlisted scalar JSON values, never full result maps or execution contexts; unknown or malformed fields become fixed `unknown` values. Dates are normalized to ISO 8601. Reason values are fixed codes suitable for the existing `EvaluationReason.label/1` UI mapping. Empty available rows mean no recorded checks; unavailable history remains distinct and does not block otherwise eligible file delivery. These are historical observations and do not update present applicability or qualification.

Prepared verification is in `test/harness_forge_web/harness_delivery_test.exs`: real approved source and goal-plan builds, separate plan approval, exact ZIP entry bytes, preview truncation, entry limits, current authority drift, revocation, claim supersession, actual/pending purge, payload/metadata tampering, wrong workspace, authentication, ZIP headers and privacy-fence serialization. These tests have not been executed by the service author; Root owns the coordinated run and actual browser journey. UI escaping and active-session clearing require the UI owner's integration verification.

Six additional prepared history cases cover actual static-integrity PASS and unsupported-backend BLOCKED records, latest-ten tie ordering, workspace/digest isolation, malformed/large synthetic canaries and SQL projection, empty versus unavailable history, current revocation despite historical PASS, and invalid references. No additional provider/runtime dispatch was performed by the service author; Root owns the coordinated test run. Download construction and its exact ZIP file contract are unchanged.
