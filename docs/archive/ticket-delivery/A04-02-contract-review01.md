# A04-02 independent software-contract review

**Verdict: changes requested before author handoff.** The ownership boundaries and existing authority reuse are appropriate, but three interface gaps remain. These are proposed-contract findings, not demonstrated implementation exploits. Reviewed decision SHA: `c2c7a88957cf4abec5139328ddb2990c45649002ca4dc09ac46682271518e162`.

## Blocking

**P1 — Bind explicit authorization to the reviewed preparation (decision15–29).** `authorize` carries only config identity, while manifest/stage/consent references live in mutable run state. The contract does not define whether `expected_version` protects session or run state, nor whether asynchronous preparation increments it. A tab can therefore display preparation A and authorize after state advances to B under the same config unless implementers invent an extra rule.

Minimal correction: define `id=setup_session_id`, `expected_version=setup_session.lock_version`, and add `expected_run_version` for actions after prepare. Return both versions. Persist immutable preparation `{id,digest,config_ref,retrieval_ref,stage_ref,manifest_ref,context_digest}`; `authorize` additionally supplies `prepared_ref:{id,digest}`. Compare all identities atomically against current owned state. No grant or budget on mismatch. Worker publication CAS-increments run version; it cannot silently replace the reviewed preparation. `RunAuthorization.authorize(config_ref,prepared_ref,caller)` is a trusted internal call reachable only through the accepted explicit command. Compatible consent reuse still calls the existing same-pin validator; context compatibility must compare a specified canonical projection, including goal/profile/project, purpose and destination, not merely source coverage. The immutable receipt retains exact manifest identity.

**P1 — Freeze cross-lane operation and acquisition interfaces (decision25,27,35–39).** `binding_ref`, registered setup operation and capture profile binding are not specified objects/APIs. Current `AnalysisV2.analyze/3:13–27` reseals and creates an operation-owned budget; `StageAuthority.new/5:197–204` starts Ledger before opening StageControl. Merely checking registration after either call is too late.

Minimal correction: Setup owns durable `setup_run_operations` with unique workspace/operation_id and command→operation linkage. Registration, command receipt and run CAS commit together before any work. Define trusted `SetupRuns.operation_binding(operation_id,caller)` returning immutable config/prepared/authorization references and expected generations; reject supplied replacements. Models owns `AnalysisV2.analyze_prepared(operation_ref,caller)`, `StageAuthority.new_for_run(operation_id,manifest_ref,stage_ids,authorization_ref,caller)` and `RunAuthorization.current(authorization_ref,operation_ref,caller)`. StageControl persists authorization_id/budget_id; Ledger resolves them from registration, never falls back to operation_id for a registered setup operation. Legacy new/analyze and registration-less direct dispatch must fail before budget creation for those IDs. Fresh retries receive distinct registered operation IDs but the same authorization/budget. Bind exact prepared prompt inputs/windows and manifest through execution/publication; no reseal.

Root owns `Capture.start_for_setup(config_ref,command_ref,caller)` and corresponding run/profile schema. Define its transaction participation explicitly: run, immutable limits/fingerprint, Oban intent, command receipt and CAS either all commit or all roll back. Durable unique item/checkpoint charges and lease fencing must cover enumeration and body/file reservation before I/O; commit actual accounting with source publication. Existing checkpoint upserts reset item state and increment entry_count (`capture.ex:316–346`), so they are not replay-safe aggregate counters. Count identical replay once; changed content needs a fresh charge or stale rejection, never a free reread bypass. Expired leases retain unresolved allowances; resume never renews the original deadline. Exhaustion is incomplete, not successful truncation.

**P2 — Define explicit new-run recovery (decision31–35).** Unique session/config authorization correctly prevents replay budget resets, but fixed-profile `prepare` has no explicit new-run identity/intent. After expiry or cancellation, authors could either permanently block the same scope or silently mint another config/budget.

Minimal correction: keep ordinary prepare idempotent for identical active intent; add an explicit `new_run` command (expected versions and predecessor run_ref), creating a new run incarnation, not automatic authorization. Require a fresh displayed run-limit confirmation before its budget exists. Increased caps remain unsupported by this fixed-profile slice; future changes must create a new explicit authorization. Preserve predecessor usage/uncertainty and links. No navigation, retry, reload or internal stage may perform this action.

**Schema/return freeze:** Root defines `setup_run_preparations` (workspace,owner,session,config,run_incarnation,id,digest,retrieval/stage/manifest refs,context_digest; immutable) and `setup_run_operations` (workspace,owner,session,run_incarnation,command_id,operation_id,preparation_id,authorization_id,kind; immutable). Unique command identity and workspace/operation_id prevent duplicate admission; composite workspace references prevent cross-workspace linkage. Mutable run states own CAS version/phase; workers publish only against their registered operation and expected version. Models owns authorization validation and StageControl/Ledger behavior; Setup owns registration/orchestration; Root alone edits migrations/record schemas. Internal reads return `{:ok, binding}` or fixed errors; commands return accepted receipt or conflict with current authorized versions. Replay checks an existing matching command before stale-version rejection, but revalidates caller before revealing its receipt. Authorize commits consent receipt, authorization/Ledger identity and command receipt atomically; failure leaves none partially granted.

## Non-blocking implementation requirements

Ledger15–19 currently rejects zero cost; narrow validation to positive request/token caps and nonnegative cost, with bounded integers and existing-budget exact-cap verification. Never coerce zero request/token limits to defaults. Ollama estimate is zero (219), but zero cost must not admit cloud or changed descriptors. Reservations may conservatively consume attempts before a send; do not promise two successful sends.

Check current authorization/revocation AND consent at final HTTP guard/publication, not only admission. Existing final guard reaches `current/1`, whose inspected845–859 does not independently check consent. Withdrawals must invalidate active registered operations while retaining uncertain Ledger reservations. Root owns all new-table migration, inventory, purge and restore quarantine; never restore active authorizations or duplicate a budget during remap.
