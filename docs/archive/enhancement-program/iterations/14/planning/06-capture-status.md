# 06 — Capture progress and honest coverage

**Recommendation.** Put an evidence-capture status card beside the primary corpus question. It should explain what this run has observed, what has reached the index, what failed, and whether the scan is verified. Keep review, separate claim/plan approvals, export and task evaluation visually downstream. This reuses the current capture contract; it requires no graph or ranking change.

**Direct frozen-source observations.** `Capture.capture_status/3` already returns revision-bound pages of per-path outcomes, 25 rows at a time (`lib/harness_forge/evidence/capture.ex:76–89`). `status/1` provides current-epoch state counts, checkpoint number, verified completion, error code and an **independent** active-member index numerator/denominator (`capture.ex:513–544`). `Capture.resume/3` accepts a matching lock version for paused/failed or expired runs (`capture.ex:93–117`). The schema retains epoch, scan verification, incompleteness and checkpoint fields (`evidence/capture_records.ex:11–20`). The LiveView currently calls status without a cursor, keeps the response only in the current socket, and offers no resume event (`lib/harness_forge_web/live/corpus_review_live.ex:17,323–339`). The component renders just `Capture: <state>` and refresh (`lib/harness_forge_web/components/company/corpus_review.ex:570–577`), although the scope summary correctly says discovery and whole-corpus model coverage are unknown (`corpus_review.ex:263–287`).

**Inference.** A paused scan can look indistinguishable from a useful completed capture, while a fresh tab loses the run handle. The visible `fts.ready` state can be mistaken for full discovery: its denominator is *current active members*, not all company files (`capture.ex:521–540`). Current-epoch state totals are observed entries, not a predeclared inventory denominator. Directory entries also appear as `excluded`; therefore do not call every exclusion a skipped *file*.

**Small UI slice.** Render run ID suffix, state, checkpoint, verified/incomplete flag, last error, and current-epoch outcome counts labelled “observed entries so far”: captured, unchanged, excluded, pending, failed/stale. Render indexing as `indexed / active captured members` and label discovery total **unknown** until verified; even then say “observed in this approved directory,” never company-wide completeness. Link a paginated, accessible outcome drawer with path, kind, state and reason. Show **Resume capture** for an eligible paused/failed run, using the existing revision and `Capture.resume/3`; on stale revision refresh status and require the user to retry deliberately. Restore the latest run for the selected corpus/connection only through an authorized existing lookup; if no such safe lookup exists, defer cross-session restore rather than infer a run ID from client state.

**Acceptance and ownership.** UI owner: component and LiveView; evidence API owner only if a bounded authorized latest-run lookup proves necessary. With a public synthetic interrupted scan, verify observed-count labels, failure detail, revision-safe resume and eventual verified completion; show partial indexing separately. A changed scope, expired cursor or failed status refresh must clear old controls and explain recovery. Keyboard/reader users must reach status, outcome pages and resume. Root's iteration-13 browser record establishes scripted review → two approvals → eight-file export, but task evaluation stayed `BLOCKED: model_not_selected`; this proposal does not claim real-model quality or 100k/million-file scale. Defer relevance, semantics, publisher races and full MCP/CLI lifecycle to iteration 15.
