# Iteration 14 proposal 12 — responsive density and disclosure

**Recommendation.** Give the company corpus journey one readable vertical order at every width: selected corpus and goal → capture/index state → focused question → named evidence → synthesis/review → separate claim and plan decisions → export/evaluation status. Use existing Phoenix HEEx, `<details>`, and CSS custom properties. Keep the evidence decision reachable without scrolling through unrelated inspection controls; make detailed identities available on demand.

**Direct frozen-source observations.** `company_panel.ex:1313–1340` puts a secondary “Browse captured corpus evidence” action before the saved-workflow guide; the guide then presents seven saved-record tasks (`guide.ex:5–13,334–346`). In `corpus_review.ex:39–98`, “Choose what to inspect” precedes the two evidence panels. The preview and original report sit in equal columns (`:98–235`); CSS stacks them below 65rem (`app.css:288,300`). Original findings show exact snippets, but citation footers lead with opaque source/revision IDs (`corpus_review.ex:464–479`). Capture metadata is disclosed (`:309–336`), while the pipeline’s result rows display lane/relation and a repeated “Inspect exact passage” action without a source title (`:609–635`). The question form has no bound value (`:578–599`). CSS gives corpus cards 1.5rem padding and an unbounded visible `<pre>` (`app.css:276,296`), reduced only below 35rem (`:301–304`). Existing guide disclosures have explicit button state and `aria-controls` (`guide.ex:248–269`). These are markup and rule observations, not measured usability failures.

**Inference.** At narrow widths, stacking a long preview ahead of the original report may bury the decision context. At desktop widths, equal columns may make the operator compare unrelated live preview and sealed analysis as if they share one provenance. Repeated unnamed result actions increase scanning effort. Neither effect was browser-tested here.

**Smallest useful slice.** Promote a compact corpus entry/status and next action in the existing Company guide; place the current question and its selected corpus/goal close together. In the evidence list, lead each row with source title, provisional relation, inclusion state, date/status when available, and a short excerpt; reveal exact byte/hash identities and full parent text through an explicit disclosure. Preserve the existing “additional preview is outside model input” boundary and keep support/contrary/unknown labels provisional. On small screens, prioritize question, run status, and selected evidence before ancillary preview; let long text scroll within its own region without horizontal page overflow. Do not hide human resolution or approval state behind a closed disclosure.

**Acceptance and seams.** Component/CSS checks should verify the same order at narrow and wide widths, keyboard/focus/labels for disclosures and repeated passage actions, and no clipped actions or horizontal page scroll. A packaged public-fixture browser journey should cover an empty/failed replacement query clearing stale evidence, unavailable graph/model setup with a next action, draft retention across ordinary navigation, and exact claim then separate plan approval reaching exported files; distinguish static PASS from task BLOCKED. UI ownership: `CompanyPanel`, `Guide`, `CorpusReview`, LiveView state owner for draft binding, and `app.css`; Root owns shared routing/board. Risk: reordering must not imply preview evidence entered the sealed recommendation. Defer relevance calibration, graph changes, scaling claims, and real-model effectiveness to 15. Root’s iteration-13 records establish a scripted eight-file export and blocked task evaluation, not this proposed UI behavior.
