# Readiness language: distinguish mechanics from meaning

**Direct frozen-source observations.** Retrieval publishes `ready` when capture is verified, every active member has an index, no selected parent is incomplete, no candidate was omitted, and at least one passage was selected. Otherwise it publishes `abstained` (`lib/harness_forge/company/retrieval.ex:446–451,519–576`). The same coverage object always says `semantic_coverage: unknown` and warns that finite search cannot establish company-wide completeness (`:560–563`). The corpus UI prints the raw run state and selected count, then enables synthesis only for `ready`; it already calls relations provisional, but does not explain what `ready` proves (`lib/harness_forge_web/components/company/corpus_review.ex:601–642`). A synthesis abstention displays “The model found insufficient evidence,” while other failures become one generic retry message (`lib/harness_forge_web/live/corpus_review_live.ex:593–605`). Evaluation reason labels separately identify `model_not_selected`, static integrity, and synthetic tasks; the run list displays outcome, reason, and `runtime_qualified` (`lib/harness_forge_web/evaluation_reason.ex:23–36`; `lib/harness_forge_web/live/portal_live.ex:3104–3111`).

**Root-reported evidence.** The iteration 13 handoff records a nonsense question returning `ready` with three provisional candidates, and an exported package with static integrity PASS while representative task evaluation was BLOCKED: `model_not_selected`, `runtime_qualified=false`, `not_dispatched`. These are Root's retained observations, not my execution.

**Inference.** A reader may take “ready” or “Proposed guidance is ready” as evidence that the passages answer the question or that the harness works on tasks. The code only supports a structural claim. Calling the retrieval state “insufficient evidence” in all abstentions would also overstate meaning when capture or indexing is incomplete.

**Smallest useful UI scope.** Keep backend states and admission unchanged. Translate retrieval `ready` to “Evidence gathered for review” with “Capture and index checks passed; relevance and whole-company coverage remain unknown.” Show separate explanations for: incomplete capture/index or omitted context (“Search incomplete—resume/refresh capture and try again”); zero selected passages with complete capture (“No candidate passages found for this question—try clearer terms; absence is unproved”); graph or model setup failure (“Search/model unavailable—check the selected setup, then retry”); and model abstention (“No recommendation saved; inspect the cited scope and ask another question”). Preserve source identity, provisional relations and exact passage inspection. Keep static PASS adjacent to task BLOCKED and `not_dispatched`; never call export an evaluation success.

**Acceptance and seams.** UI/component owner maps only existing run coverage and error codes; LiveView owner keeps failed replacement clearing stale run/stage/claim handles. Verify each state with a public fixture, including incomplete capture, no candidates, graph/model unavailable, model abstention, and failed replacement with no stale approval action. Keyboard and screen-reader status should announce the distinct reason and next action. A packaged browser journey should show separate exact claim and plan approvals, actual export, then static PASS beside task BLOCKED. Defer relevance scoring, semantic abstention, real-model task benefit and scale qualification to iteration 15. Dissent: a label alone cannot make an irrelevant `ready` retrieval safe; the synthesis review must continue treating every candidate as provisional.
