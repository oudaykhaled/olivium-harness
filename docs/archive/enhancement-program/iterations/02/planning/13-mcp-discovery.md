# Proposal 13 — First-party MCP discovery in the Company journey

**Recommendation: defer an MCP portal panel in iteration 02.** The counted UI benefit should be prerequisite-derived Company guidance through the existing approval and package path. MCP discovery is valuable, but a second setup path risks making an unfinished company journey appear complete. The [UX retrospective](../../01/retro/02-ux.md) identifies the more immediate defects: the always-complete source step and a claim-only “awaiting a decision” count beside a proposed plan. Product, trust and QA retrospectives likewise prioritize guided completion and visible blockers ([product](../../01/retro/01-product.md), [trust](../../01/retro/04-trust.md), [quality](../../01/retro/05-quality.md)).

**Observed surface.** `PortalLive` has Company navigation and a four-step workflow banner but no MCP entry (`lib/harness_forge_web/live/portal_live.ex:5,905,980–997`). The router serves the portal at `/` (`lib/harness_forge_web/router.ex:26–32`); `LocalOrigin` dispatches `/mcp` separately (`lib/harness_forge_web/plugs/local_origin.ex:51–52`). Neither serves repository Markdown. The task-oriented [local MCP how-to](../../../../../mcp.md) is linked from `README.md:79` and can be shared from a native installation, but there is no hosted or portal documentation URL to link. `config/runtime.exs:20–21` makes MCP opt-in; `MCP.Auth` also requires a valid environment-referenced bearer (`lib/harness_forge/mcp/auth.ex:10–17,50–67`). An enabled process is therefore not evidence that a client can authenticate.

**Later bounded help candidate.** After Company guidance is validated, add a small “Use this package from an MCP client” disclosure beside the package handoff. Explain the three read-only inspection tools, direct the operator to the packaged local `docs/mcp.md` path, and show only safe states such as disabled, enabled/configuration unverified, or client check passed when actually observed. Never render or log the bearer, infer credential validity from enablement, or claim Codex/Claude compatibility from the synthetic SDK check. Preserve browser sign-in versus MCP access as separate concepts. This follows the staff documentation writer’s task-oriented how-to and source-of-truth guidance, without inventing a docs service.

**Acceptance for a later iteration.** Native and source-checkout operators can find the packaged guide; disabled and missing-bearer states have accurate recovery text; keyboard and narrow-screen use remain clear; no credential value appears in DOM, logs or screenshots. Risk: stale copies of setup prose and misleading “connected” labels. Keep detailed configuration in `docs/mcp.md` and verify links against the actual package layout.
