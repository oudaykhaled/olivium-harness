# Proposal 04 — Company disclosure and section navigation

**Evidence.** `CompanyPanel.render/1` renders `Catalog.setup` and `Plan.builder` together (`company_panel.ex:543–571`). Those components expose seven sections (`catalog.ex:26,99,284`; `plan.ex:46,64,225,256`). The saved native DOM contains repository and project editors, a package form, decisions, and build controls in one scroll (`tmp/enhancement-program/01/browser/company-dom.txt:82–250`). The screenshot reaches only the profile below heading and metrics. This is synthetic evidence, not a novice study. `portal_live.ex:987–991` labels a separate four-stage banner. The information-architecture principle is one task-oriented entry point per section, including return visits.

**Bounded change.** On Company, replace the four-stage banner with a seven-section navigator using existing names. Show each label and saved-record status; expand the next actionable section by default and allow direct opening. Keep others as visible summary rows with counts or a selected record and an “Open” control. Treat goals and milestones as optional context. Keep claim review linked to Evidence; keep exact plan review separate, showing proposal/approval/rejection and revision hash before its decision control. Never infer approval from an expanded section. Build remains separate with current eligibility and export/evaluation/release links.

**Acceptance.** Empty, partial, proposed, rejected, approved, and stale workspaces open the appropriate section while all seven remain reachable by keyboard and narrow-screen scrolling. Switching sections and tabs, opening a different saved plan, and returning preserve unsaved profile, repository, project, and plan form inputs; an explicit save or discard is the only way to lose a draft. Reopening review shows the same selected exact revision and decision state; after a context change it visibly requires a fresh review. The active section has a programmatic heading and focus target; opening via the navigator moves focus there. Summaries distinguish saved state from drafts and never hide pending claim or plan decisions.

**Risks.** Conditional rendering can discard form values or focus, while cached summaries can misstate eligibility. Keep draft state in the LiveComponent and derive status from current saved records on each reload; test both transitions. Do not imply that build or static integrity proves runtime qualification.
