## Finding S02-02 — queued old events can resurrect cleared drafts or records

**Status: resolved. V2 source, unchanged-envelope/remount regressions and the final-artifact reset-first real queued-submit/ack path with saved records were verified.** See the native evidence sections for the exact scope and masked-nonce limit.

- **Severity:** Medium privacy/data-integrity impact in an authenticated local browser workflow; CVSS v3.1 **4.4** (`AV:L/AC:L/PR:L/UI:N/S:U/C:L/I:L/A:N`). This is accidental or deliberate stale-request replay after an explicit erasure boundary, not authentication bypass. The generation is a freshness fence; it need not grant new authority.
- **Affected owner/component:** A handles admission in `CompanyPanel`; A/B serialize event generation in Guide/Catalog/Plan form and button markup; C owns deterministic queue regression tests. Root supplied the exact reset-before-old-event ordering, and this reviewer traced the actual code without running it.
- **Source evidence at discovery:** `CompanyPanel.handle_event/3:84–96` checked only current operator authentication and event shape before dispatch. `company_reset_token` was compared only in `update/2:30–42`. The form `data-company-reset-token` attributes support DOM patching and are not submitted freshness credentials. Change dispatch (`:132–141`) immediately called `capture_draft/3`; save dispatch (`:154–167`) captured before `pinned_input/3`. `capture_draft/3:530–550` accepted old text; `pinned_input/3:553–557` checked only catalogue identity/hash, with no generation test. These line numbers identify the pre-v2 snapshot below.
- **Original reproduction:** Suspend one Portal channel; queue `:company_cache_reset`; then deliver a previously serialized Company form change/submit; resume so reset is handled before the old event. Without the fence, an old change could repopulate a private draft canary. An old new-profile/new-repository submission without a prior expected hash could also create a record after full purge; an unchanged saved-profile hash could still match after selective source purge. Even when domain hashes refused a save, capturing first retained the stale private draft. The client callback cannot erase bytes already serialized into that queued event. Root's corrected native run now verifies rejection for the actual queued browser profile change/submit case.
- **Recommended remediation:** Serialize a mounted-instance/reset generation with each Company form event and state-changing button event; compare it with current server generation **before any capture, selection, dispatch or domain call**. Missing/malformed/stale generations must not retain or reflect submitted private payloads. Preserve the ordinary refresh generation independently. Bind freshness to a unique mounted instance, or use a fresh opaque generation, because a counter reset to zero on every mount can accidentally match retained generation zero after reconnect. Existing string-keyed bounded validation and domain hashes stay in force.
- **Alternative and tradeoff:** Rotate the existing operator session epoch after destructive privacy success. Current event authentication would then reject all queued old-session events, but all tabs would require login and privacy UX text would need correction. A bounded per-view event-generation fence preserves the existing authorized session and is the recommended scope.
- **Required evidence:** Real channel ordering for old change and old submit after reset, no canary in child assigns/rendered/client values or persisted catalogue, plus fresh post-reset events still working and normal same-generation drafts surviving refresh. No main/demo/native purge; use the existing isolated fixture/private harness. Reported immediately to conductor; no product mutation by reviewer.
- **Reviewed v2 correction:** Panel authenticates before raw traversal, requires an exact current root 32-lowercase-hex generation and optional paired empty scalar unused marker, removes validated metadata, then normalizes/shapes/dispatches. Missing/stale/malformed envelopes change only a fixed notice and retain no incoming payload. A fresh cryptographic 128-bit generation is assigned on each mount and privacy reset; ordinary refresh preserves it; invalid authentication clears it; parent-supplied overrides are dropped. An independent source inventory found explicit metadata on all **22** click producer definitions (Guide 5, Catalog 8, Plan 9), exactly one enabled hidden root generation on each of **nine** forms, and propagation through all disclosure/discard/milestone/review helpers. No automatic generation injection/retry is added to JS. This implementation matches the frozen decision and the documented native behavior.
- **Verified focused evidence:** `company-focused-v2-01.log` passes **19 tests, zero failures**, seed 0, exit 0. Raw event maps are captured before reset and replayed unchanged after processing, without fresh generation injection. Negative assertions preserve every child assign except the fixed notice/LiveView change marker, preserve the parent tab, and compare profile/repository/project/plan/artifact/audit snapshots. Real isolated source purge, workspace purge and quarantined restore replay old form envelopes in both initiating and sibling views; generation rotation is explicitly asserted. Old clicks, malformed/missing metadata, valid current controls, ordinary refresh retention and old-mount rejection at numeric zero are covered. Root's separate native run supplies the installed-client suspended-channel/ack evidence below.

## Finding S02-01 — focused browser draft may survive wrapper-only reset

**Status: resolved for observed native focused text/textarea and final-artifact pending-submit lock/ack cases.** The final case also verifies saved-profile rehydration and cleared selected-plan/built-package display. Closure uses actual client value/default observations and recorded database equality, not server-rendered assertions alone; it does not claim a complete native control-type or accessibility matrix.

- **Severity:** Low confidentiality impact for an already authenticated local operator; CVSS v3.1 **3.3** (`AV:L/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N`). This is a privacy-lifetime defect, not approval bypass or remote code execution. It blocks the explicit iteration requirement that purge/restore clear cached drafts.
- **Affected owner/component:** A/B, `CompanyPanel` generation wrapper at `company_panel.ex:864` and the Company browser patch/reset behavior. C's current LiveView tests inspect server assigns/rendered HTML, which cannot observe a focused DOM input's live `value` property.
- **Source evidence at initial review:** The installed Phoenix LiveView **1.2.13** uses `node.id` as its primary DOM key (`deps/phoenix_live_view/assets/js/phoenix_live_view/dom_patch.ts:208`). Its bundled morphdom indexes old descendants globally and `handleNodeAdded` reuses matching keyed descendants under a newly inserted ancestor (`deps/phoenix_live_view/priv/static/phoenix_live_view.esm.js:2194`, `:2210`). Thus changing `company-cache-0` to `company-cache-1` does not necessarily replace fixed-ID inputs such as `company-profile-name`. LiveView's `onBeforeElUpdated` explicitly preserves a focused editable input unless `phx-patch-focused` is present (`dom_patch.ts:474`); `DOM.mergeFocusedInput` excludes the `value` attribute (`dom.ts:637`). The original implementation supplied no reset-specific override.
- **Original reproduction:** A connected Company control retains focus and a private draft while another view triggers reset. Fixed-ID descendant reuse can preserve its live value after a wrapper-only patch. The prior source-purge server test moved the sibling to Evidence and could not establish this focused client case. Root's native proof uses the existing workspace reset signal in the disposable fixture, observes the actual focused control, and tests a later real locked submit; actual purge/restore wiring remains covered by the isolated server tests. This reviewer inspected evidence and did not run a browser.
- **Remediation:** Add narrowly scoped client erasure/forced patch behavior tied to the server-owned reset generation, preserving the ordinary refresh/draft path. Two possible approaches: a reset-only LiveView focused-patch opt-in (small surface, requires proving it does not stay enabled for later ordinary patches), or a bounded Company hook that replaces/resets client form state on generation change (explicit behavior, adds client lifecycle code). Do not weaken event authentication, accept user-selected script/selector targets, or enable forced overwrite on every ordinary refresh. Prove focused input/textarea/checkbox reset and ordinary typing retention using isolated data; no purge/restore against main/demo/native browser workspaces.
- **Reviewed correction:** A/B chose a LiveSocket `dom.onBeforeElUpdated` callback scoped to nine compiled Company form IDs and a valid increasing server reset generation. It maps `form.elements` to incoming authoritative server controls by tag/type/name and checkbox/radio value; it synchronizes values/defaults, checked/defaultChecked, select selections/defaults and clears obsolete controls. It resets both the supplied form and the connected form when LiveView supplies a private locked clone, then stamps the new generation. Catalogue/Plan/Guide forms carry that generation. Same-generation patches do nothing; focus still uses the original compiled allowlist. Root's actual installed LiveView lock/ack observations now support this correction for the documented profile controls.

Both findings were reported promptly and corrected. Their dispositions combine distinct source, isolated server and actual native client evidence; no single server-rendered assertion substitutes for those boundaries.
