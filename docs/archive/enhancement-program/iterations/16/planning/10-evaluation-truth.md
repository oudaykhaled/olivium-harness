# Evaluation truth across the company handoff

The journey can end with a correct export while the operator still lacks evidence that its obligations work in tasks. Iteration 15 produced eight coherent files after an exact corrected claim and a separately approved plan. Its static integrity passed, but the task record was `BLOCKED/model_not_selected/not_dispatched/runtime_qualified=false`; the only synthesis was SCRIPTED (15→16 handoff, “Verification and actual connected outcome”; accepted-evidence01.json, `connected_journey`, `limits`). A “passed” badge without its kind and dispatch state would imply company benefit. The architecture retrospective identifies the missing link as approved obligation → demonstrated behavior; the retrieval retrospective adds that applicability, contrary evidence and justified abstention remain unmeasured.

Two bounded reuse options are available. First, add a compact outcome panel to the existing Company plan/build handoff, using saved artifact, approval, assessment and evaluation/readiness records. This preserves one route and makes the next action visible, but may become dense if every obligation is shown. Second, link from the existing “Evaluate built packages” action to the current Evaluations view with a selected artifact and contextual explanation. That is smaller in Company, but makes the user cross tabs to understand a blocked result. I recommend the first option at summary depth, with a link to detailed evaluation. Reuse `Readiness.for_artifact` and the existing plan binding; do not add an evaluation engine or infer obligation coverage from a passing static check. The curated readiness interface already separates integrity, eligibility, managed runtime, evaluation, applicability, cleanup and release admission, with reason codes and a next action (readiness.ex:19–35, 74–86, 280–357). The Company plan already displays exact plan/artifact bindings and a one-task, one-goal assessment entry (plan.ex:317–423, 766–775).

Acceptance is falsifiable: for the recorded iteration-15 artifact, the summary labels static integrity **PASS** and task evaluation **BLOCKED**, shows model absent and no dispatch, and offers only the existing configuration/evaluation route. It identifies the exact artifact, approved claim and separate approved plan before any assessment action. A selected goal is labelled as one-goal scope; uncovered obligations remain **unknown**, never zero. Switching artifact, plan or corpus clears or recomputes the displayed correspondence; stale identities cannot retain a ready action. Keyboard and screen-reader users can read each status as text, reach its explanation and next link in order, and see focus after navigation. Root should verify those states in the authorised WEB journey and inspect the exact saved record; a scripted model response cannot qualify task behavior.

The interface is read-only explanation. Evaluation authority remains with the existing trusted checks: static integrity and offline smoke do not qualify release, and comparable task runs require matching immutable identities (curated evaluations interface:1–7, 227–245). This slice improves comprehension, not missing model access, semantic coverage, obligation-to-task mapping, or the own-MCP company-context debt.
