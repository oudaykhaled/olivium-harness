# 14 — Prove a bounded corpus-to-review UI slice

**Benefit.** Give an operator one saved project/corpus and one assigned future goal, then a review queue with paginated source metadata, capture/index progress, bounded supporting and conflicting passages, and an explicit coverage/abstention state. A source row opens its pinned passage and parent context on demand. The queue must lead into the existing edit/reject/exact-claim approval, separate plan approval, build/export and assessment journey. A whole-corpus checkbox and a count of citations are insufficient: the present form requires 2–4 checked sources (`source-before/lib/harness_forge_web/components/company/analysis.ex:241–285`), and its “coverage” counts distinct cited sources rather than searched or missing sources (`:430–471`).

Source scopes below use `tmp/enhancement-program/12/source-before/`.

**Evidence and seam.** The current domain takes 2–4 source references, totals at most 32,768 source bytes, and places full bodies into one prompt (`source-before/lib/harness_forge/company/analysis.ex:169–213,257–274`). `Chat.Retrieval` has a useful local lexical/FTS path and exact bounded excerpts, but its `:all` path and top-ranked 12 snippets do not establish project scope or contradiction coverage (`source-before/lib/harness_forge/chat/retrieval.ex:10–23,31–54,107–136`). Reuse its lexical baseline and existing claim/plan/export authority. Root should own shared PortalLive events/state and migration; a UI author should own `components/company/analysis.ex` and focused LiveView checks; a domain author should own bounded corpus membership, cursor metadata, passage/origin and job APIs. The selected Graphiti 0.31.2/Jev dependency belongs behind the separately controlled adapter in the following functionality slice; this UI may display only real stored progress and evidence.

**Acceptance proof.** Use a public synthetic corpus larger than four files, with a saved goal, dated policy, incident, explicit exception, later contradictory decision and unapproved discussion. Freeze expected relevant *and conflicting* source/revision/span sets before implementation. Positive: an authenticated operator chooses the assigned corpus and goal, pages metadata without full bodies, sees honest completed/failed/unindexed counts, opens exact UTF-8 excerpts with status/date/context, corrects and rejects unsafe advice, approves the exact successor and plan, and verifies corrected bytes in actual target exports and the representative rubric. Negative: foreign scope, empty group, changed/uncited source, revoked evidence, missing consent and incomplete scan produce no provider dispatch or current approval; missing critical contrary evidence forces visible abstention. Recovery: resume capture from a checkpoint without duplicate membership; after recapture or failed derivative rebuild, stale rows stay blocked until a newly versioned result is deliberately reviewed. Regression: preserve immutable receipts, current four-source flow, keyboard focus/error announcement, dirty-draft protection, consent/budget and purge fences. Assert rendered behavior and database/artifact effects with machine-readable results; add Playwright keyboard/axe checks where a real browser path exists. Scripted responses prove mechanics only. Record critical-source recall, citation correctness, completion/recovery and bounded query/p95 measurements separately from real-model quality.

**Effort and dissent.** Estimate two UI/domain author-weeks plus root integration and QA, assuming bounded APIs arrive. A cheaper “show more source checkboxes” patch would reduce form friction quickly, but preserves full-body prompting, 100-source arrays and unknown corpus coverage; it does not meet the stated benefit. Conversely, demanding a production million-file graph benchmark before this UI would defer a reviewable operator gain. Keep million-file readiness and real company value explicitly unqualified until measured.
