# Planner 16 — coherent corpus review architecture (proposal)

**Bounded benefit.** An operator chooses one authorised corpus and saved goal, sees paginated capture and coverage, then inspects bounded supporting and conflicting passages before editing, rejecting or approving a recommendation. Its backing contract must serve real scoped data and report incomplete coverage honestly.

**Context.** Today `Company.Analysis` accepts 2–4 source refs and at most 32,768 body bytes (`lib/harness_forge/company/analysis.ex:169–211`); its UI renders assigned sources as checkboxes (`lib/harness_forge_web/components/company/analysis.ex:241–285`). `PortalLive.reload` loads all source DTOs (`lib/harness_forge_web/live/portal_live.ex:937–963`) and `Evidence.list_sources` hydrates revisions (`lib/harness_forge/evidence.ex:51–59,682–690`). `Chat.Retrieval` scans allowed IDs or searches FTS, then scores whole bodies (`lib/harness_forge/chat/retrieval.ex:10–57,94–104`). Exact UTF-8 citation validation and revision pins matter (`lib/harness_forge/evidence.ex:273–289,475–498`; `lib/harness_forge/evidence/origin.ex:30–50`). Graphiti converts empty groups to unfiltered (`research/.../graphiti_core/search/search.py:98–110,155–156`); nonempty server-derived scope must precede that call.

**Decision proposed.** Build a narrow read contract: corpus identity, goal/hash, capture checkpoint/counts, metadata cursor, and passage previews with source/revision/body hash, exact byte span, parent context, effective/capture dates and documentary status. Distinguish eligible, stale, blocked, unscanned and unknown counts; counts are never semantic coverage. Require a versioned server-owned retrieval origin with transitive dependencies including uncited prompt inputs, summaries and new contradictions. Empty scope refuses retrieval/dispatch. Tombstoned sources remain unservable through failed Graphiti rebuild. The UI receives no whole bodies. Keep exact claim/plan approvals, deterministic export, consent and per-attempt metering in Elixir; Graphiti 0.31.2/Jev stays behind a bounded Python adapter, with FTS5 as baseline.

**Dependency order and ownership.** Root owns shared schema/migration, privacy fence and integration contract. Writer A owns membership, cursor, passage/origin API and tests. Writer B owns stateless corpus/goal, progress, conflict and review presentation/tests. Root connects `PortalLive`/`CompanyPanel` events, generation guards and verification. Alternative three-writer contract: root owns migration/Portal; A owns domain plus Graphiti adapter; B owns UI. Prefer the first this round because adapter/backend/consent qualification could swamp the UI benefit; reserve adapter implementation for the following functionality slice. Target ≤400 net lines per PR, schema/API before UI, then root integration. Blast radius: source reads, review authority, privacy and dispatch.

**Acceptance.** Positive: on a larger public synthetic corpus, select corpus plus goal; page metadata; see bounded supporting and contrary passages with uncertainty; correct/reject, approve exact claim and plan, inspect corrected bytes in actual target exports, then record representative assessment. Negative: foreign/empty scope, stale revision, incomplete scan, unavailable model and unconsented stage yield explicit refusal/abstention. Recovery: interrupted capture resumes from checkpoint; new contrary evidence invalidates origin; revoked source disappears even when graph cleanup fails. Measure critical misses, citation accuracy, review recovery and latency; fixture responses prove mechanics only. Dissent: UI over the four-document API preserves the bottleneck. Graphiti installation now may be necessary if the bounded contract otherwise fails, but increases backend/operational qualification work and requires a connected slice.
