# 02 — Novice scope and evidence review

**Recommendation.** Make one saved project’s authorised corpus and one saved future goal the entry to a bounded **evidence review workspace**. The novice sees a plain-language scope summary first: captured, pending, failed, excluded, stale, and unknown counts, plus the goal and last completed checkpoint. A page of source metadata confirms what the corpus contains without rendering a million checkboxes. After a resumable analysis produces one recommendation, show its proposed action, goal rationale, support, contrary evidence and missing coverage together. Each evidence row opens a bounded passage with parent context, status and historical dates. Exact revision, hash and UTF-8 span remain in a disclosure. The reviewer can edit or reject, resolve conflicts, then navigate to exact claim and separate plan approval, export and assessment.

**Why this slice.** The frozen Company guide derives its progress from saved records but counts assigned current sources and eligible claims in memory (`guide.ex:17–85,270–337`). Project setup renders every source and goal as a checkbox (`catalog.ex:350–455,517–559`); the analysis form asks for 2–4 checked sources, displays their full revision details, and reports only structural citation count (`analysis.ex:195–300,430–543`). Domain admission also requires 2–4 source refs (`company/analysis.ex:169–180`). The focused LiveView test proves this small-fixture path through corrected export (`company_analysis_test.exs:51–210`); large-corpus usability is unproved. Assessment already shows staged progress and linked errors (`assessment.ex:100–153`), yet its successor action can be hidden inside identity details (`assessment.ex:529–581`; WEB-11-01). Keep recovery actions visible and focusable rather than burying them with hashes.

**Working seam and ownership.** UI owner: Company guide/catalog/analysis components, CompanyPanel state and focused LiveView tests. Root owns shared PortalLive and schema/router integration. Domain owner supplies server-derived nonempty access scope; relational corpus membership and keyset metadata pages; bounded capture checkpoint/count API; a versioned retrieval origin with support, conflict, unknown and transitive dependencies; lazy passage hydration only after access/revision checks. Reuse SQLite/FTS5 and the pinned Graphiti/Jev adapter under Elixir consent, budget, approval and purge authority. Missing model or backend remains an honest unavailable state. Tombstones must block rows and passages through failed summary rebuilds.

**Acceptance.** Positive: with a public synthetic corpus above the current manual limit, a novice selects project and goal, resumes capture, sees page/count status, opens supporting and conflicting passages, corrects and approves an exact recommendation and plan, and verifies corrected bytes in exported files and a representative rubric. Negative: foreign scope, stale revision, uncaptured source, missing conflict, empty group, or revoked derivative never appears as actionable evidence; incomplete coverage cannot read as “complete.” Recovery: interruption resumes at the same checkpoint, changing evidence invalidates the review with visible next action and focus, and a failed rebuild keeps affected evidence blocked.

**Alternative and effort.** A paginated source picker is cheaper (roughly 2–3 engineer days) but preserves manual triage. This slice is medium-high, roughly 8–12 engineer days plus benchmark and UX validation. The 51 offline mocked Graphiti passes and scripted provider flow establish neither semantic quality nor million-file performance.
