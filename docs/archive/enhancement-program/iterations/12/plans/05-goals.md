# 05 — Saved future goal in the company corpus journey

**User benefit.** An operator selects one saved future goal and one authorised project corpus, sees what is in scope and missing, then starts a bounded evidence request. A changed goal or project membership leads to a visible recovery choice. This makes future intent part of corpus analysis rather than a separate rule-writing detour. The UI must ship against a real server-owned scope and bounded result; a decorative corpus picker would not remove the manual 2–4-source bottleneck.

**Observed seams.** `Goals.list_goals/0` returns every workspace goal and `content_hash/1` pins title, owner and acceptance (`goals.ex:7–17`); `add_goal/1` only creates (`:19–36`). The Goals tab creates/displays goals (`portal_live.ex:2321–2353`), while a separate Evidence form proposes a goal-only rule with a generation token (`:395–429,1248–1289,1904–1964`). Company projects explicitly assign goal and source IDs (`company_panel.ex:345–365`; `company/catalog.ex:429–444`). Current analysis unions profile/project assignments, checks current goal hash and source scope server-side, and admits only 2–4 whole source revisions/32 KiB (`company/analysis.ex:170–226`). Its UI shows all assigned source checkboxes, one goal, unknown coverage and a pinned hash (`company/analysis.ex` UI `:179–320`). `Analysis.capture/5` clears pins on project change (`company/analysis.ex` UI `:19–49`), but the selection lifecycle needs a readable stale-goal path. Existing tests cover unchecked entry, project-scoped choices and source recapture refusal (`company_analysis_test.exs:49–80,331–354`); builder tests preserve catalogue drafts across tab/refresh (`company_builder_test.exs:740–810`).

**Proposed slice and ownership.** Present a project/corpus summary with server-reported membership, captured/current/stale/blocked counts and explicit exclusions; select one assigned saved goal with owner and acceptance visible. Show a bounded preview of relevant supporting and contrary passages, plus coverage gaps, before committing analysis. Use paginated metadata and lazy passage hydration; no whole-corpus goal/source checklist or full bodies in LiveView assigns. The root owns shared Portal events, route/state and any migration; a domain writer owns scoped membership/query and versioned retrieval-origin contracts; a UI writer owns CompanyPanel/Analysis components and accessible focus/status handling. This is an estimated 4–6 engineering days plus fixture-backed validation, contingent on the necessary bounded capture/retrieval seam.

**Acceptance.** Positive: a saved goal assigned to an authorised project appears with its exact content hash; a bounded corpus request shows relevant and contradictory evidence, missing coverage, and a recommendation that still requires exact claim and separate plan approval before corrected export. Negative: an unassigned/foreign goal or empty group scope refuses before retrieval or model dispatch; stale source, goal or membership never silently repins. Recovery: after goal or membership change, preserve the unsent draft, identify the changed item, require explicit reselect and new origin, and keep old decisions historical. Test keyboard focus and error announcement after refusal, and duplicate/late event generations. Graphiti 0.31.2/Jev remains a bounded Python dependency; Elixir/revisioned SQLite/FTS5 owns access, provenance, consent, budget, privacy and export. No model, paid pilot or million-file performance is established by the offline spike.

**Dissent.** A goal-only shortcut is smaller and fits existing Portal code, but leaves manual document selection intact. A corpus-wide auto-select would reduce clicks but hide exclusions and could dispatch unconsented material. Select explicit project membership plus one pinned goal, with server-side scope and honest coverage.
