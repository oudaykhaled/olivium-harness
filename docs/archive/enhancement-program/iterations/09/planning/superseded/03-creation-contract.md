# 03 — Creation-time selected-goal coverage

**Benefit:** Every persisted proposed plan accounts for each selected goal with a reviewable milestone, so plan lists and successor histories cannot contain a revision that silently omits a declared goal. This is a stronger invariant than approval-only coverage, but it costs partial-draft persistence.

**Context.** `Company.create_plan/1` validates, resolves references, inserts an immutable revision, then appends `company.plan_proposed` in one transaction ([company.ex:72–95](../../../../../../lib/harness_forge/company.ex)); `Validation.plan/1` defaults missing milestones to `[]` and currently checks only that milestone goal IDs belong to selected goals ([validation.ex:37–63,79–95](../../../../../../lib/harness_forge/company/validation.ex)). The existing test creates and approves that empty case ([company_test.exs:400–406](../../../../../../test/harness_forge/company_test.exs)). Malformed/unknown milestone goal refs already fail at validation or resolve; do not invent a new parser error. Rejection remains permitted via `approval_eligible(_, "reject")`, while approval rechecks eligibility ([company.ex:111–133,328–346](../../../../../../lib/harness_forge/company.ex)).

**Decision candidate.** In `Validation.plan/1`, after structural milestone validation and before `Repo.insert`, require the union of milestone `goal_ids` to equal selected `goal_ids`. Preserve the existing `:invalid_input` boundary unless the API error vocabulary is deliberately extended. Empty selected goals remain valid with empty milestones. This checks declared accounting, not acceptance quality, company policy completeness or real-model outcomes.

**Acceptance.** Positive: two selected goals, each referenced by a structurally valid milestone with nonblank acceptance/evaluation text, create a proposed revision; exact-hash approval succeeds. Negative: one selected goal omitted, including duplicate references to the other, returns `{:error, :invalid_input}`; plan and proposal-audit counts do not rise, and approval is impossible. Edge: malformed or out-of-scope goal refs still fail; rejected revisions can still be rejected when valid; an approved ancestor remains byte-identical/buildable after a valid successor is created, and a superseded proposed revision still cannot gain approval ([company_test.exs:143–157](../../../../../../test/harness_forge/company_test.exs)).

**Cost and alternative.** One Company/Validation author plus focused Company tests, roughly half a day; no migration. Approval-time gating preserves incomplete persisted drafts and avoids revision churn. Creation-time gating blocks them: `Company` exposes create/supersede, not update, so partial authors must retain local form state until complete. Choose this only if reviewable proposed records must already be complete. A saved incomplete plan accepted after this change, or a rejected creation that leaves a proposal/audit row, falsifies the contract.
