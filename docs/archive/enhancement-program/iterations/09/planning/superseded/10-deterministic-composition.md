# Deterministic repository dependency admission

**Recommendation:** At approval of an exact company-plan revision, require every selected repository’s *direct* catalogue dependencies to be selected in that plan. Return a stable, bounded list of missing `dependent identity → dependency identity` pairs for correction. This is a composition check, not a claim that policies are complete or coherent.

**Evidence.** Repository writes verify dependency IDs exist and forbid self-dependency, but `Company.resolve/1` checks selected repositories against project membership without checking dependency closure (`lib/harness_forge/company.ex:204`, `lib/harness_forge/company.ex:234`). `Company.approval_eligible/2` checks the revision and current snapshot, so it is the narrow admission point (`lib/harness_forge/company.ex:110`, `lib/harness_forge/company.ex:328`). `build_inputs/1` reduces selected repositories to identities; the compiler records those in scope and hashes deterministic output, while native guidance sorts rules by ID (`lib/harness_forge/company.ex:138`, `lib/harness_forge/harnesses.ex:82`, `lib/harness_forge/compiler.ex:78`, `lib/harness_forge/adapters/opencode.ex:261`). The synthetic acceptance fixture selects both `orders` and its `identity` dependency, so its green result does not test omission (`test/harness_forge/company_acceptance_test.exs:48`, `test/harness_forge/company_acceptance_test.exs:99`). Current milestone DAG validation already covers unknown/cyclic milestone edges; this proposal does not duplicate it (`lib/harness_forge/company/validation.ex:79`).

**Contract.** Reuse the pinned snapshot and approval transaction. Sort missing pairs by opaque identities; return at most 100 pairs plus total count. Never infer repositories from free text, auto-add them, or compile a refused plan. Preserve exact claim decisions, ancestor approvals, immutable artifact digests and fresh-directory export.

- Positive: `orders` plus `identity` approves the exact eligible revision and builds byte-identically on retry.
- Negative: `orders` alone, when its declared dependency is `identity`, refuses approval with that pair and creates no plan decision, audit event, binding or artifact.
- Edge: a catalogue dependency edit triggers existing stale-snapshot refusal; a new incomplete successor leaves its approved ancestor unchanged. A dependency outside project scope is reported, never silently added.

**Trade-off and size.** Approval-time checking keeps partial drafts; creation-time checking catches errors earlier but restricts authoring. Expect one Company helper, one caller error presentation and focused Company/Harnesses tests, about a day including regression review. Falsifier: a selected dependent can still be approved without its declared dependency, or pair ordering varies with input order. This detects declared graph omissions only; semantic rule conflicts and real-company/model quality remain unproven.
