# 08 proposal — package-name recovery at the build operation

**Problem and evidence.** A rejected package name reaches `PortalLive.handle_event("build")` ([source](../../../../../lib/harness_forge_web/live/portal_live.ex#L425)). The compiler returns `invalid_harness`, whose bounded details identify `$.metadata.name` ([contract](../../../../../lib/harness_forge/contracts.ex#L323)); the schema requires a lowercase letter followed by lowercase letters, digits, `_` or `-`, at most 64 characters ([schema](../../../../../priv/schemas/harness-v1alpha1.json#L20)). The LiveView sends other contract errors through `connector_error/1`, whose fallback tells the operator to inspect a provider import ([source](../../../../../lib/harness_forge_web/live/portal_live.ex#L1258)). This is a confirmed wrong recovery instruction. The current build form also renders fixed default values ([source](../../../../../lib/harness_forge_web/live/portal_live.ex#L2008)); draft retention needs an explicit check.

**Decision and benefit.** Give the build operation fixed, name-specific correction when its validated error details identify `$.metadata.name`. Preserve the submitted build draft for correction and route generic invalid specifications to safe build advice. Reuse the existing `#error` alert and `#notice` status; avoid a new notice framework. Keep raw validator details and rejected names out of notice copy. This improves the next action without changing compile admission or immutable artifact identity.

**Acceptance.** Positive: an invalid name produces a keyboard-readable correction with the allowed pattern and length, retains the submitted name/version/runtime draft, and creates no artifact or build audit entry. Negative: an `invalid_harness` error on a different field gets safe build advice; connector errors keep their own remedy; no raw details render. Edge: correcting the name and submitting again produces the existing success notice and artifact, with the previous build error gone. Repeated failures replace the earlier build error, rather than accumulating contradictory notices. Verify at 320/390 CSS pixels and actual 200% zoom; fit is not a comprehension study.

**Expected ownership and checks.** UI author: `portal_live.ex` and focused LiveView tests in `test/harness_forge_web/`; root schedules Mix and native browser verification. Schema/compiler stay unchanged. An unrelated asynchronous operation may still combine flash states; a general operation-owned notice model is broader work, with more cross-flow risk.

**Strongest alternative.** Goals-to-Evidence continuation would help users advance from a saved goal, but needs new navigation/focus and unperformed human comprehension evidence. The 4/5 target in prior reports is a proposal, not a measured result. Neither path establishes company/model fitness, portable authority, all connectors, or full WCAG conformance.
