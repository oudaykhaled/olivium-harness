# Independent retrospective 02 — UX

**Verdict: helpful for controlled company-package construction; not yet a reliable, complete self-service company harness journey.** Iteration 01 adds a useful inspection surface, not an operator-facing completion flow. The three MCP tools search an authored catalogue, inspect exact-plan readiness, and inspect package integrity/current eligibility (`lib/harness_forge/mcp/tools.ex:31,200,248`). They neither supply native guidance content nor perform setup, approval, build, or execution. Their explicit `qualification: not_assessed_by_this_tool` and unavailable portable approval verification are valuable boundaries, not evidence of company effectiveness.

The accepted manifest and `verification.md` record 388 passing tests, 15 existing Docker skips, and 44 successful official-SDK checks against protocol 2025-11-25. These support scoped implementation reliability. They do not establish real-model quality, current Codex/Claude interoperability, or a first-time operator's ability to finish. I inspected the saved `browser/company-dom.txt`, actual `company-before-ux.png`, portal/components, and CSS; I did not run a user study, interaction session, or accessibility audit.

The screenshot provides an orderly visual hierarchy, a persistent navigation rail, and recognizable Company selection. However, the first viewport reaches only the beginning of the company profile, after substantial heading, metrics, and workflow space. The DOM then exposes seven setup sections, catalogue editing/search, project membership, claim approval, target limits, optional milestones, plan decisions, and build/export handoffs. My cognitive-load assessment is an inference from that structure: a newcomer must retain dependencies and translate several distinct approval states while navigating a long page. Helpful explanations exist, but reading them is currently the principal navigation mechanism.

Ranked gaps and acceptance criteria:

1. **Progress indicators can misdirect the next action.** The banner always styles “Connect sources” complete and presents four stages (`portal_live.ex:987`), while Company has seven. More concretely, the saved DOM says “AWAITING A DECISION 0” despite a proposed 0.2.0 plan: the metric counts claims only (`portal_live.ex:980`). Acceptance: explicitly distinguish pending claim and plan decisions; derive company progress from saved prerequisites; provide an actionable next step for empty, partially configured, proposed, approved, and stale-plan states. An empty workspace must never announce source completion.

2. **Form recovery requires too much diagnosis.** Every Company section renders together (`company_panel.ex:543`), and the fallback rejection asks operators to check required fields, memberships, claims, and dependencies collectively (`company_panel.ex:518`). Existing labels, fieldsets, status/alert roles, and focus styling are useful foundations, not proof of accessibility compliance (`catalog.ex:46`; `company_panel.ex:534`; `app.css:16`). Acceptance: identify the affected field or selected record, explain one corrective action, preserve entered values, and provide a keyboard-reachable error summary. Show the active task prominently and let operators revisit completed sections without concealing exact-revision review.

3. **A built package has no demonstrated company outcome.** The UI correctly states that build, export, evaluation, and release are separate (`company/plan.ex:256,343`), but target selection and turn/time fields can still suggest an executable journey. Managed execution, selected live connector scopes, and real-company qualification remain unverified or unavailable in the accepted evidence. Acceptance: show independent build/export/runtime/evaluation states and precise blockers; reserve qualification for a recorded evaluation tied to the exact digest, target version, and acceptance evidence.

Iteration 02 should be bounded to the existing Company surface: replace its misleading progress summary with prerequisite-derived navigation, prioritize one next action, progressively disclose completed setup, and improve validation recovery. Keep claim and plan decisions separate. Verify empty/partial/stale paths plus keyboard and narrow-viewport behavior; capture comparable screenshots. Do not count cosmetic polish as completed onboarding.

The next functional need is a supported isolated evaluation path with an availability preflight and digest-bound outcome evidence. Start with a reproducible synthetic company acceptance case; a later explicitly authorized company pilot must establish practical usefulness. UI guidance alone cannot close that reliability gap.
