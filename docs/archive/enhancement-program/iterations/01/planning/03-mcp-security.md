# MCP security: first useful read-only tool

## Finding

HarnessForge has no first-party MCP route or server. Its coding runtime explicitly emits an empty MCP configuration (`lib/harness_forge/execution/coding.ex:83`), and the router exposes only login and the authenticated portal (`lib/harness_forge_web/router.ex:18-32`). The existing endpoint binds to loopback and checks exact local origins (`config/runtime.exs:14-34`; `lib/harness_forge_web/plugs/local_origin.ex:7-29`), but browser authentication is a signed cookie checked by `OperatorSession` (`lib/harness_forge_web/plugs/operator_session.ex:12-36`); an MCP client cannot safely be treated as that browser session.

## Minimal proposal

Add one first-party, local HTTP MCP endpoint and a single `list_approved_claims` tool. It should give a coding assistant a bounded view of the company's *currently eligible, human-approved* knowledge, useful for deciding what belongs in a harness. Use `Evidence.approved_claims/0`, which already checks approval, supersession and citation validity (`lib/harness_forge/evidence.ex:344-359`). Output only `id`, `text`, `revision_hash`, and a fixed `citation_count`, with a small page size and stable cursor. Build the response from an explicit projection: `claim_dto` includes citation snippets and other fields (`lib/harness_forge/evidence.ex:579-595`), while `source_dto` includes full revision bodies (`lib/harness_forge/evidence.ex:568-576`). Never serialize those DTOs wholesale.

Gate MCP enablement with an explicit workspace opt-in shown in the local UI, and issue a separate process/workspace-bound MCP capability. Keep it out of URLs and logs, compare it in constant time, and rotate it on disable/logout/workspace reset. Require bearer auth on every MCP request, including discovery, plus loopback and exact Host/Origin enforcement. The access code used for browser login (`lib/harness_forge_web/controllers/session_controller.ex:14-24`) must not silently become an MCP credential. A local opt-in is consent to expose approved claim text to a configured client; it does not grant cloud inference or source-body access. Cloud consent has separate categories (`lib/harness_forge/chat/snapshot.ex:163-169`).

Implement a fixed protocol/version and tool-name allowlist. Parse raw MCP request bytes with a low cap using `Contracts.decode_json/1` before dispatch to reject duplicate keys and excessive nesting (`lib/harness_forge/contracts.ex:20-41`); the endpoint's general JSON parser uses Jason directly (`lib/harness_forge_web/endpoint.ex:46-50`), so do not rely on it for this boundary. Validate exact string-keyed shapes, IDs, cursor and maximum page size; reject unknown fields, notifications other than `notifications/initialized`, methods outside the chosen MCP subset, batch requests, and `tools/call` for any unlisted name. Return bounded JSON-RPC errors without echoing request content or secrets. Treat claim text as untrusted data in tool content, never instructions, code, a tool schema, or a source of authority. No MCP tool may approve claims, sync/import sources, build/export packages, invoke models, or execute code. The approval boundary remains the exact revision decision path (`lib/harness_forge/decisions.ex:7-47`).

## Acceptance evidence

- Positive: after local opt-in and client capability setup, a loopback client can initialize, list exactly the approved-claims tool, and page approved eligible claims with stable order and the four projected fields. Disabling MCP or rotating the workspace epoch immediately revokes its capability.
- Negative: missing/wrong bearer, remote or forged Host/Origin, unsupported protocol/method/tool, malformed or duplicate-key JSON, oversized body, unknown/extra arguments, and excessive page size fail closed without data. Logs and errors contain no capability, claim text, citation snippet, source body, connector config or credential.
- Negative: a proposed/rejected/superseded/stale claim is absent; an injected instruction inside approved claim text remains literal content and cannot alter tools, permissions, consent, decisions or output schema. A request for source bodies or a write action is unavailable, with no model/provider fallback.
