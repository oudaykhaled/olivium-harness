# Operability: recoverable outcomes and safe MCP failures

**Priority: P1, after the first read-only MCP boundary is chosen.** A company operator needs to know whether a queued sync, proposal, or evaluation actually finished, why it stopped, and the safe next action. Today `Jobs.Operation` has one attempt, broadcasts a free-form summary, and cancels failures ([operation.ex:1-27](../../../../../../lib/harness_forge/jobs/operation.ex#L1-L27)); `PortalLive` displays every completion as an information flash ([portal_live.ex:372-373](../../../../../../lib/harness_forge_web/live/portal_live.ex#L372-L373)). A refresh loses that summary. The separate sync worker retries unreadable local files but intentionally cancels provider failures for explicit resubmission ([sync.ex:3-25](../../../../../../lib/harness_forge/jobs/sync.ex#L3-L25)). Startup cancels uncertain executing jobs before Oban starts and records only an aggregate interruption count ([startup_gate.ex:31-49](../../../../../../lib/harness_forge/startup_gate.ex#L31-L49)).

Add a bounded, workspace-scoped **operation status** view keyed by persisted Oban job ID, with a small companion status record holding only safe outcome codes. Enqueue should return the ID to the portal; show `queued`, `running`, `succeeded`, `stopped`, or `interrupted`, the action and target ID, completion time, and one fixed recovery instruction. Map known codes (rate limit, unavailable provider, stale evidence, missing local runtime, workspace mismatch) to explicit guidance. Unknown exceptions become `operation_failed` with a correlation ID. Treat a cancelled job as stopped, never as success. On refresh, reload recent statuses; `StartupGate` must persist an interruption reason when converting stale executing rows so the UI can distinguish them from ordinary cancellations. Keep the last committed sync cursor and require another user request after a provider error. Existing audit events already whitelist detail keys and redact values ([audit.ex:6-44](../../../../../../lib/harness_forge/audit.ex#L6-L44)); add a fixed `code` field and record only action, status, IDs and code, with a documented retention bound. Do not store raw exception terms in UI status or audit details.

Add a structured readiness result for the same local workspace: storage/recovery, queue availability, configured model/runtime availability, and MCP availability, each `ready`, `blocked`, or `unavailable` with fixed reason codes and a timestamp. Readiness is diagnostic, not a claim that a real model, connector credential, or coding runtime was exercised. The current telemetry module defines Phoenix, database and VM metrics but no operation or MCP outcome metric ([telemetry.ex:22-83](../../../../../../lib/harness_forge_web/telemetry.ex#L22-L83)); emit low-cardinality counts and durations tagged only by fixed action/outcome/code. Do not put source names, prompts, paths, tokens, URLs or workspace IDs in metrics.

For the proposed `/mcp` endpoint (none exists in the current router, [router.ex:18-32](../../../../../../lib/harness_forge_web/router.ex#L18-L32)), centralize an error mapper around the existing safe error contract ([error.ex:1-14](../../../../../../lib/harness_forge/contracts/error.ex#L1-L14)). Return protocol-valid JSON-RPC errors for malformed input, unsupported version/method, invalid arguments, unauthenticated requests, and internal failure; retain the valid request ID only when safely parsed. Use fixed messages, bounded code-only data, and a generated correlation ID. HTTP status and notification behavior must follow the selected MCP revision; never echo raw request bytes, provider bodies, exception messages, or authorization headers. Keep MCP errors distinct from tool-result business blockers. Connector HTTP handling already suppresses provider bodies and exceptions ([common.ex:134-154](../../../../../../lib/harness_forge/connectors/common.ex#L134-L154)); preserve that boundary in logs too.

**Acceptance:** A synthetic failing and successful job show different persistent statuses after refresh; a restart marks uncertain executing work interrupted; rate limits show explicit manual retry guidance without an automatic retry; readiness reports missing runtime as unavailable. Send malformed, unauthorized, unsupported, and throwing MCP requests through the actual local HTTP path and assert bounded protocol responses, request-ID rules, and no secret/body/path leakage from response, audit, or captured logs. Verify fixed-cardinality telemetry and `mix test`. These fixture checks do not establish live provider or broad MCP-client compatibility.
