## Goal-origin basis v1: compatibility and authority contract

1. **Storage and discrimination.** Add nullable `basis` map column to `evidence_claims`, default SQL NULL, plus Ecto field. Migration up uses `alter table(:evidence_claims) do; add :basis, :map, null: true; end` (SQLite nullable TEXT/JSON representation via the existing Ecto adapter), without a default/backfill/index/table. No existing row is rewritten; existing immutable triggers continue covering the entire row. Preserve legacy public DTO shape by dropping `basis` when null in claim DTO construction; do not change generic Store.dto or other records. Missing/null basis means the unchanged citation-origin contract and requires valid nonempty citations. The only non-null accepted shape is exactly `{"version":1,"kind":"goal","goal_id":UUID,"goal_content_hash":lowercase_SHA256}`; reject additional/unknown keys, versions/kinds, malformed IDs/hashes, missing fields and mixed nonempty citations. Goal claims store `citations: []`. No fallback from malformed goal basis to cited origin.
2. **Exact hashes.** Source claims retain the existing hash input, encoding and hash calculation byte-for-byte; never add a null basis key to that calculation. Goal content hash is the existing Company expression: `Contracts.digest(Map.take(Store.dto(goal), ~w(id title owner acceptance)))`. Reuse it through one public Goals helper if needed, retaining existing output exactly. New goal claim hash is `Contracts.digest(%{"kind" => "goal-origin-claim", "version" => 1, "text" => trimmed_text, "basis" => exact_basis})`. Goal ID belongs to the currently scoped workspace through the goal lookup, not a client-supplied workspace field. Existing goal immutability remains; changed-goal cases are adversarial drift fixtures, not a new goal-edit feature.
3. **One authoritative claim validation path.** Evidence owns origin validation and exposes it to Decisions and Company. On proposal and decision, resolve the current workspace goal, match content hash and validate the immutable claim hash. Source-origin validation keeps current citation behavior. Approval remains the existing append-only `Decisions.decide/2` with actor and expected exact revision hash; the separate user action approving the rule covers its pinned basis. There is no second basis approval record. Proposed, rejected or superseded claims cannot become eligible; restored decisions are cleared. New proposal and decision validation occur inside their transaction before insert, respecting the existing privacy/write fence. Audits contain safe identifiers/hashes, never goal/rule bodies.
4. **Typed lineage.** A successor may not change origin type: citation→goal and goal→citation supersession are rejected. This prevents converting cited ancestry into apparently independent intent. Existing source-family purge remains intact. A genuinely new goal-origin family has no source lineage; source purge retains it unless its plan has a separate affected source dependency. Goal-to-goal successors are separately approved exact revisions and invalidate the prior claim as usual. No automatic text conversion/import or approval exists.
5. **Plan scope.** At plan creation, approval and each `Company.build_inputs/1`, resolve the goal claim through the shared validator and additionally require its goal in the plan's selected goal IDs and allowed profile/project scope. Pin the existing exact claim refs and canonical goal hashes in the existing snapshot. No plan schema/hash version change is needed: a goal claim's revision hash binds basis and text; the snapshot already binds the selected goal. Legacy source-only payload/snapshot/hash values remain identical. A goal alone remains contextual intent and never creates or approves a rule.
6. **Publication/admission.** Planned build retains outermost-transaction requirement, purge synchronization, durable prebinding and repeated in-transaction unchanged-plan checks before publication. Map an admitted goal rule to existing `goal_id` and empty evidence; source rules remain unchanged. The source-only direct `Harnesses.build/1` refuses with `:goal_claim_requires_plan` if its current approved claim set contains a goal-origin claim; it must neither include it without a plan nor silently omit an approved rule. `Harnesses.eligible/1` must require at least one current exact valid plan binding for any artifact containing a goal-origin rule (detected when EITHER artifact rule goal_id is non-null OR its current typed claim is goal-origin; require agreement between rule origin/goal_id and current typed basis and refuse sanitized/contradictory provenance); the legacy empty-binding allowance cannot admit it. Reconstruct and compare the complete expected artifact using the existing valid-binding path. No missing/deleted/invalid binding becomes legacy authority. Source-only legacy behavior remains unchanged. Export and release continue through this authoritative eligibility path; no changes to release task qualification or runtime validation are selected.
7. **Lifetime and privacy.** Current goal scope/hash, exact claim/plan approvals and valid bindings are checked afresh at admission. Historical artifacts/decisions are evidence, never substituted for current authority. All existing privacy fences, connection consent withdrawal, workspace quarantine and stale-event checks remain. Selective source purge follows typed source lineage; workspace purge deletes all claims/bases via the existing claim table. Backup keeps immutable artifact bytes; restore clears claim and plan decisions, rewrites workspace rows under existing quarantine, and keeps historical hashes/goal IDs unchanged. Test pre-migration backups and new goal-bearing backups. No new table requires inventory expansion: Snapshot workspace/immutable lists and Purge immutable/content lists already contain evidence_claims and must remain unchanged. Source purge traverses existing cited families and Company source/claim dependencies; type-stable supersession means no extra goal→source edge is invented. Root changes privacy source only if the required tests expose an actual missing lifecycle edge, and records the exact correction before editing. Old backups without the column restore through existing quarantine SQL; normal startup migration adds the nullable column before Ecto claim access. New backups carry basis in the existing claim row; workspace-ID rewriting and decision clearing already cover it.
8. **Compatibility/rollback.** Frozen v1alpha1 schema, compiler/template identity and artifact bytes remain unchanged for identical source-only input. No historical package is recompiled or rewritten. The additive column is the only migration. Root verifies legacy row/hash/trigger preservation and migration from a pre05 database. Rollback must not discard goal data: down migration first checks `SELECT count(*) FROM evidence_claims WHERE basis IS NOT NULL` across all workspaces and raises without dropping anything when nonzero; when zero it removes only the additive column using adapter-supported DDL while verifying retained triggers; retain the migrated database and backup. Do not run old binaries against goal-bearing data as a supported compatibility claim. A copied pre05 database/release is the rollback baseline; newer workspace records are retained for recovery rather than silently deleted.

Fixed new errors should distinguish invalid basis (`:invalid_claim_basis`), stale/unavailable goal (`:stale_goal_basis`, generic foreign/missing refusal without foreign metadata), origin-changing supersession (`:claim_origin_change`), missing selected goal (`:goal_not_selected`) and direct-build refusal (`:goal_claim_requires_plan`). Existing higher-priority privacy/workspace errors retain priority. Authors may map internal lookup failures to these fixed public reasons; unknown input must fail closed. No dynamically atomized input, private source bodies, route endpoints or transferable approval assertions enter errors.

## Alternatives and consequences

- **Selected exact goal basis:** highest direct representability value for the blocked operator job; reuses compiler schema and existing approval/plan mechanisms. Cost: cross-cutting admission, privacy and migration checks. The nullable column avoids another authority store; explicit type-stable families simplify source provenance. Requires two approvals already present in the product, rule then plan.
- **Declared conflicts (04–06):** valuable prevention of known contradictions; requires declarations, winner semantics and a new invalidation lifecycle. Planner04's silent loser exclusion conflicts with exact approved-plan behavior; planner05/06 successor-only direction is safer. Defer the whole separate unit. Undeclared conflicts and completeness remain unresolved.
- **Task route snapshot (07–09,14):** concrete failure/fallback and identity reliability concern; benefits future qualification. Broader execution/recorded-identity/cleanup and Docker evidence burden, and14's apparent Coding-only scope does not resolve Evaluations' separately computed profile. Defer without weakening03 abstention or accepting silent fallback as safe.
- **Selected-plan drift report (12):** smaller, useful recovery feature with no new approval authority; would identify why a current plan blocks but still leaves intended uncited policy unrepresentable. Defer as a distinct candidate, not bundled into goal errors.
- **Separate goal-rule table or basis decision:** stronger structural separation but duplicates exact claim revisions/decisions and expands purge/restore tables. Reject for this unit. **Implicit goal authority, fabricated citations or rewriting legacy hashes:** reject because they violate explicit approval or history.
