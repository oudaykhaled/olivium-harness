# 07 proposal: validated route at task admission

**Finding.** `Evaluations.create/2` persists a task identity through `applicability_identity/2` before dispatch (`lib/harness_forge/evaluations.ex:391-416`); that calls `Coding.profile_digest/0` (`:72-109`). `Coding.profile/0` resolves transport three times, while `Coding.run/2` and `start_proxy/2` resolve it again (`lib/harness_forge/execution/coding.ex:26-51,128-152,444-469`). `transport/0` treats every response except exact `Docker Desktop\n` as Unix, including a timeout/nonzero/malformed response (`:427-431`). A stored profile can therefore disagree with the relay/proxy route, or claim Unix without validated discovery. This is a source-derived risk, not an observed route-drift execution.

**Decision.** At each authoritative OpenCode task attempt, resolve and validate one local Docker endpoint plus recognized daemon route before persisting an executable task identity or creating relay/container resources. Use that attempt-owned snapshot for profile digest, relay mode, proxy topology and recorded identity. Reject unknown/error results with a bounded reason; do not infer Unix. Before release qualification, perform a fresh validated comparison through the existing gate (`lib/harness_forge/releases/validation.ex:8-49`); changed route/configuration makes the historical run inapplicable. Cleanup uses the route and names originally owned by that run. This repairs a prerequisite to representative qualification, not company fitness.

**Boundary and alternative.** `Readiness` deliberately abstains from current OpenCode task applicability without live commands (`lib/harness_forge/readiness.ex:105-111,198-219`; `test/harness_forge/readiness_test.exs:660-668`). MCP package inspection reports eligibility and `qualification: not_assessed_by_this_tool`, without granting runtime authority (`lib/harness_forge/mcp/tools.ex:69-81,248-263`; `test/harness_forge/mcp_tools_test.exs:332-350`). Keep both command-free and abstaining. A cached route would make these reads look decisive but could be stale; increasing the discovery timeout leaves identity disagreement and fallback intact.

**Acceptance.** Positive: recognized Desktop and Unix fixtures each yield one route used by persisted profile, relay and proxy. Negative: timeout, nonzero, malformed or unknown discovery refuses before resource creation and never labels Unix. Edge: changed endpoint/configuration refuses release qualification; interrupted cleanup retains original ownership; Inspect/Refresh and MCP read tools execute zero command/port calls and never promote saved identity. Execution owner: `Coding`/`Command`; evaluation owner: persisted identity; root: shared validation integration. QA proposes controlled command-boundary tests, actual Docker cases only if available, and independent no-probe traces. No tests or runtime probes were run for this planning note.
