# Adversarial choice: validate one coding-attempt route

**Recommendation (ADR sketch).** Context: `Coding.profile/0` calls `transport/0` three times, `run/2` observes it again, and proxy creation and container verification rediscover it (`lib/harness_forge/execution/coding.ex:28,130,427,444,653`). Any Docker-info response except exact `Docker Desktop\n` becomes Unix, including timeout, nonzero and malformed output. `Evaluations.applicability_identity/2` records a digest from that mutable profile (`lib/harness_forge/evaluations.ex:71-93`). Thus a route discrepancy can make the recorded identity inconsistent with execution; this is a **source-derived risk**, not an observed drift exploit.

**Decision:** add one validated, typed Docker transport observation at task-attempt admission; pass that immutable route into relay, proxy configuration, network verification and persisted environment-profile identity. A recognized Engine route and Desktop route are explicit; discovery failure is unavailable before relay/container creation. Recheck current applicability through an explicit live admission path, while read-only OpenCode inspection remains command-free and `not_assessed` (`lib/harness_forge/readiness.ex:105-116`). Keep cleanup keyed to existing run/workspace ownership, never a newly observed route. Do not reinterpret historical profiles as current authority.

**Why this unit wins:** five 06 retros rank company/model qualification first, but current two-task synthetic suite (`lib/harness_forge/evaluation/task_suite.ex:2,63`; `test/harness_forge/coding_evaluation_test.exs:115-149`) cannot establish representative company fitness. Goal-only evaluation still lacks that oracle; adding it now risks a misleading “qualified” label. Declared-conflict admission has higher direct policy value but needs reviewed obligation taxonomy and invalidation semantics beyond one bounded change (`lib/harness_forge/company.ex:234-261`). Portable approval requires signer, scope, freshness and revocation contracts; MCP-client revocation needs a separate client-identity lifecycle (`lib/harness_forge/mcp/auth.ex`). Neither should ride on route repair. The route fix removes a concrete ambiguity before any outcome evidence is interpreted, at modest but cross-cutting execution/evaluation blast radius.

**Falsifiable acceptance:** recognized Desktop and Engine observations yield the same route in dispatch, proxy/container checks and recorded profile. Timeout, nonzero, malformed or unknown OS refuses before resources and never asserts Unix. A route/config change invalidates applicability at live admission; cleanup still removes only originally owned resources. Readiness performs no Docker command and abstains. Verify with injected command responses and focused execution/evaluation/readiness tests, then root-owned canonical `mix test`; report Docker skips and real-route limits.
