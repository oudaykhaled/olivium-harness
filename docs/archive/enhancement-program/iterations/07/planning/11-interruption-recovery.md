# 07 proposal: finish the owned cleanup sweep after a partial failure

**User benefit.** An operator cancelling an evaluation, or restarting after service loss, gets the maximum safe teardown in that attempt and an honest incomplete status when any owned resource remains. This is a bounded reliability improvement, not a claim that interrupted company/model work is qualified.

**Evidence.** `Evaluations.cancel/1` records pending before teardown and preserves failure (`lib/harness_forge/evaluations.ex:132-158`); startup retries unfinished attempts (`:189-240`). But `cleanup_all/1` stops after `Execution.cleanup/1` fails (`:463-465`). `Coding.cleanup_owned/1` stops at the first failed container and therefore never reaches later names or the network (`lib/harness_forge/execution/coding.ex:803-820`). Existing names are deterministically run-scoped (`:957-968`), and each removal checks workspace/run/profile labels before deletion (`:668-697`, `:865-875`). Current tests cover cancellation and pending restart, but not a first-resource failure followed by independently removable owned resources (`test/harness_forge/coding_evaluation_test.exs:324-361,403-421`). The 06 handoff reports representative interruption/cleanup recovery as unproven (`docs/enhancement-program/iterations/06/handoff-to-07.md`).

**Decision.** Take one run-owned cleanup snapshot of the existing expected resource names and attempt every independently removable owned container, then the network, and both execution backends. Aggregate failures; report `complete` only after verified absence of all owned resources, otherwise `cleanup_failed` and retain retry eligibility. Preserve label verification, cancellation fencing and the original run/workspace identity. A broad health monitor, new recovery state machine or route redesign has greater lifecycle cost and cannot substitute for exhausting the known cleanup set. The proposed route snapshot from 06 addresses execution identity, a separate value; it should not be bundled here.

**Acceptance.** Positive: cancellation and startup reconciliation remove all owned resources and leave `cancelled`/`interrupted` with `complete`. Negative: one injected owned removal failure still attempts later owned resources and the other backend, retains `cleanup_failed`, and never removes a foreign-label resource. Edge: a lost Docker service yields incomplete status without claiming absence; a later retry succeeds idempotently, preserving the original cancellation outcome. Test with controlled command responses plus one guarded Docker ownership case; root schedules the single Mix window. Minimal ownership: `evaluations.ex`, `execution/coding.ex`, focused evaluation tests; no schema or UI change.
