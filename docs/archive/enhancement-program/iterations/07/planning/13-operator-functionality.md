# Operator journey: truthful task evaluation route

**Recommend one validated route observation per OpenCode task attempt.** An operator queues a model-backed task in the existing Evaluations form, then reads its persisted outcome. Today the run records `Coding.profile_digest()` during creation, while `Coding.run/2`, proxy creation, and container verification rediscover transport; failed or unfamiliar discovery becomes Unix (`lib/harness_forge/evaluations.ex:391-409`; `lib/harness_forge/execution/coding.ex:28-42,129-148,426-451,661`). This is a source-derived mismatch risk, not a demonstrated route-drift failure. A blocked run already appears in Portal with its reason and qualification status (`lib/harness_forge_web/live/portal_live.ex:2143-2211`). The operator benefit is an interpretable attempt: its recorded profile describes the route actually used, or its reason says why dispatch was refused.

**Decision and boundary.** Validate Docker Desktop versus supported Unix discovery once at the task-attempt boundary; carry that typed observation through profile, relay, proxy, and verification. Persist an explicit bounded discovery-unavailable reason with `runtime_qualified: false`, `usage_status: not_dispatched`, and truthful cleanup status when discovery fails. Preserve the existing run card; avoid another status panel. `Readiness` must keep current OpenCode identity *Not assessed* without a trusted current task observation (`lib/harness_forge/readiness.ex:105-113`). MCP package inspection must keep `qualification: not_assessed_by_this_tool`; its three fixed read-only tools do not execute evaluations (`lib/harness_forge/mcp/tools.ex:32-85,251-264`; `test/harness_forge/mcp_tools_test.exs:86-109`). This gives Portal/MCP consistent authority limits without expanding the MCP surface.

**Trade-off.** Declared conflict admission would improve company-policy coherence, but adds review/invalidation lifecycle; Goals-only continuation improves author navigation, but is primarily the even-iteration UX job. Route consistency is smaller and directly protects the meaning of qualification. It does not prove company/model outcomes or portable approval (`docs/enhancement-program/iterations/06/handoff-to-07.md`; `docs/enhancement-program/iterations/05/handoff-to-06.md`).

**Falsifiable acceptance.** Positive: recognized Desktop and Unix observations yield matching execution/proxy/profile identities in one attempt. Negative: timeout, malformed, nonzero, or unknown discovery persists a blocked, unqualified run before relay/container creation, without asserting Unix. Edge: route or configuration drift invalidates applicability; cleanup uses original owned-resource identity, while synchronous readiness remains command-free. Proposed ownership: one execution/evaluation author, with root integrating shared boundaries. Verify focused synthetic route/record/cleanup tests, then canonical `mix test` and a native Portal run-card check under root's coordinated window; no live provider qualification is claimed.
