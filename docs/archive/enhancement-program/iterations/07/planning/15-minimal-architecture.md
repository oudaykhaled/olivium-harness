# 15 — Minimal coherent architecture

**Recommend one validated transport observation for each task attempt.** `Coding.profile/0` calls `transport/0` three times; `Coding.run/2`, `start_proxy/2`, and `verify_container/6` call it again (`lib/harness_forge/execution/coding.ex:28,130,446,661`). Discovery maps every non-Desktop response, including timeout and malformed output, to Unix (`:427`). `Evaluations.create/2` records the profile digest before dispatch, then `execute_supported/2` runs coding (`lib/harness_forge/evaluations.ex:391,262`). The recorded profile can therefore describe a different route than the proxy. This is source-derived risk, not an observed drift incident.

**Decision/ownership.** In `Coding`, make discovery return only recognized Desktop/Unix observations or an explicit unavailable error; derive profile fields and execution/proxy verification from a supplied immutable route value. In `Evaluations`, obtain that value once for task admission, use it for the persisted profile digest and synchronous dispatch, and keep existing blocked-result semantics on discovery failure. The existing JSON result can carry the route if needed; no migration, new provider, or release endpoint is justified. Tests belong in `test/harness_forge/coding_evaluation_test.exs` with a deterministic discovery seam. Root coordinates any shared integration.

**Acceptance.** Positive: a recognized route produces one matching profile digest, relay socket choice, proxy config, network expectation and recorded result, despite a changed later discovery response. Negative: timeout, nonzero exit, malformed or unknown operating system blocks before relay/container creation and never labels Unix. Edge: a changed route makes later `Evaluations.applicability/2` refuse qualification; cancellation/reconciliation still remove only existing run/workspace/profile-owned resources; `Readiness` keeps OpenCode current identity unassessed without Docker commands (`lib/harness_forge/readiness.ex:105,203`). Verify focused cases, then root's coordinated canonical suite and guarded Docker checks; fixtures alone do not prove daemon behavior.

This repairs route-choice consistency, **not Docker daemon identity**: `Command.docker/3` resolves the local endpoint for each call (`lib/harness_forge/execution/command.ex:6-37`). Endpoint pinning through cleanup would also change command transport and durability and deserves a separate decision if current-daemon identity is required. Declared policy-conflict admission touches `Company.resolve` and a wider approval/invalidation lifecycle (`lib/harness_forge/company.ex:234`); portable approval receipts add signer and revocation policy. Goal-only evaluation/coverage is valuable but requires a representative task oracle. Route consistency is the smaller verifiable prerequisite; it does not establish company fitness.
