# 06 proposal: identify the package behind each export result

**Finding.** `PortalLive` stores only `:export_path` on success (`lib/harness_forge_web/live/portal_live.ex:36,432-443`), then renders one success notice after all artifact cards (`:1948-1976`). It omits the digest even though the form submits one and `Artifacts.export/3` returns `{digest,path}` (`lib/harness_forge/artifacts.ex:61-69,348`). With same-named versions or reordered cards, “Exported to …” does not identify the immutable package. Export failure goes through generic `finish/3`, clearing flash but retaining the previous success path (`portal_live.ex:733-741`); native05 observed a stale *direct-build* alert beside export success (`docs/enhancement-program/iterations/05/verification.md:55`). Readiness already labels exact digest and clears its report on selection/reload (`lib/harness_forge_web/components/package_readiness.ex:63-81`; `portal_live.ex:910-960`); export needs comparable ownership. The goal-only web test asserts only target text (`test/harness_forge_web/goal_claims_test.exs:128-139`).

**Decision (UI only).** In `PortalLive`, replace `:export_path` with one ephemeral export outcome keyed by the submitted full digest, carrying the returned digest/path on success or the submitted target and mapped reason on failure. Render outcome *inside its matching digest card*, with package name, version, full digest and destination. Use the returned identity as authority. Clear superseded export outcome on each attempt, package removal, privacy reset, revocation and remount. Keep a failed target in that card's input for correction; clear it after success. Show accurate fresh-directory, unsafe/missing-parent and filesystem remedies from existing error codes. Do not change export admission, artifact bytes, audit, approvals or readiness assessment; OpenCode task readiness remains command-free **Not assessed** under accepted03 amendment. Owner: one web author for `portal_live.ex` and focused LiveView tests; root coordinates shared/native work.

**Acceptance.** Positive: export B among A/B, reorder/reload records, and announce B's exact digest/path in B's card only; readiness selection remains independent. Negative: occupied target refuses without overwrite, retains B's input, identifies B and offers a fresh directory, with no old success or unrelated alert erased. Edge: retry A after B, delete/purge or lock/remount clears old result/private target; stale events cannot restore them. Keyboard reaches the failed input and perceivable status; card/result and full digest reflow at 320/390 CSS pixels and actual 200% zoom. Test the real LiveView and filesystem, including identical names, opposite submission order and failure-after-success. Comprehension and screen-reader speech remain unmeasured.
