# Iteration 04 proposal 08 — export alert lifecycle

**User benefit.** After export fails, the operator sees a safe remedy beside that package's directory field. A successful retry shows only the new success; a later failure removes the old “Exported to” result.

**Evidence.** `PortalLive` exports at `portal_live.ex:393–404`; success assigns `:export_path` and adds info flash without clearing error, while failure calls `finish/3`. `finish/3` clears flash but retains `:export_path` (`:695–702`). The page renders both flash and `@export_path` (`:1186–1191`, `:1769–1786`). `Artifacts.export/3` distinguishes `unsafe_artifact_path` for missing/symlinked parents and `export_conflict` for occupied destinations (`artifacts.ex:245–278,324–328`), yet `error_message/1` sends most contract errors to generic connector advice (`portal_live.ex:1060–1083`). Quality retrospective flags this defect (`iterations/03/retro/05-quality.md`).

**Decision / bounded change.** Give the export form a per-attempt result tied to its artifact digest. On submit, retire the previous export result. On failure, retain the attempted directory in the editable field and show fixed, actionable text: create/select an **existing, nonsymlink parent** with a fresh child name for `unsafe_artifact_path`; choose a fresh child for `export_conflict`. On success, clear the failure, show the successful path, and keep the form usable for another export. Keep other operations' flash behavior separate. No domain error details or arbitrary filesystem paths enter HTML except the operator's own submitted path rendered safely.

**Acceptance.** Real missing-parent and occupied-destination attempts show appropriate remedies and no stale success. Retrying into a fresh directory exports bytes verified against the artifact, clears the old error, and announces one success. Keyboard focus reaches the field/remedy; the field keeps the failed target until edited. Exporting another package or resetting/locking clears stale export state. `Artifacts.export/3` remains authoritative for containment, no-overwrite and admission; OpenCode task assessment remains **Not assessed**.

**Alternative / trade-off.** Static cleanup explanation has broad comprehension value and strong retrospective support, but this unit fixes a concrete failed-action recovery loop. Generic flash cleanup alone is smaller, yet cannot connect a remedy to the correct form or preserve the failed input. Risk: LiveView patching may retain stale DOM input; test server state and native keyboard retry, including 320px/200% layout. **Files/effort:** `portal_live.ex`, focused LiveView tests, ~0.5–1 engineering day plus independent browser verification.
