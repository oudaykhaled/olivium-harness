# Proposal 06 — Truthful static-evaluation guidance

**Benefit.** An operator inspecting a static package check should understand what was verified, why no runtime cleanup occurred, and what evidence a release still needs. This prevents an unattempted cleanup from reading like a cleanup incident, without reassuring anyone that a model-backed task passed.

**Evidence.** `Evaluations` initializes `cleanup_status: not_started` and takes a separate `static_integrity` path (`lib/harness_forge/evaluations.ex:249,265,404`). `Readiness.cleanup_stage/1` maps every non-`complete` value to blocked and `evaluation_cleanup_incomplete`; action priority selects cleanup before applicability (`lib/harness_forge/readiness.ex:255,300`). The UI announcement therefore leads with “Recorded evaluation cleanup is incomplete,” while the row shows “Not started” (`lib/harness_forge_web/components/package_readiness.ex:134,210,366`). Iteration03's [UX review](../../03/review/ux-validation.md) and [handoff](../../03/handoff-to-04.md) identify this confusion. The accepted [amendment](../../03/decision-amendment.md) separately requires OpenCode current task identity and matched-task admission to remain **Not assessed**.

**Scope and acceptance.** Change only the Packages readiness presentation for a verified selected `static_integrity` pass whose recorded cleanup is `not_started`: put “Static package check passed; this evaluation ran no model-backed task, so runtime cleanup was not attempted. Release review still requires a qualified task evaluation” beside the summary and cleanup row. Retain the exact recorded status, seven stage results, existing action, gate reason, refusal and release command behavior. A task with `cleanup_failed` must still lead with a cleanup warning; pending or unknown metadata must get no reassuring copy. A no-selection view must not imply a static pass. Keyboard reading order, 320 CSS-pixel layout and 200% zoom must expose the explanation before the lower-detail limitations. Domain/LiveView tests should prove these contrasting cases and unchanged report/gate values. No private run data should enter flash, telemetry or URL copy.

**Alternative.** Export error recovery is also valuable: the current handler uses generic `finish/3` after export failure and can retain a stale success path (`lib/harness_forge_web/live/portal_live.ex:393`). It is a separate filesystem interaction with no-overwrite risks, so defer it.

**Risk, files, effort.** Keep wording conditional on trusted, allowlisted kind/outcome/cleanup fields; do not infer current task identity from historical runs or change auth nonce, generations, reset, consent or purge behavior. Likely `package_readiness.ex` and focused `package_readiness_test.exs` only. About half a day including native comprehension checks.
