# Exact-package next actions

**Recommendation — functionality 03.** Add a read-only `PackageReadiness.for_digest/1` projection and an operator action on each saved Packages row. It should return ordered, typed states for **integrity**, **current company eligibility**, **runtime availability**, **task evaluation**, and **release approval**, each with the exact package digest, reason and permitted next action. The operator chooses a saved package; no “latest” package or run is inferred across digests. This turns an exportable package into an actionable qualification path without granting new authority.

[Company.Guide.next_action/5](../../../../../../lib/harness_forge_web/components/company/guide.ex) currently sends a built plan to Packages with generic export/evaluation advice. [PortalLive](../../../../../../lib/harness_forge_web/live/portal_live.ex) lists immutable artifacts, then separately asks for artifact and run selections in Evaluations and Releases. The projection should reuse [Harnesses.get/1 and eligible/1](../../../../../../lib/harness_forge/harnesses.ex), `Compiler.verify/1`, [Evaluations.applicability/2 and capabilities/0](../../../../../../lib/harness_forge/evaluations.ex), and [Releases.Validation.check/3](../../../../../../lib/harness_forge/releases/validation.ex). Readiness is recalculated from saved records and current runtime identities on reload/action; it is never persisted as approval. Only a verified, applicable, passed task run with complete cleanup may offer the existing exact release-approval action. Static integrity and runtime smoke may be run as diagnostics but never appear qualified.

**Observable acceptance.** For an exact saved digest, Packages shows one primary next action and distinct state/reason for all five gates. Missing artifact or failed integrity blocks downstream actions; changed claims or plan context instructs review/rebuild while preserving the immutable older artifact. An unavailable Codex/Claude managed backend, absent model, unsupported required control, or `unqualified` runtime version displays a blocker rather than a runnable task promise. A failed, cancelled, incomplete-cleanup or mismatched-suite/model/environment run cannot offer release approval. A valid run for another digest cannot be borrowed. After an eligible qualifying run, the action preselects its exact digest/run/scope, but `Releases.approve/1` still revalidates at submit. Tests should exercise these transitions and a stale-state race through domain and LiveView boundaries.

**Trade-off.** Product/architecture retros favor goal-origin policy and explicit conflict decisions first; UX/trust/quality favor readiness. This bounded path gives immediate operator value from existing gates, but leaves goal-backed rules, declared conflict admission and portable approval unresolved and visible. Do not label a synthetic pass company fitness; representative authorized work remains a separate qualification milestone.
