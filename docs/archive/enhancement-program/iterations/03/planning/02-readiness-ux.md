# Exact-package qualification readiness

**Gap.** Operators must choose an artifact and evaluation separately in the portal, then discover release refusal after submission. The [evaluation panel](../../../../../../lib/harness_forge_web/live/portal_live.ex#L1624) lists individual outcomes, while the [release form](../../../../../../lib/harness_forge_web/live/portal_live.ex#L1695) offers every run without showing whether it applies to the chosen package. This obscures the next safe action. Export already rechecks [current eligibility](../../../../../../lib/harness_forge/harnesses.ex#L120); evaluation admission rechecks eligibility and [artifact integrity](../../../../../../lib/harness_forge/evaluations.ex#L112). A passed static check does not qualify a release ([release validation](../../../../../../lib/harness_forge/releases/validation.ex#L8)).

**Change.** Add a read-only, workspace-scoped `Qualification.readiness(artifact_digest)` projection and show it beside the selected package in Packages, Evaluations and Releases. Return string-keyed `artifact_digest`, `plan_revision_hash` when bound, `integrity`, `eligibility`, `runtime_availability`, `task_evidence`, `cleanup`, `release_admission`, `blockers`, and one `next_action` with a destination. Derive each status from `Harnesses.get/1`, `Compiler.verify/1`, `Harnesses.eligible/1`, `Evaluations.capabilities/0`, existing runs, `Evaluations.applicability/2`, and `Releases.Validation.check/3`; never infer qualification from a run’s label alone. Show the exact evaluation ID and suite/model/runtime/environment identities for a usable run. Preserve distinct “unavailable,” “not attempted,” “failed,” “stale,” and “qualified evidence” states. Recompute on selection, evaluation completion, and approval attempt; release commands retain their existing admission checks. The known short Unix-socket path requirement belongs in the relevant blocked action, not as a universal warning.

**Acceptance.** Given an eligible exact package and applicable, completed, cleanup-complete qualified task run, readiness identifies that run and offers release review; static-only and smoke-only passes remain unqualified. Given a changed approved plan, revoked claim, changed model/suite/profile, unsupported managed runtime, cancelled run, or failed cleanup, readiness names the specific blocker and cannot offer approval. A package switch changes every displayed identity and run association. Domain tests assert these transitions; portal tests assert the selected digest, blocker and action remain paired after refresh. This projection grants no approval and makes no company-fitness claim.

**Trade-off.** Policy intent and declared conflicts ([architecture retrospective](../../02/retro/03-architecture.md)) would improve what can be expressed, but require authority and schema changes. Portable approval ([trust retrospective](../../02/retro/04-trust.md)) improves independent verification after export, but requires signer trust and revocation design. Readiness gives immediate operator value from existing gates with smaller blast radius. Risk: a stale display could mislead; recompute at navigation and action time, and make domain refusal authoritative.
