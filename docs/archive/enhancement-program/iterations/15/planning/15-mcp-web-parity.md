# Supporting MCP evidence parity for the web journey

**Scope and priority.** Fix the demonstrated whole-question evidence omission in the browser's shared retrieval path first. A nine-content-term public question selected three passages and omitted `policy.md`; the focused question selected four including its two-reviewer rule. This proposal is a dependent, read-only MCP parity slice, not a new product journey or an alternative retrieval engine. MCP is currently disabled on Main14, so acceptance must occur in a separate authorised local configuration.

**Proposal.** Extend the existing authenticated `HarnessForge.MCP.Tools`/`Protocol` with a bounded `harnessforge_company_run_evidence` observation for an exact `run_id` plus `run_digest`, with an optional opaque page cursor and an exact selected-passage context request. Delegate to `Company.Retrieval.read_run/4` and `open_passage/4` using the authenticated caller. Return the same checked candidate order, selected status, provisional lane/relation, exact source/revision/hash/UTF-8 pins, bounded snippet/context, capture/index readiness, semantic-coverage-unknown and pagination that the web review consumes. A response is data for inspection, never synthesis consent, a claim decision, a plan decision or later-operation authority. Deny stale, revoked, changed-scope or unknown run/context through existing currentness and privacy fences; do not expose parent source bodies or unbounded corpus lists. Keep the current four metadata tools intact. No new standalone CLI flow, graph/RAG/Jev framework or model fallback.

**Reuse and handoff.** The browser already calls `Retrieval.retrieve`, `read_run` and `open_passage`; `read_run` pages at most 25 checked candidates, and `open_passage` checks a candidate against its exact run. `MCP.Tools` presently offers only readiness for a retrieval run. Share the retrieval service and use the existing `Passages`, `OriginV2`, `AnalysisV2`, stage authority, exact claim/plan decisions, compiler/export and evaluations. The MCP result should point the human to the existing browser review, where correction, exact claim approval and a separate exact plan approval precede actual files.

**Checkable acceptance.** On independently authored public development cases, compare the existing FTS5 baseline with whichever bounded full-query, multi-query or packing correction wins measured critical-policy/contrary recall, irrelevant inclusion, abstention, caps and latency. Include reordered middle terms, later exception/failure, distractors and no-answer cases; all-abstention fails answerable cases. For a corrected run, web and MCP must show identical run digest, selected passage identities and exact context within page limits. A stale/revoked run must fail in both surfaces; retrieval must grant no consent or approval. A human correction tied to the saved goal must reach actual exported bytes only after separate exact claim and plan approvals; rejected content stays absent. Representative task evaluation remains `BLOCKED model_not_selected` until an authorised configured model exists. Scripted synthesis proves mechanics only.

**Alternatives.** Readiness-only MCP is smallest but leaves clients unable to inspect why a run is ready. A new MCP search/synthesis workflow risks duplicate authority, consent and currentness logic. The bounded read-only adapter adds one contract while keeping web review authoritative. If evidence parity competes with the policy-omission fix, defer this adapter until the shared retrieval correction passes its public development cases.
