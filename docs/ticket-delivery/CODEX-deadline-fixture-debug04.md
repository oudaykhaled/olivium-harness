# Codex deadline / SQL-owner diagnosis 04

No test or production code was changed. The evidence does not establish an ordinary fixture-owner lifetime bug; changing delays, deadlines, assertions or retrying unchanged would not resolve the demonstrated failure mechanism.

Root124 passed 102 tests (seed 609495, 31.8 s). Root134 ran 72 tests with one failure (seed 312623, 26.9 s). Both records are source-stable. The entire native Responses fixture, Runtime, HTTP provider and local identity source have identical hashes in both checks and the current tree. The changed rule-policy code therefore did not directly edit this failing path.

The failed test calls Runtime.responses synchronously with a 500 ms transport budget. Its synthetic peer delays each of three metadata routes by 120 ms and inference by 350 ms. It requires one cumulative deadline, actual inference admission, uncertain/unknown settlement and a retained reservation. The log instead reports a DBConnection client exiting, then raises when Ledger.reconcile begins at runtime.ex:165. The test process was still performing settlement; the evidence contains no mapped identity or stack for the exited client PID.

The fixture checks out a committed, non-transactional SQL Sandbox connection and shares it with relay/collector processes. config/test.exs uses Sandbox with pool_size 1. Existing owner setup is intentional: independent Relay GenServers otherwise fail source/privacy checks. It must not be removed casually. Synthetic delayed upstream handlers only read their Agent state and write HTTP responses; they do not query Repo. Their delay or late exit alone cannot explain a database client being killed.

HTTP.bounded_request runs both native transport and its dispatch guard in supervised tasks. Every task installs an absolute :kill timer and the caller also uses brutal Task.shutdown on expiry. The dispatch guard invokes Runtime.current_identity; metadata guards invoke current_sources, which queries privacy/configuration/connections. DBConnection.Ownership.Proxy explicitly shuts down the shared holder on a dead client ETS transfer; ConnectionPool logs the observed client-exited message. Thus a cutoff that lands during guard SQL can invalidate the shared Sandbox connection before the original caller settles its reservation. The three metadata delays nominally consume 360 of the 500 ms allowance before accounting for repeated guards and scheduling. This supplies a credible timing-sensitive mechanism, not a captured worker-PID proof.

The leading hypothesis is cancellation of a SQL-using collector, amplified by the shared committed Sandbox holder (confidence 0.85). An unrelated lingering client remains possible until its PID is identified. A general production cancellation/settlement issue cannot be excluded: production pool recovery differs from the shared Sandbox proxy, but the product does permit deadline-killed workers to execute SQL-bearing guards. The prior scoped review explicitly limited its claim about database-contention headroom; that does not explain away this unhandled exit.
