## Installed lifecycle source

- `@e2e-dev/web/dist/surface.js:443–447`: `open` calls `ensurePage()` before it can call `page.goto` with the test's requested URL.
- `attempt-session.js:188–199`: the first page of a persistent attempt is the **first nonclosed tab in the attached context**, regardless of the currently visible tab. It sets `firstPage = false`, then awaits that tab's `goto('about:blank')` before returning it. This blank document installs the context's init scripts; it is not a HarnessForge destination.
- `attempt-session.js:155–178`: the attempt publishes its page binding only after `nextPage` succeeds. A failure inside that first blanking therefore precedes page publication and the real requested navigation.
- `cdp-recovery.js:52–66`: a new persistent attempt attaches the dedicated default context with `page: null`; first-page selection happens later. `browser-connection.js:82–88` documents that CDP cleanup detaches and leaves the host-owned Chrome running. `attempt-session.js:249–251` uses that cleanup, so old tabs can remain between independent CLI runs.
- The current owned config explicitly attaches to that existing Chrome/profile using `cdpEndpoint` and `reconnectEndpoint`; this is not a newly launched browser per independent CLI.

This establishes a competing navigation on the retained first tab during adapter preparation. The leading origin explanation is an old auth redirect: `Workspaces.init` creates a fresh session epoch on every VM start; `OperatorSession.valid?/1` compares it and its plug/on-mount path sends invalid sessions to `/login`. Installed Phoenix `view.ts:1333–1341` forwards a join redirect; `live_socket.ts:917–922` unloads and delegates to `Browser.redirect`, whose `browser.ts:79–89` assigns `window.location.href`. The exact initiating old request/client was not captured by check 82, so that origin remains a source-supported inference. A concurrent controller or another pending old navigation is the competing explanation.

The earlier MCP028 opening failure and MCP029 successful normal login navigation are consistent with this lifecycle. They do **not** by themselves prove the first tab was settled: `firstPage` has already been flipped when its initial `about:blank` fails, so the next navigation in that same adapter can allocate a different tab. A stable active tab is not sufficient evidence about the tab a fresh CLI will choose.

## Verified supported route to the exact first tab

Root proposed a separate project-tool configuration importing the frozen base config, without editing that config, the test or the framework. Installed `engine.d.ts:12–24` explicitly exposes public `PlaywrightLiveSurface.context()` and `.page()`; `engine.js:20–24` maps them to the current attempt's `requireContext` and `requirePage`. The context exists from `startAttempt`, while a page exists only after the first successful `app.open`/`browser.goto`. `surface.js:387–396` confirms `context()` does not require a published page. Therefore the tool should use `surfaceOf(base.targets[0].engine).context()` directly. It must not depend on `surface.page()` after a failed first-page preparation.

`BrowserContext.pages()` and `Page.isClosed()` are installed public Playwright APIs (`playwright-core/types/types.d.ts:10332–10335` and `3803–3806`). Selecting `context.pages().find(page => !page.isClosed())` is exactly the expression used by the framework's `nextPage`; it addresses the actual reused first tab without private fields, raw CDP or active-tab assumptions. The framework's public-surface documentation labels these native operations out of band: retain the project-tool receipt separately and do not count preparation as a passed CLI action.

The bounded tool recommendation is supported: reuse the same imported engine instance; register one mutating project tool through the existing extension; require an existing first page with URL `about:blank` or exact origin `http://127.0.0.1:8889` and path `/login`, `/setup` or `/setup/…`; navigate that page once to public `/login` with normal load completion; await visible `#access-code`; verify the final exact login location and that the same page remains the first nonclosed page; return only path, title and visible boolean. No input value, cookie, image, context creation/reset, page/context close, auth bridge or state injection is needed. Any guard, navigation or visibility failure must remain a failure. Finish the adapter normally, then let Root run the unchanged recovery CLI once with fresh authentication still required.
