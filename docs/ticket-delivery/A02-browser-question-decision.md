**Competing interpretations checked.**

- A question change invalidates evidence relevance and analysis: correct, but that justifies clearing run/page/passage/stage/claim/session outcome, not the corpus coverage classification. Preserve separate fact lifetimes.
- The declaration actually became stale: the observed event and unchanged scope URL do not show a lifecycle change. Existing `refresh_readiness` already rechecks the declaration and withholds stale previews while retaining an explicit reference. Dropping the reference is the wrong stale response because it enables fallback.
- This is only a collapsed-details presentation issue: contradicted by the changed readiness reason and unconditional server reference clearing.
- The current test authorizes the behavior: `test/harness_forge_web/company_readiness_test.exs:408–425` explicitly expects both references nil after question change. It encodes implementation behavior that conflicts with AC3 and the scope contract; replace those assertions while retaining its authority/invalid-link coverage.

**Recommended minimal change.** In the shared valid question/retrieve handler, when question or mode changes, use the existing question-work invalidator (`clear_run`, lines980–990) rather than `clear_requirements`. Retain the saved DTO/ref and readonly classification and continue summary/currentness checks. A deliberate retrieval still clears prior question work before dispatch. Keep full clear/stale behavior for actual connection/project/goal selection, workspace/session/privacy reset, revoked access, changed corpus generations, supersession, and receipt/configuration mismatch. Do not change declaration schema, auto-save a new declaration, silently rebind receipts, restore an arbitrary latest declaration, or gain command authority from readiness.

Busy handling matters: native controls are disabled while busy, but the server currently accepts forged question-change events. Clearing session observation while a synthesis is active can leave its ignored callback unable to clear busy; retrieval callbacks bind only view generation. The narrow option is to reject question/mode edits while busy, matching the UI. If edits during operations must be supported, they instead need operation-bound cancellation/currentness and late-result tests; that is a larger change. Do not increment the scope generation casually just to clear question work, since it also binds metadata cursors and view context.

The source-search filter handler at live:191–198 also clears requirements. It is an adjacent same-scope reset worth deciding explicitly: a text filter does not change declared coverage either. Preserve coverage there if included in this bounded fix, but retain any filter-specific result reset. This observation is source-derived; the actual browser finding concerns the question.
